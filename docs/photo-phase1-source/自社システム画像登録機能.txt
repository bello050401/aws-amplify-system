## A-2. 実装方針

この機能は既存Inventory / Listingを置き換えるものではない。
**既存機能を壊さず、撮影画像の受入・確認・紐付け層を追加する。**

最重要原則:

- ローカルPhoto StationとAWS/Webの責務を分離
- 1回のSD差分取込 = 1商品 = 1 PhotoBatch
- 商品との紐付けはWeb側のみ
- S3 object keyは登録後も移動しない
- Inventoryとの紐付けはPhotoBatchに持つ
- PhotoAssetにinventoryIdを複製しない
- DynamoDB Scanを前提にしない
- 冪等性は「検索して無ければCreate」ではなく条件付き書込みで保証
- 300枚級バッチでも破綻しない
- 同時操作・再送・通信断を正常系として設計
- 既存画像は初期導入時に一括移行しない
- 画像バイナリをNext.js API経由で中継しない
- S3への直接uploadを基本とする
- 本番データ削除・大規模migration・IAM変更は承認前に行わない

# B. 業務フローの確定仕様

現場では以下を前提とする。

```text
商品Aを撮影
↓
SD-Aを撮影専用PCへ挿入
↓
ローカルPhoto Stationが前回取込との差分だけ検出
↓
その差分全体を「商品Aの撮影バッチ」として扱う
↓
ローカルでLightroom Classic + 自動加工
↓
加工済みJPEG / thumbnailをAWSへアップロード
↓
PhotoBatch = READY_FOR_REVIEW
↓
撮影担当はその間にSD-Bで商品Bを撮影
```

AWS/Web側:

```text
左メニュー「画像登録」
↓
未登録撮影バッチ一覧
↓
画像を目視確認
↓
不要画像削除 / 必要なら追加upload
↓
「撮影待ち」を中心にInventory選択
↓
PhotoBatchをInventoryへ紐付け
↓
商品詳細に画像表示
↓
EC出品画面で使用画像を選択
```

**撮影時点ではInventoryを選ばせない。**

# 1. 最重要の設計原則

## 1.1 ローカルPCとAWSの責務を混在させない

ローカルPCは以下のみ担当する。

- SDカード検知
- 新規画像差分検出
- ローカルコピー
- Lightroom Classic連携
- 自動画像加工
- 撮影バッチ生成
- S3アップロード
- AWSへアップロード完了通知

ローカルPC側では在庫選択を行わない。
在庫の紐付けはWeb自社システム側のみで行う。

---

## 1.2 「1回のSD取込 = 1商品 = 1撮影バッチ」

業務ルールとして、1商品を撮影し終えたらSDカードをPCへ接続する。

例:

- 商品AをSD-Aで撮影
- SD-AをPCへ挿入
- 自動取込開始
- その間にSD-Bで商品Bを撮影
- SD-BをPCへ挿入
- 以下繰り返し

そのためローカルPC側では画像を商品ごとに分割する必要はなく、
1回の差分取込結果全体を1つの PhotoBatch として扱う。

---

## 1.3 S3上のオブジェクトは登録後も原則移動しない

画像を在庫へ紐付けた後でも、S3キーは変更しない。

悪い例:

photo-batches/batch-001/processed/001.jpg
↓
inventory/INV-123/001.jpg へ移動

これは禁止。

代わりにDB上で PhotoBatch / PhotoAsset と Inventory の関係を作る。

理由:

- S3コピー・削除を減らす
- URL変更を防止
- 冪等性を担保
- 障害点を減らす
- 監査履歴を維持
- 将来の再紐付けに対応しやすい

---

## 1.4 PhotoBatch と PhotoAsset を分離する

PhotoBatch:
1回の撮影・取込単位

PhotoAsset:
その中の画像1枚単位

Inventory:
既存の商品 / 在庫

Listing:
EC出品

関係:

PhotoBatch
  └ PhotoAsset x N
        ↓
     Inventory
        ↓
      Listing

---

# 4. データモデル

## 4.1 PhotoBatch

目的:
1回のSD取込・1商品の撮影単位を管理する。

推奨フィールド:

- id: ID!
- batchCode: String!
  - 人間が読めるコード
  - 例: PHOTO-20260915-0001
- status: PhotoBatchStatus!
- captureStartedAt: AWSDateTime
- captureEndedAt: AWSDateTime
- importedAt: AWSDateTime
- uploadedAt: AWSDateTime
- registeredAt: AWSDateTime
- sourceDeviceId: String
  - ローカル撮影PC識別子
- sourceSdCardId: String
  - SD識別子
- localImportSessionId: String
  - ローカル側の冪等キー
- imageCountOriginal: Int
- imageCountProcessed: Int
- imageCountUploaded: Int
- coverPhotoAssetId: ID
- inventoryId: ID
- linkedByUserId: String
- linkedAt: AWSDateTime
- notes: String
- errorCode: String
- errorMessage: String
- createdAt
- updatedAt

推奨ステータス:

CREATED
UPLOADING
READY_FOR_REVIEW
LINKED
ARCHIVED
ERROR

最低限の意味:

CREATED:
PhotoBatch作成直後。まだ画像登録前。

UPLOADING:
ローカルPCからアップロード中

READY_FOR_REVIEW:
加工済み画像がクラウドへ揃い、Web上で確認可能

LINKED:
Inventoryへ登録済み

ERROR:
アップロードまたは処理異常

# 4.5 DynamoDBアクセスパターンとインデックス（必須）

DynamoDBでは「モデルを作る」だけでは不十分。
実際の画面・APIがScanにならないよう、アクセスパターンを先に固定する。

最低限必要なアクセスパターン:

1. 未登録PhotoBatchをuploadedAt降順で取得
2. Inventoryに紐づく全PhotoBatchをlinkedAt降順で取得
3. PhotoBatchに属するPhotoAssetをsequence順で取得
4. localImportSessionIdから既存PhotoBatchを取得
5. 同一Batch内でsha256から重複Assetを検出
6. Listingに属する画像選択をsequence順で取得
7. PhotoAssetがListingで使用中か逆引き

推奨インデックス例:

PhotoBatch:
- byStatusUploadedAt(status, uploadedAt)
- byInventoryLinkedAt(inventoryId, linkedAt)
- byLocalImportSessionId(localImportSessionId)

PhotoAsset:
- byBatchSequence(photoBatchId, sequence)
- byBatchSha256(photoBatchId, sha256Processed)

ListingImageSelection:
- byListingSequence(listingId, sequence)
- byPhotoAsset(photoAssetId, listingId)

AuditLog:
- byBatchCreatedAt(batchId, createdAt)
- byInventoryCreatedAt(inventoryId, createdAt)

Amplify Gen2で同等のsecondary indexを定義すること。
未登録一覧やInventory画像取得にテーブルScanを使わない。

---

# 4.6 InventoryとPhotoAssetの関係を正規化する理由

今回の業務ルールでは「1撮影バッチ = 1商品」である。
よってinventoryIdはPhotoBatchにだけ保持する。

PhotoAssetにinventoryIdを複製すると:

- バッチ登録時に画像枚数分の更新が必要
- 300枚級で大量書込み
- PhotoBatchとPhotoAssetのinventoryId不一致が起こり得る
- 再紐付けが重くなる
- TransactionWrite上限を意識する必要が出る

ため、初期設計では禁止する。

Inventoryの商品画像取得:

Inventory
  ↓ byInventoryLinkedAt
PhotoBatch x N
  ↓ byBatchSequence
PhotoAsset x N

とする。

必要になった場合のみ、後から検索用の非正規化を追加する。

---

# 4.7 複数撮影バッチ

1つのInventoryに複数PhotoBatchを許可する。

# 5. S3設計

推奨キー:

photo-batches/{batchId}/original/{assetId}.{ext}
photo-batches/{batchId}/processed/{assetId}.jpg
photo-batches/{batchId}/thumbnail/{assetId}.jpg

例:

photo-batches/01JXYZ.../processed/01JABC....jpg

S3オブジェクトキーに商品名・ブランド名を含めない。

理由:

- 商品名変更に影響しない
- 日本語文字列を避ける
- URL安全性
- 参照安定性
- 紐付け変更に強い

---


# 5.5 S3アップロード完全性

presigned PUT発行時に可能な範囲で以下を固定:

- Content-Type
- Content-Length上限
- checksum

completePhotoAssetUpload時にHeadObject等で:

- object存在
- content length
- checksum / metadata

を確認してREADYへする。

「クライアントが完了と言っただけ」でREADYにしない。

ただしBatch finalize時に全画像へ再HEADはしない。
検証はAsset complete時に分散して行う。

---


# 6. original RAWの保存ポリシー

Phase 1のAWS側は「加工済みJPEG + thumbnail」を必須とする。
RAWのAWS保存は必須にしない。

理由:

- RAWは容量が大きい
- 通常の商品画像確認・EC出品ではprocessed JPEGで足りる
- S3転送時間と保管費用が増える
- Photo Stationの高速回転を阻害する可能性がある

推奨初期運用:

ローカルPC:
- RAWを一時保持
- processed JPEGのAWS登録成功後も一定期間（例7日）だけ保持
- 期間経過後、自動クリーンアップ

AWS:
- processed JPEG: 長期保持
- thumbnail: 長期保持
- RAW: 高額商品等、明示設定時のみ将来対応

RAW削除ルールはローカルPhoto Station側設計で最終決定する。
AWS v1実装にS3 RAW Lifecycleを先行導入しない。

# 7. ローカルPCとのAPI契約

ローカルPCがDynamoDBを直接操作することは禁止。

必ずAppSync / API層を通す。

必要API概念:

## 7.1 Create Photo Batch

入力例:

{
  "localImportSessionId": "DESKTOP01-SD02-20260915T103200",
  "sourceDeviceId": "BELLO-PHOTO-PC-01",
  "sourceSdCardId": "SD-A",
  "imageCountOriginal": 24
}

返却:

{
  "batchId": "...",
  "batchCode": "PHOTO-20260915-0001"
}

localImportSessionId を冪等キーとして扱う。

重要:
Amplifyの通常Modelだけでは「一意制約」を保証できない場合がある。
単なるGSI検索 → Createでは競合時に重複Batchが作られ得る。

実装は必ず以下のいずれかで原子的に一意性を担保する:

- 専用Idempotencyレコードを条件付きPut
- Lambda内でDynamoDB conditional write
- localImportSessionIdを一意キーとして扱える専用テーブル

同じsessionIdで再送された場合、
新規PhotoBatchを作らず既存batchを返す。

---

## 7.2 Request Upload URL

各画像についてpresigned URLを返す。

入力:

{
  "batchId": "...",
  "fileName": "DSC01234.JPG",
  "sha256": "...",
  "type": "PROCESSED"
}

返却:

{
  "photoAssetId": "...",
  "uploadUrl": "...",
  "s3Key": "photo-batches/.../processed/....jpg"
}

---

## 7.3 Complete Asset Upload

入力:

{
  "photoAssetId": "...",
  "sha256Processed": "...",
  "widthProcessed": 3000,
  "heightProcessed": 2000,
  "fileSizeProcessed": 1240000
}

サーバー側でS3 object存在確認を行ってからREADYへ更新する。

---

## 7.4 Complete Photo Batch

入力:

{
  "batchId": "...",
  "imageCountProcessed": 24,
  "imageCountUploaded": 24
}

サーバー側で:

- expected asset件数
- READY件数
- FAILED件数
- 必須メタデータ

を確認。

各AssetのS3存在確認はcompletePhotoAssetUpload時に1件ずつ行う。
completePhotoBatch時に300オブジェクトへ再度HEADを投げる設計にはしない。

expected == READY件数 かつ FAILED == 0 の場合のみ READY_FOR_REVIEW。

---


# 7.5 Presigned URL発行の効率化

1商品で50〜300枚を想定するため、
画像1枚ごとにWeb UI相当の往復を強制しすぎない。

初期実装では以下いずれかを採用:

推奨A:
requestPhotoAssetUploads(batchId, assets[最大25〜50件])
で複数Assetを一括登録し、複数presigned URLを返す。

代替B:
1枚ずつ発行。ただしローカル側が最大4〜8並列で処理。

一度に300件の巨大Mutationを送ることは避ける。
25〜50件程度のchunkを基本とする。

Photo Stationは各chunkを再送可能にし、
asset単位の冪等性を保つ。



# 7.6 Batch Manifest

PhotoBatchには「この取込で何枚を予定しているか」を固定する。

最低限:

- expectedAssetCount
- completedAssetCount
- failedAssetCount

を持つ。

ローカルPCの再起動や通信断後でも、
AWS側を見るだけで:

「24枚予定 / 21枚完了 / 3枚未完了」

が分かる状態にする。

PhotoBatchをREADY_FOR_REVIEWへ移す条件は
completedAssetCount == expectedAssetCount
かつ failedAssetCount == 0。


# 8. 冪等性

この機能では冪等性を最重要とする。

ローカルPCはネットワーク切断やアプリ再起動があるため、
同じ処理が何度も送信される前提で設計する。

必須冪等キー:

- localImportSessionId
- sha256Original
- sha256Processed
- photoAssetId
- batchId

同一batch内の同一sha256画像は重複登録を避ける。

ただし同じ画像が別batchに存在することはあり得るため、
システム全体で一意にはしない。

# 10. 画像登録一覧画面

URL例:

/admin/photo-registration

表示対象:

カード形式を推奨。

1カードにつき:

- 代表サムネイル
- 撮影日時
- アップロード日時
- 画像枚数
- batchCode
- 警告有無

# 18. 登録処理

ユーザーがInventoryを選択して登録。

重要:
PhotoAsset全件へinventoryIdを書き込まない。
1バッチが300枚の場合、全Asset更新は不要な大量書込みとなり、
DynamoDB TransactionWriteの上限にも抵触し得る。
Inventoryとの関係はPhotoBatch.inventoryIdを唯一の正とする。

登録時:

1. PhotoBatch.inventoryId = inventoryId
2. PhotoBatch.status = LINKED
3. PhotoBatch.linkedAt = now
4. PhotoBatch.linkedByUserId = currentUser
5. 必要ならInventory.photoStatusを更新
6. AuditLog作成

PhotoAssetはphotoBatchIdのみでPhotoBatchへ所属する。

同一Inventoryへ複数PhotoBatchを紐付け可能とする。
これは再撮影・追加撮影を想定した仕様である。

リンクMutationは条件付き更新とし、
inventoryIdが既に設定済みの場合はCONFLICTを返す。
二人のスタッフが同じバッチを同時登録しても二重確定しないこと。

# 93.5 開発シミュレーションで確認済みの主要失敗パターン

## ケースA: 300枚をInventoryへ紐付け
v1案のように全PhotoAssetへinventoryIdを書き込むと、
大量更新・部分失敗・再紐付け負荷が発生する。

v2:
PhotoBatch.inventoryIdのみ更新。
300 Assetは触らない。

## ケースB: Photo StationがcreatePhotoBatchを二重送信
「GSIで検索して無ければCreate」だけでは同時実行で重複し得る。

v2:
conditional write / idempotency recordで原子的に一意化。

## ケースC: 300枚のfinalizeでS3 HEADを300回
finalizeが遅くなり、Lambda timeoutやUX悪化要因になる。

v2:
各Asset complete時に1件ずつS3検証。
Batch finalizeはDB状態集計のみ。

## ケースD: 商品登録後にS3 pathをInventory pathへ移動
URL変更・コピー中失敗・二重保存が起きる。

v2:
S3 keyは不変。DB linkだけ変更。

## ケースE: 同じBatchを2人が同時登録
後勝ちでinventoryIdが上書きされる危険。

v2:
条件付きupdate。
既にlinkedならCONFLICT。

## ケースF: Listingで使っている画像を商品詳細から削除
出品下書きの画像参照が壊れる。

v2:
Listing利用中Assetは削除ブロック。

## ケースG: 未登録一覧をDynamoDB Scan
データ増加で遅くなり、コストも増える。

v2:
status + uploadedAt GSIを必須化。

## ケースH: RAWを全てAWSへ送る
撮影→SD→次の撮影という高速運用に対し転送ボトルネック。

v2:
Phase 1 AWSはprocessed + thumbnailを中心とし、
RAWはローカル一時保持を基本とする。

# AB. Claude Codeへの最終メッセージ

本機能の目的は「高機能な画像管理画面を作ること」ではない。

目的は、

**撮影担当者が商品撮影後にSDを挿すだけでローカル処理を完了させ、Web側では未登録画像を目視確認して商品へ短時間で紐付け、その画像を商品詳細とEC出品へそのまま流用できる状態を作ること。**

そのため、以下を常に優先する。

1. 撮影現場の操作を増やさない
2. Webの登録操作を数クリックで終わらせる
3. 既存データを壊さない
4. 再送・通信断・二重操作に強くする
5. 画像枚数が増えても性能劣化しにくくする
6. ローカルとAWSを疎結合にする
7. 将来のAI画像処理・再加工に拡張できるようにする

以上。
