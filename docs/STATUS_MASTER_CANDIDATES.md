# 状態マスタ（StatusMaster）の調査と候補（2026-09-04）

**本番マスタへの登録は一切行っていません。**

---

## 0. 結論（2026-09-04 確定）

**Category を正式な現行の状態管理として維持します。StatusMaster へは移行しません。**

決まったこと:

| | |
|---|---|
| 現行の状態管理 | **`Category`**（発送完了 / 販売中 / 破棄 / 補修待ち …） |
| `StatusMaster` | **使わない**。データ登録もしない |
| 並行運用 | **しない** |
| 設定画面の「状態」タブ | **UIから削除済み**（前フェーズで追加したもの） |
| データモデル・関連コード | **残存**。スキーマ削除は migration と Amplify への影響があるため別作業 |

削除したのは設定画面の「状態」タブだけです。このタブは `StatusMaster` を
**書き込む唯一の場所**でした。他の参照（一覧の状態列・登録/編集フォームの選択・
CSV入出力・検索フィールド）はすべて読み取りで、いずれも0件のまま今までどおり動きます。

Category を参照する処理（販売中 / 発送完了 / 補修待ち / 破棄 の判定、EC出品対象、
在庫一覧の絞り込み、商品編集、ZAICO同期）には一切触れていません。
回帰確認: verify:inquiry 247 / verify:import 58 / verify:zaico 80 /
verify:zaico-mapping 45 / verify:listing 112 / verify:inventory-cursor 20 /
verify:product-identification 90 すべて合格。

以下は、その判断に至った調査の記録です。

## 1. 調査してわかった、いちばん大事なこと

**「状態」はすでに存在し、実際に運用されています。ただし置き場所が `StatusMaster` ではなく `Category`（カテゴリ）です。**

カテゴリマスタに登録されている20件は、商品の分類（ソファ・椅子・テーブル…）ではなく、
**在庫のライフサイクル状態**でした。実データの分布（在庫5,329件）:

| 件数 | カテゴリ名 | これは何か |
|---:|---|---|
| 4,576 | 発送完了 | 状態（終端） |
| 271 | 販売中 | 状態 |
| 179 | 破棄 | 状態（終端） |
| 133 | 事務所備品 | 用途区分（状態ではない） |
| 48 | 補修待ち | 状態 |
| 31 | 無償提供 | 用途区分 |
| 26 | 複数在庫 未出品 | 状態 |
| 13 | 出荷指示済 | 状態 |
| 11 | 出品待ち | 状態 |
| 9 | 保留 | 状態 |
| 8 | コーディネート用 | 用途区分 |
| 8 | 五十嵐さん | 担当者？（状態でも分類でもない） |
| 5 | 撮影待ち | 状態 |
| 4 | 業者間 | 販路 |
| 4 | 入金待ち | 状態 |
| 3 | 出品待ち,川越移動予定 | **状態＋移動予定を1項目に詰め込んでいる** |
| 0 | 大原確認 / 市川確認 / 川越移動予定 / 売り切れ | 登録済みだが未使用 |

コード側もこれを前提に書かれています。`lib/inventory/masterSeed.ts` の `CATEGORY_SEED` は、

```
補修待ち → 撮影待ち → 出品待ち → 販売中 → 売り切れ → 入金待ち → 出荷指示済 → 発送完了
```

という**業務フローそのもの**です。さらに次の処理が「カテゴリ名＝状態」に依存しています。

| 場所 | 依存の内容 |
|---|---|
| `lib/inquiry/onSaleCategory.ts` | `ON_SALE_CATEGORY_NAME = "販売中"`、`PAST_INVENTORY_CATEGORY_NAMES = ["発送完了","破棄","売り切れ"]` で商品特定の対象を絞る |
| `lib/imageProcessing/jobService.ts` | カテゴリが「撮影待ち」→「出品待ち」へ変わった瞬間を加工ジョブの起動条件にしている |
| `lib/inquiry/productResolver.ts` | 注文由来の商品特定で「破棄」だけを除外する |
| 在庫一覧のサイドバー・URL（`?categoryIds=`）・検索・件数集計 | すべてカテゴリを絞り込み軸として使う |

一方 `StatusMaster` は **0件**、`Inventory.statusId` を持つ在庫も **0件**。
ZAICO側の `state` も実データで**全件が未設定**（1,571件を確認、すべて `undefined`）でした。
つまり `StatusMaster` は「同じ概念のために作られたが、一度も使われなかった側」です。

## 2. したがって、問いは「どの状態を作るか」ではありません

登録すべき状態は**すでに実データにあります**。本当の判断は次の3択です。

### 案A. 現状維持（`Category` を状態として使い続け、`StatusMaster` は使わない）

| | |
|---|---|
| 作業量 | ゼロ |
| 利点 | いま動いているものを一切触らない。移行事故が起きない |
| 欠点 | 「カテゴリ」という名前と中身が食い違ったまま。商品分類（ソファ・椅子…）を持つ場所が無い |
| 欠点 | 設定画面に「状態」タブ（今回追加）が空のまま残り、次に見た人がまた同じ調査をする |

### 案B. `StatusMaster` へ移行する

| | |
|---|---|
| 作業量 | **大きい**。5,329件の `categoryId` → `statusId` 付け替え、上記4箇所のロジック変更、URL・サイドバー・検索フィールド・件数集計の条件変更、シードデータ、E2E |
| 利点 | 名前と中身が一致する。カテゴリを本来の商品分類に使えるようになり、EC出品の説明文生成でも分類を根拠にできる |
| 欠点 | 移行中に「販売中」の判定がずれると、**商品特定・自動返信・画像加工の起動条件**が同時に狂う。影響範囲が業務の中心 |
| 前提 | 上の表の「用途区分」「担当者」「販路」（事務所備品・無償提供・コーディネート用・五十嵐さん・業者間）を状態と分けてどこへ置くかを先に決める必要がある |

### 案C. `StatusMaster` を廃止する（構造ごと畳む）

| | |
|---|---|
| 作業量 | 中。スキーマからの削除、検索フィールド・一覧列・フォーム・CSV入出力からの除去 |
| 利点 | 「空のまま存在する構造」が消え、迷いが無くなる |
| 欠点 | 一覧の「状態」列・絞り込み・フォームの選択肢という**機能を削る**ことになる（前フェーズの禁止事項に触れる） |

## 3. 採用した案とその理由（→ 案A）

**案Aを採用しました。** 案Bは「商品分類が本当に必要になったとき」に、独立した作業として
計画するのが妥当という判断です。

理由:

- いまの運用は回っています。カテゴリを状態として使うのは名前が不正確なだけで、**業務上の実害は出ていません**。
- 一方で案Bの移行は、商品特定・自動返信・画像加工という**顧客対応の中心**に同時に触れます。
  性能改善や整合性強化と違い、「移行して何が良くなるか」が現時点では
  「名前が正確になる」「将来カテゴリが空く」という将来価値にとどまります。
- 今回の指示書の方針（既に十分動いている箇所は変更しない／推測で最適化しない）にも沿います。

案Aを採ると、設定画面に「登録しても使われないマスタの登録画面」が空のまま残ります。
次に見た人がまた同じ調査から始めることになるので、**そのタブはUIから削除しました**
（§0）。削除したのはタブだけで、データモデルと関連コードは残しています。

## 4. 案Bを選ぶ場合の候補一覧

移行するなら、実データから起こした候補はこうなります。
「用途区分」「担当者」「販路」は状態と分けるべきなので、別項目の候補として併記します。

### 4-1. 状態（StatusMaster の候補）

| 状態名 | 用途 | どのタイミングで付くか | 手動/自動 | EC出品可否 | 一覧表示 |
|---|---|---|---|---|---|
| 補修待ち | 修理・清掃が必要 | 入庫時の検品で | 手動 | 出品しない | 作業待ちとして見たい |
| 撮影待ち | 写真がまだ無い | 補修完了後 | 手動 | 出品しない | 作業待ちとして見たい |
| 出品待ち | 写真あり・未出品 | 撮影完了後 | 手動（画像加工の起動条件になっている） | 出品準備の対象 | 作業待ちとして見たい |
| 販売中 | EC/店頭に出ている | 出品完了時 | 手動（将来は出品APIから自動化しうる） | **出品中** | 既定の作業対象 |
| 売り切れ | 売れたが未発送 | 受注時 | 手動 | 出品終了 | 出荷作業の対象 |
| 入金待ち | 入金確認前 | 受注後 | 手動 | 出品終了 | 経理の対象 |
| 出荷指示済 | 配送手配済み | 入金確認後 | 手動 | 出品終了 | 出荷作業の対象 |
| 発送完了 | 完了（終端） | 発送後 | 手動 | 出品終了 | 既定では隠したい（86%がこれ） |
| 破棄 | 廃棄（終端） | 廃棄判断時 | 手動 | 出品しない | 既定では隠したい |
| 保留 | 判断待ち | いつでも | 手動 | 出品しない | 目に付く場所に置きたい |
| 複数在庫 未出品 | 同一商品の在庫が複数あり、代表以外 | 入庫時 | 手動 | 出品しない | — |
| 大原確認 / 市川確認 | 人の確認待ち | いつでも | 手動 | 出品しない | 目に付く場所に置きたい |

「大原確認」「市川確認」は現在0件ですが、マスタには登録済みです（＝過去に使っていたか、これから使う想定）。

### 4-2. 状態ではないもの（別の置き場所が要る）

| 現在のカテゴリ名 | 件数 | 本来の性質 | 置き場所の候補 |
|---|---|---|---|
| 事務所備品 | 133 | 用途区分（販売対象外） | 状態の1つにするか、専用のフラグ |
| 無償提供 | 31 | 用途区分 | 同上 |
| コーディネート用 | 8 | 用途区分 | 同上 |
| 業者間 | 4 | 販路 | 販路の項目 |
| 五十嵐さん | 8 | 担当者または預け先 | 保管場所マスタ（既に「柳沢さん」「竹西さん」がある） |
| 川越移動予定 | 0 | 移動予定 | 状態と別軸。`出品待ち,川越移動予定` という連結値が、1項目に2つ詰めている証拠 |

**`出品待ち,川越移動予定` が3件あること**が、いまの1項目運用の限界を示しています。
移行するなら、この「状態」と「移動予定」を分ける設計を先に決める必要があります。
