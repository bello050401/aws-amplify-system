# 実ブラウザからの性能計測（2026-09-04）

これまでの計測は DynamoDB / AppSync 区間だけでした。利用者が実際に感じるのは
「クリックしてから操作できるまで」で、そこにはネットワーク・SSR・JSの転送・
hydration・React描画が全部乗ります。ここを実ブラウザ（Chromium / Playwright）で測りました。

計測: `npm run measure:browser`（`--cold` でCold条件、`--runs=N` で回数）

---

## 1. 先に、測れなかった範囲

**ログインが要る画面（在庫一覧・検索・商品詳細・メッセージ・EC出品）は測れていません。**

Stagingのログイン情報がこの環境の資格情報マネージャーに登録されておらず
（`Test-BelloStagingCredential.ps1` が `Not stored.`）、保存済みのログイン状態も
ありません。**認証の迂回もゲートの無効化もしていません。**

測るには、次を1回だけ実行してログイン情報を登録してください（対話でメールアドレスと
パスワードを聞かれます。値はWindows資格情報マネージャーに入り、コード・ログ・
スクリーンショットのどこにも出ません）。

```
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\staging-auth\Set-BelloStagingCredential.ps1
```

登録後は同じコマンドで保護された画面まで自動で測ります（ハーネスは対応済みで、
ログイン状態が無ければ公開画面だけに絞る作りにしてあります）。

測れた範囲でも、**全画面に共通して効く問題が1つ見つかり、直しました**（次節）。

---

## 2. 見つけた問題と、直した結果

### 日本語書体の全サブセットを先読みしていた（全画面に影響）

ルートレイアウトの `next/font` は既定で `preload: true` です。日本語書体は
Google Fonts が unicode-range で百数十個に分割しており、それが4ウェイトぶん並びます。
結果、HTMLへ `<link rel="preload" as="font">` が **353本** 書き出されていました。

`preload` は「必ず要る」という指示なので、unicode-range による出し分けが**効きません**。
実際に使う文字は数百字なので、ほぼ全部が無駄でした。しかもルートレイアウトなので
**全画面で毎回**起きていました。

**直し方**: `preload: false` の1行。`@font-face`（unicode-range 付き）だけが出て、
ブラウザは実際に必要なサブセットだけを取りに行きます。`display: "swap"` は既に
指定済みなので、文字はフォールバックで即表示され、読み込み後に差し替わります。
**見た目の最終形は変わりません。**

#### Before / After（Staging・Warm・各3回・中央値）

| 画面 | 項目 | Before | After | 変化 |
|---|---|---:|---:|---|
| ログイン画面 | リクエスト数 | 375本 | **17本** | **−95%** |
| | 転送量 | 4,780KB | **657KB** | **−86%** |
| | TTFB | 478ms | **245ms** | −49% |
| | 初回描画 (FCP) | 536ms | **272ms** | −49% |
| | 操作可能まで | 1,441ms | **1,112ms** | −23% |
| 管理ログイン | リクエスト数 | 374本 | **16本** | **−96%** |
| | 転送量 | 4,125KB | **2KB** | **−99%** |
| | TTFB | 211ms | **198ms** | −6% |
| | 初回描画 (FCP) | 296ms | **224ms** | −24% |
| | 操作可能まで | 1,132ms | **1,057ms** | −7% |

ローカルビルドでの確認: HTML **88KB → 6KB**、font preload **353本 → 0本**、
`@font-face` は485件（unicode-range 484件）そのまま＝書体は今までどおり効きます。

## 3. 残っている遅さと、その責任区間

### ログイン画面が「操作可能」になるまで約1.1秒

初回描画（272ms）から操作可能（1,112ms）まで約800msの開きがあります。分解すると:

| 区間 | 実測 | 責任区間 |
|---|---|---|
| TTFB（Warm） | 221〜245ms | Network（日本→us-west-2）＋ SSR |
| 初回描画（Warm） | 252〜272ms | Browser |
| **Cognitoへの往復 ×2** | **1,858ms / 2,235ms（Cold時）** | **外部API（Cognito）** |
| パスワード入力欄がDOMに出る | 2,686ms（Cold時） | React rendering（Cognito応答待ち） |

パスワード入力欄は**サーバー描画されたHTMLに含まれていません**。ログイン画面は
クライアントコンポーネントで、まず Cognito に「既にログイン済みか」を問い合わせ、
その応答が返ってから初めてフォームを描画します。

**直していません。** ログイン画面は1セッションに1回しか通らず、直すには
「既にログイン済みなら別画面へ飛ばす」という現在の挙動そのものを組み替える必要が
あるためです。実害に対して変更のリスクが見合いません。

### 日本→us-west-2 の往復（約160ms／1往復）

TTFBの下限を決めています。縮めるにはリージョン移行（DynamoDB・Cognito・S3の移設）が
必要で、今回の範囲外です。

## 4. Cold / Warm — 実ブラウザで測ると、影響は以前の見立てより大きい

11分アイドル後に、キャッシュも接続も無い新しいブラウザで測りました。

| 画面 | 条件 | TTFB | 初回描画 | 操作可能 | 転送 |
|---|---|---:|---:|---:|---:|
| ログイン画面 | **Cold** | **3,989ms** | 4,052ms | **5,425ms** | 657KB |
| ログイン画面 | Warm | 221ms | 252ms | 1,084ms | 657KB |
| 管理ログイン | Cold | 238ms | 324ms | 2,208ms | 2KB |
| 管理ログイン | Warm | 179ms | 220ms | 1,056ms | 2KB |

### 責任区間の切り分け

**管理ログインのCold行が、切り分けの鍵**です。この計測も新しいブラウザ（TLS・DNS・
接続すべて新規）ですが、TTFBは238msしかありません。直前のログイン画面のアクセスで
**SSRが既に温まっていた**ためです。

つまり:

| 区間 | 実測 | 内訳 |
|---|---:|---|
| TLS・DNS・接続確立（ブラウザCold） | 約 240ms | 管理ログインのCold TTFB |
| **SSRのコールドスタート** | **約 3,750ms** | 3,989 − 238 |
| 操作可能までの追加分 | 約 1,370ms | Cognitoへの往復（§3） |

以前 `fetch` で測った **+1,982ms** は `/inventory` のリダイレクト（307）を測ったもので、
**画面を実際に描画する経路はもっと重い**ことがわかりました。ページによって
約2秒（リダイレクトのみ）〜約3.8秒（フル描画）の幅があります。

### 利用者から見ると

**その日の最初のアクセスは、操作できるまで約5.4秒。** 温まったあとは約1.1秒です。
差は約4.3秒で、「重い」と感じる水準です。

### ウォームアップについての結論

**導入していません**（指示どおり）。そのうえで、以前より影響が大きいと分かったので
見解を更新します。

| 案 | 追加SSRリクエスト/月 | 効果 |
|---|---:|---|
| 入れない（現状） | 0 | その日の最初と、10分以上空いたあとに毎回 約5.4秒 |
| 5分間隔・24時間 | 約 8,640回 | ほぼ常にWarm。ただし誰も使わない深夜も回り続ける |
| **5分間隔・営業時間のみ**（平日9〜19時） | **約 2,640回** | 業務中はほぼ常にWarm。朝一の1回だけColdを踏む |

**提案は3案目**です。Coldを踏むのが「朝一の1回」に限定され、追加リクエストは
24時間案の3割で済みます。ただし Amplify Hosting のSSRリクエスト課金は契約内容に
よるため、**実際の増加額はご自身の請求ダッシュボードで確認してから**判断してください。
こちらからは導入していません。

## 5. 計測ハーネスについて

`scripts/measure-browser.ts` は1回の画面表示を次へ分解します。

```
TTFB → HTML取得 → DOM構築 → 初回描画(FCP) → 主要表示 → 操作可能 → 総所要
```

あわせてリクエスト数・API呼び出し数・重複リクエスト・転送量・失敗したリクエストを
記録します。各条件を既定3回測り、**最小・中央値・最大**を出します（平均だけでは
1回の外れ値が隠れるため）。

ログイン状態が保存されていれば保護された画面も測り、無ければ公開画面だけを測って
その旨を明記します。認証を迂回する経路は持っていません。
