## 2. メッセージ機能 — 3つの根本原因

いずれもコードとStagingの実データで確認した。

### ① 「不明な顧客」

`Conversation.externalCustomerId`(LINEのuserId、33文字)は4件すべてに
保存されていたのに、`customerDisplayName` は全件 DynamoDB NULL。
**LINEのプロフィールAPIを呼ぶコードがどこにも存在しなかった。**

対処後の実測(バックフィル実行結果):

| 会話 | 結果 |
|---|---|
| 実際のLINE会話 1件 | **表示名を取得して保存**(12文字) |
| E2Eで作ったテスト用ID 3件 | NOT_FOUND ×2 / UNKNOWN ×1 |

取得できなかった会話には「不明な顧客」という文字列を**保存していない**。
保存すると後で取得できるようになっても「取得済み」に見えて再取得され
なくなるため、`customerNameSource` に理由だけを記録した。

### ② 画像を受信できない

`parseLineWebhookBody` の `normalizeEvent` が `message.type !== "text"`
で null を返し、**画像イベントをパーサ段階で捨てていた**。会話にも履歴
にも何も残らなかった。

対処: 1:1チャットのメッセージは種別を問わず記録する。画像は受信直後に
LINEのコンテンツAPIから実体を取り、BELLO側S3(`messaging/attachments/`)
へ保存する(LINEのURLは期限切れするため)。取得に失敗しても会話は残し、
`attachmentStatus=FAILED` と理由を記録する。

### ③ 未読が消えない

`unreadCount` は `webhookStore.ts` / `service.ts` のすべての箇所で +1
されるだけで、**0へ戻す経路がコード中に1つも存在しなかった**。

対処: `isUnread` を正本にし、`markConversationRead()` だけが false に
する。呼ぶのは「人が画面で会話を開いた」経路のみ —— AI生成・Webhook・
一覧描画からは呼ばない。新着受信時は必ず未読へ戻す。

### 検索(約7.7秒)— 今回は変更していない。理由を明記する

原因は特定できている: `fetchAllInventoryRecords` が
`Inventory.list({filter})` = テーブル全体のフィルタ付きScanを

## 5. ナレッジ文書の編集と履歴

- 画面上で本文を直接編集。保存は「変更内容を確認する」→「この内容で
  保存する」の2段。
- 現在版＋直近2世代を保持。復元も「その版の中身で保存し直す」新しい
  変更として扱うので履歴が枝分かれしない。復元でできた版には
  `changeType=RESTORE` と `restoredFromVersion` を残す。
- 競合検知: 編集開始時の version を保存時に渡し、現在と違えば
  **保存せずに知らせる**(古い画面で他人の変更を消さない)。
- 削除と本文編集をボタンとして分離。
- AIが参照するのは `KnowledgeDocument.searchText` のみで、履歴表は
  一切参照しない(下書きがAIへ使われない、という要件を構造で満たす)。

## 8. 画像加工 — 実測で見つけた2件

### ジョブが10件、5日間ずっと処理されていなかった(修正済み・実機確認済み)

image-processing-worker のログには5分ごとに `0 pending job(s)` が出て
いたのに、ProcessingJob には `status=PENDING` が**10件**あり、最古は
2026-08-31 だった。画像加工を依頼しても永久に処理されない状態。

**原因**: pending取得が1回のScanで `Limit: 20` を付けていた。
DynamoDBの `Limit` は**フィルタ適用前に読む件数**の上限で、「合致した
件数」ではない。完了済みの行が積み上がり、先頭20件がすべてDONEに
なった時点から、PENDINGが何件あっても毎回0件しか返らなくなる。

当時と同じクエリを実データへ投げて再現:

```
returned=0 / scannedCount=20 / hasMore=true    （全49件: DONE 39 / PENDING 10）
```

「0件」はテーブルの状態ではなく、読み方の結果だった。

**修正**: 必要件数が集まるまでページを進める(1ページ200件・最大20ページ)。

**実機確認**:

| 時刻(UTC) | ログ |
|---|---|
| 17:45 | `0 pending job(s)` |
| 17:50 | `0 pending job(s)` |
| **17:55** | **`10 pending job(s)`** ← 修正後の初回実行 |

その後 ProcessingJob は **49件すべて DONE**(PENDING 0)。

### 保持期間の判定が実在しないstatusを見ていた(修正済み)

`status !== "COMPLETED"` を条件にしていたが、ImageProcessingStatus に
`COMPLETED` は存在しない(UNPROCESSED / QUEUED / PROCESSING / READY /
NEEDS_REVIEW / FAILED / REPROCESSING / SUPERSEDED)。つまり
「動くように見えて何も削除対象にならない」状態だった。自分で書いた
検証が通っていたのは、fixtureにも同じ架空のstatusを書いていたから。

実データを数えて(NEEDS_REVIEW 33 / READY 6)気づき、削除対象を
READY と SUPERSEDED に限定。NEEDS_REVIEW は人がまだ採否を決めていない
状態なので消さない(実データの85%がこれ)。

現時点の判定結果(削除は実行していない): 版39件 / 採用済み6 / 削除対象 **0**。
