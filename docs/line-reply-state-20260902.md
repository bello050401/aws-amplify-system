# LINE公式アプリからの返信と「返信済み判定」

2026-09-02 / 現状の制約整理と、将来の補助方式への備え

**今回ブラウザ自動化は実装していません。** 指示どおり、公開APIで取れない
情報を「取れる」として実装することも避けています。

---

## 1. 現状の制約（コードとLINE仕様の確認結果）

### BELLOが受け取っているもの

`app/api/line/webhook/route.ts` が受けるのは LINE Messaging API の
Webhook イベント。実装を読むと、扱っているのは**顧客からの受信**
（`message` イベント）です。

### 取れないもの

LINE Official Account Manager やLINE公式アプリから**スタッフが手で返信
した**場合、その送信は Messaging API の Webhook には届きません。
Messaging API は「Bot（＝BELLO）が送受信するチャネル」を対象にしており、
管理画面からの手動応答は別経路です。

したがって、

```
顧客がLINEで質問 → BELLOに「未返信」として表示
        ↓
スタッフがLINE公式アプリで返信（BELLOを経由しない）
        ↓
BELLOは何も知らないので「未返信」のまま
```

という取りこぼしが構造的に起こります。

> **未確認:** LINE側に手動応答を通知する仕組み（Webhookイベント種別、
> 管理APIなど）が存在しないことを、公式ドキュメントで網羅的に確認した
> わけではありません。「Messaging API の Webhook では取れない」までが
> 確認できた範囲です。

---

## 2. いまの設計は、既にLINEへ密結合していない

これは調べて分かった良い知らせです。返信済み判定の中核は
`lib/messaging/conversationStatus.ts` の1関数で、

```ts
export function deriveNeedsReply(
  lastIncomingAt: string | null,
  lastOutgoingAt: string | null,
): boolean
```

**受け取るのは時刻2つだけ**です。LINEのAPIにもイベント形式にも依存して
いません。「最後の受信より後に、こちらから送ったか」という事実だけで
判定しています。

つまり将来、補助ワーカーが「この会話に○時○分にスタッフが返信した」と
いう事実さえ供給できれば、**この関数は1行も変えずに正しく動きます**。

必要になるのは「外部で行われた返信を記録する入口」だけで、判定ロジックの
作り直しではありません。

---

## 3. 将来の補助ワーカーに向けて、いま守るべきこと

指示の「過度にLINE APIへ密結合しない」に対して、現状で守れていること／
今後守るべきことを整理します。

| 事項 | 現状 | 備考 |
|---|---|---|
| 返信済み判定がLINE非依存 | **できている** | `deriveNeedsReply` は時刻2つのみ |
| 会話の識別がLINE非依存 | **できている** | `Conversation.channel` + `externalCustomerId` で抽象化 |
| メッセージの向きが抽象化されている | **できている** | `direction: INBOUND / OUTBOUND` |
| 外部で行われた返信を記録する入口 | **無い** | 将来ここだけを足せばよい |
| 状態が単一の軸に潰れていない | **できている** | 返信状態と業務ステータスが別（§5） |

### 足すとしたら1箇所だけ

将来、補助ワーカーが管理画面から返信を検知したとき、必要になるのは

- その会話の `lastOutgoingAt` を更新する
- そのメッセージを `direction: "OUTBOUND"` として記録する（本文が取れれば）
- 出所が BELLO 経由でないことを区別できるようにする

の3点です。3点目は重要で、**BELLOが送った返信と、LINE公式アプリで送られた
返信を区別できないと、送信の失敗調査ができなくなります**。

いまは実装しません。補助ワーカーの検証結果を見てから、実際に取れる情報に
合わせて設計するのが正しい順序です（取れない情報を前提に器だけ作ると、
高い確率で作り直しになります）。

## 4. 状態管理（指示 §5）

指示が挙げた4状態を、既存の設計を壊さずに表現できることを確認しました。

| 指示の状態 | BELLOでの表現 | 追加の有無 |
|---|---|---|
| 未返信 | `needsReply === true`（`status: WAITING_FOR_REPLY`） | 既存 |
| 返信済み | `needsReply === false`（`status: REPLIED`） | 既存 |
| **商品確認待ち** | `workflowStatus: "AWAITING_PRODUCT_URL"` | **今回追加** |
| 対応不要 | `workflowStatus: "COMPLETED"`（「対応済み」） | 既存 |

### なぜ workflowStatus 側へ足したか

BELLOの状態は意図的に**2軸**に分かれています（既存コードのコメントより）。

```
返信状態      … こちらが返したか。送信の事実から導く。人は操作しない
業務ステータス … 誰が確認するか、どの段階か。人が操作する
```

「商品URLを送ってもらう返信をした」状態は、

- 返信状態としては **REPLIED**（こちらは返した）
- 業務としては **まだ本題に入れていない**

なので、業務ステータス側の値として足すのが正しい形です。返信状態の軸へ
混ぜると「返信したのに未返信」という矛盾した表現になります。

この状態が無いと、URL依頼を送った会話が「返信済み」に埋もれ、**お客様から
URLが届いても誰も気づかない**という運用の穴が残ります。

### 既存を壊していないこと

- `ConversationStatus`（OPEN/WAITING_FOR_REPLY/REPLIED/RESOLVED/ARCHIVED）は**変更なし**
- `needsReply` の算出は**変更なし**
- 既存の `workflowStatus` の値は**すべて残っている**
- 一覧タブは既存の並びのまま、業務ステータス群の先頭へ1つ増えた
  （大原確認から右が1つずれるので、並びを固定していたテストも更新済み）

## 5. 今回やっていないこと

- LINE Official Account Manager のブラウザ自動監視（指示どおり見送り）
- 手動返信を検知する入口の実装（取れる情報が確定してから）
- LINE公式アプリからの返信を「返信済み」に反映すること（上記が前提）

現状では、LINE公式アプリから返信した会話は BELLO 上「未返信」のまま
残ります。**この制約は解消していません。** 運用上は、BELLOの返信機能から
送るか、対応済みへ手で移す運用で回避することになります。
