# 会話文脈の引き継ぎと商品情報の補完（2026-09-03 追加指示 §17-§49）

## 直した不具合

実際に起きたやり取り。

```
顧客  https://bellointeri.base.shop/items/156144635
      3万円まで下げられますか？

BELLO お届け先の都道府県を教えていただけますでしょうか

顧客  埼玉です
```

3通目を**独立した新規問い合わせ**として処理していたため、商品・希望価格・
値下げ交渉であることを毎回失い、返信案が「商品URLをお送りください」になっていた。
顧客はすでに送っている。

さらに、この商品は在庫にサイズが入っておらず、送料が計算できないため
「想定送料：不明」のまま通知されていた。BASEの商品ページには寸法が
書かれており、**計算に必要な数字は目の前にあった**。

## なぜ履歴を渡すだけでは足りないのか

パイプラインは以前から直近10件の履歴をAIへ渡していた。それでも失っていたのは、
「どの商品か」「いくらの希望か」を**毎回、文章から読み直していた**から。

読み直しは同じ結果になる保証が無い。「埼玉です」の1通からは商品も金額も
読み取れないので、そのターンで消える。一度確定した事実は文章ではなく
**構造**として持たなければならない。

## 保存する場所

`Conversation` の行そのもの。

| 項目 | 用途 |
|---|---|
| `inquiryContext` | 確定情報のJSON（`lib/inquiry/conversationContext.ts` の `ConversationContext`） |
| `inquiryContextVersion` | 楽観ロック用の版数 |

別モデルにしなかったのは、会話と1対1で、会話が消えれば無意味になるから。
読み書きが2往復に増えると、Webhookの中で同期処理している現構成では
そのまま顧客への返信遅れになる、という実務上の理由もある。

## マージの規則（最重要）

`mergeConversationContext` は **消さない** ことを不変条件にしている。

| 渡した値 | 挙動 |
|---|---|
| `undefined` | 既存の値をそのまま保つ（今回は分からなかった） |
| `null` | 明示的に消す（話題が変わったときだけ使う） |
| 値 | 置き換える |

「埼玉です」の1通で商品が消えるのが直している不具合そのものなので、
ここを緩めると元に戻る。

## 確認待ちと、その回答

「何を尋ねたか」は**返信案の文面から**読み取る（`detectAskedQuestions`）。
別のフラグで持つと文面と食い違い、顧客が読むのは文面のほうなので直しようがない。

回答の解釈は**確認待ちの項目しか読まない**（`resolvePendingAnswers`）。

- 「11日でお願いします」は月が書かれていない。通常の日付抽出が `null` を返すのは
  正しい ——勝手に決めると配送可否の判定が丸ごとずれる。
- ただし「いまお届け日を尋ねていて、その答えとして届いた」と分かっていれば、
  直近の11日と読める。

この非対称性が安全性の根拠になっている。普通の問い合わせ本文から配送希望日を
拾い始める回帰は、構造として起きない。

## 会話をどう繋ぐか（§19）

強い順に見る。

1. チャネル側の会話ID（メルカリShopsの `inquiryId`）
2. チャネル側の顧客ID（LINEの `source.userId`）
3. 表示名 ＋ 文脈（上のどちらも取れない場合だけ）

**名前だけでは結合しない。** 同姓同名の別人の会話へ混ぜると、前の顧客の
商品・価格・住所が新しい顧客への返信に出る。表示名が効くのは、

- こちらが確認質問を出した直後（48時間以内）に同じ名前から回答が届いた
- 同じBASE商品の話が続いている（14日以内）

のいずれかで、かつ**候補が1件に決まる**ときだけ。2件以上あれば新しい会話にする。
誤って混ぜるより、分かれているほうが後から直せる。

なお公式LINEのWebhookは `source.userId` を必ず含む（含まないイベントは
`normalizeEvent` が捨てる）ので、実際には②で決まる。③は顧客IDが取れない
チャネルのための経路として用意してある。

## 同時到着（§25）

同一会話へ短時間に2通届くと、2つの処理が同じ版を読んで別々に書き戻し、
片方の更新が消える（lost update）。

`saveConversationContext` は「読んだ版と一致するときだけ書く」条件付き更新を使い、
外れたら**読み直して同じマージをやり直す**。マージが「既存を消さない」ので、
やり直しても両方の更新が残る。

### SQSを入れる場合

この仕組みは worker が並列でも壊れないが、**順序までは守らない**。
「埼玉です」より先に「できれば今週欲しいです」が処理されると、返信案が参照する
文脈が実際の会話の流れとずれる。

SQS Standard は順序を保証しないので、同一会話を直列化する必要がある。
**`MessageGroupId = conversationId` の FIFO キュー**を使えば、
「会話ごとに直列・会話をまたぐと並列」という必要な性質がそのまま得られる。

## 商品情報の補完（§29-§40）

商品情報を「Inventoryだけ」から取らない。項目ごとに出典を組み合わせる
（`lib/inquiry/productContext.ts`）。

| 項目 | 出典 |
|---|---|
| 商品名 / 仕入価格 / 販売開始日 | Inventory |
| 販売価格 | Inventory、無ければBASEの掲載価格 |
| サイズ | Inventory、無ければBASEの商品説明から抽出 |
| 素材 / カラー / ブランド / 型番 | BASEの商品説明（ラベルが明示されているものだけ） |

どの項目をどこから取ったかは値と一緒に持ち回る（`Sourced<T>`）。
送料が合わなかったときに、どこを直せばよいか分からなくなるため。

BASEへの問い合わせは**寸法が足りないときだけ**行う。足りているのに毎回
問い合わせても返信が遅くなるだけで何も良くならない。

### 寸法の読み取り（§39）

`W/D/H`・`幅/奥行/高さ`・`mm/cm`・全角/半角・`×/x/✕` の揺れを吸収する。
安全側の制約を3つ置いている。

- **3辺そろったときだけ**採用する。1辺だけBASEから足すと、出所の違う数字を
  並べた合計になる。
- ラベルの無い3連（`85×90×72cm`）は使うが信頼度LOWとして必ず【要確認】にする。
- 座面高（SH）・肘高（AH）は全高として読まない。`lib/shipping/rank.ts` が
  同じ理由で除外しているのと揃えてある。

### 実測（Staging、2026-09-03）

```
BASE取り込み済み 267件のうち、商品説明から3辺そろった寸法を読めたのは 207件
そのうち信頼度LOW（ラベル無しのため要確認）は 0件
商品名が完全一致する在庫のうち、在庫に寸法が無くBASEから補えるのは 6件
```

`AWS_PROFILE=Bello npm run verify:inquiry-live-case` で再現できる（読み取り専用）。

## 出品下書きの一本化（§41-§49）

EC出品画面の「BASE商品ページの下書きを作る」を削除し、
「出品下書き（共通項目）→ AIで下書き生成」へ一本化した。

調査の結果、**生成エンジンは2026-09-02の§2で既に共通化されていた**
（どちらも `generateCanonicalProductPage` を呼ぶ）。実際に残っていた差は
2つだけだった。

- 生成履歴（`GeneratedProductPage`）の保存がBASE側にしか無い
  → `lib/ai/productPage/history.ts` へ出して、残る入口から呼ぶ
- どちらもBASEの商品情報を補完に使っていない
  → `lib/ai/productPage/baseLink.ts` で同一商品を特定し、補完する

### 「似ている商品」を補完に使わない

文体の参考（`findSimilarArchivedProducts`）は**似ている商品**を探すもので、
そこに書かれた寸法・素材は別の商品のものである。補完に使えば、他商品の事実を
この商品の説明へ書き込むことになる。

そこで補完に使う結び付けは、同一商品と言い切れる根拠だけに限る。

1. BASEの出品（`ChannelListing`）として登録されている
2. 商品名が正規化後に完全一致し、候補が1件だけ

部分一致・類似は採らない。家具は同シリーズ・色違い・サイズ違いが多く、
そこを緩めた瞬間に別商品の寸法が混ざる。

## 社内LINE通知（§27）

- 1通目に「引き継いだ情報」を出す。「埼玉です」だけを見せられても担当者は
  判断できない。
- 1通目の最後は `【次のメッセージで返信提案します】`。
- 2通目は顧客へ送る本文だけ。`【返信提案】` の見出しは外した ——
  担当者はそのままコピーして送るので、見出しが残ると顧客へ届く。

（`ContextStoreDeps`）。実AWSでは2つの処理を同じ瞬間に走らせられないため、
継ぎ目が無いと実質テスト不能になる。`lib/messaging/webhookStore.ts` と同じ考え方。
