# AI問い合わせ返信・商品自動特定・ナレッジ文書管理（2026-09-01）

仕様書: `BELLO AI問い合わせ返信・商品自動特定・Webリサーチ・ナレッジ文書管理
Claude Code一括自律実装完全仕様書`（2026-09-01）。
ここには**実装した結果と、実測で分かったこと**だけを書く。

## 全体の流れ

```
問い合わせ受信（既存のLINE webhook / TESTチャネル。ここは無変更）
  ↓  ※ここではAIを呼ばない。webhookを遅くしない（§44）
担当者が問い合わせを開き「AI返信案を作成」を押す
  ↓
本文の正規化 → 種別判定 → 商品の手がかり抽出
  ↓
商品の特定（決定的な手がかり優先。無ければ商品名で照合）
  ↓
在庫DB → ナレッジ文書 → 既存の配送料金DB の順に根拠を集める
  ↓
まだ不明な項目だけ外部を参照する
  ↓
プロンプトを組み立て（信頼できる事実 / 外部情報 / 不明点を別ブロックに）
  ↓
生成 → 決定的な検査 → 不合格なら1回だけ作り直す
  ↓
返信案 + 根拠 + 不明点を画面に表示（送信はしない）
```

## 情報源の優先順位（§2）をどう担保したか

| 優先度 | 情報源 | 実装 |
|---|---|---|
| 1 | BELLO在庫DB | `lib/inquiry/pipeline.ts` が `getInventoryDetail` から事実を作り、TRUSTED_FACTSへ入れる |
| 2 | 問い合わせ本文の識別情報 | `lib/inquiry/references.ts` |
| 3 | BASEの商品情報 | `ChannelListing.externalListingId` / `listingUrl` との照合（BASE APIは補助であり正本にしない） |
| 4 | ナレッジ文書 | `lib/knowledge/retrieval.ts`（関連箇所だけ） |
| 5 | 既存の配送DB | `lib/shipping/service.ts` の `lookupShippingRate` をそのまま使う。**新しい送料マスタは作っていない** |
| 6 | 外部Web | `lib/inquiry/research/`（不明な項目だけ。AgentCore Web Search + 本文のURL直接取得） |

システムプロンプトに「UNTRUSTED_EXTERNAL_FACTS が TRUSTED_FACTS と矛盾する
場合は必ず TRUSTED_FACTS を優先する」と明示し、ブロックも分けている。

## 設計上、判断が要った点

### 商品名だけで商品を確定させない

家具は同シリーズ・色違い・サイズ違いが多い。「HAYのソファ」で別の在庫を
確定させると、顧客には全く違う商品の寸法が案内される。画面に
「対象商品（確定）」と出ていれば担当者も疑わない。

そこで一致を2種類に分けた。

- **同一性を保証する一致**（出品URL / BASE商品ID / SKU / 在庫ID / バーコード）
  → 単独で自動確定の水準（0.95以上）
- **保証しない一致**（型番 / ブランド / 商品名の語）
  → 合計しても `WEAK_SIGNAL_SCORE_CAP = 0.92` を超えない

さらに、最上位と2位の差が `AMBIGUITY_MARGIN = 0.05` 未満なら、たとえ
高得点でも確定しない。色違い・サイズ違いはまさにこの形で現れる。

### 商品名の「検:」以降を照合から外す（実測で見つけた問題）

Staging在庫400件を実測したところ、**172件（43%）** の商品名が末尾に
検索用キーワードを持っていた。

```
PIIROINEN A-Frame sofa 2人掛け ソファ … 検:アルフレックス カッシーナ ボーコンセプト
```

ここに並ぶのは**他社ブランド名**なので、そのまま照合すると「カッシーナの
ソファについて」という問い合わせが、カッシーナ製ではないこの商品にヒットする。
`検 / 検索 / 他` + 半角/全角コロン以降を切り落とす。

当初は「他:」だけを見ていた（最初に見たサンプルの読み違い）。実データでの
「他:」は**0件**だった。

### 送料は既存の配送DBだけを見る

新しい送料マスタは作らない（§10 / §54-1）。`lib/shipping/service.ts` の
`lookupShippingRate` と `lib/shipping/rank.ts` の `calculateShippingRankFromDimensions`
（どちらも読み取りのみ）を使う。`calculateShippingEstimate` は使わない ——
あちらは見積り結果を `ChannelListing` へ**保存する**ので、問い合わせを開いた
だけで出品情報が書き換わってしまう。

市区町村が分からない段階では金額を確定として案内しない。生成後の検査で、
配送DBから引いた金額以外が本文に出たら不合格にする。

### 外部ページは信頼できないデータとして扱う（§9.4）

二重にかける。

1. プロンプトの構造で分ける（`UNTRUSTED_EXTERNAL_FACTS` ブロック）
2. 内容から、指示に見える行を落とす（`lib/inquiry/research/sanitize.ts`）

1だけでは足りない。構造で分けても十分に強い命令文はモデルの出力へ影響しうる。
2だけでも足りない。パターンの列挙は必ず漏れる。

加えて、取得したページが「いま調べている型番のもの」だと言える根拠が無ければ、
値が書いてあっても `UNCERTAIN` へ落とす（§38）。同じシリーズ名の別年式を
正解として返すのが、この機能で最も起きやすい誤りだから。

### Web検索は Amazon Bedrock AgentCore Web Search

**新しい契約もAPIキーも増やさない**方式を選んだ。他は使えなかった。

| 方式 | 判定 |
|---|---|
| Google Custom Search JSON API | 新規受付終了（既存顧客も2027-01-01まで） |
| Bing Web Search API | 2025-08-11に廃止済み |
| Brave / Tavily / Exa | 外部のAPIキー取得が必要（Braveはカード登録必須・支出上限なし） |
| Anthropic web_search | Anthropic APIキーが必要。BELLOは未取得（AIはBedrock/Nova） |
| DuckDuckGo Instant Answer API | 実測: 3件のクエリすべてで結果0件。Web検索APIではない |
| SerpApi / Serper 等 | Google結果の転売。規約リスクのため除外 |

AgentCoreは認可がIAM（SigV4）で、検索クエリはAWS内で完結する。東京
リージョン（ap-northeast-1）。$7/1,000クエリ、固定費なし。

**呼ぶまでの条件**: 在庫DB → ナレッジ → 配送DB で答えられるなら呼ばない。
`identifyResearchableFields` が空を返せば外部へ1リクエストも出ない。
何を調べるかは**質問文から決める** —— PRODUCT_SPECに「耐荷重」を固定で
割り当てると、照明の問い合わせで的外れな項目を調べて課金だけが増える。

**検索結果を事実として採用しない**: 検索が返すのは候補URLであって事実では
ない。公式ドメイン限定の1回目 → 足りなければ範囲を広げる、で候補を得た
あと、**ページを実際に取得**し、`sanitizeExternalText` で指示文を落とし、
型番整合を確認し、決定的に抽出する。

**呼び出し回数を計測する**: `ReplyEvidence.webSearchCallCount` と構造化ログの
両方に出し、参照情報パネルにも「Web検索の呼び出し: N回」と表示する。
0回であることを主張ではなく計測で示せる。

### 型番の一致だけを「その商品のページだ」の根拠にする

実測で起きた誤り: DAIKO公式サイトの**別商品**（人感センサー付ダウン
ライト）のページを、ブランド名 daiko が一致しただけで DPN-41362Y のものと
判定し、消費電力7.8WをFOUNDとして採用していた。§38が警告する「同じ
シリーズ名の別年式」より悪い、まったくの別商品だった。

同定に使う手がかりからブランド名を外し、型番だけにした。型番の一致が
無ければUNCERTAINへ落とし、**UNCERTAINな値はAIへ渡さない** ——「確証なし」と
注記して渡しても高い確率で文中に出るし、対象商品と紐づかない仕様は顧客に
とっては単なる誤情報だから。見つけた内容自体は参照情報に残る。

### ナレッジは関連箇所だけをAIへ渡す（§8）

全文書を毎回投げない。ベクトルDBも新設しない（§8が明示的に禁止）。

「お店はどこにありますか？」という問い合わせには「住所」「所在地」という語が
1つも含まれていない一方、文書側の見出しは【所在地】である。語の一致だけでは
永久に結びつかないので、

- 判定済みの**問い合わせ種別**から検索語を補う（STORE_INFO → 住所/所在地/店舗…）
- 漢字の連続は2文字ずつにも分解する（「店舗住所」→「住所」が引ける）

の2つで解いた。形態素解析器は入れていない。

### Markdownのプレビューは HTML を生成しない

`lib/knowledge/markdown.ts` は構造化トークンを返し、
`MarkdownPreview.tsx` がReact要素を組み立てる。`dangerouslySetInnerHTML` を
使う余地がそもそも無いので、「サニタイズ漏れ」という失敗の形が存在しない。
本文中の生のHTMLタグは文字列として表示される。リンクは http/https/mailto のみ。

### 住所は「どこから来たか」で分ける（Staging実測で見つけた問題）

「お店はどこにありますか？」への返信が、既存の `factSafety` の
`PERSONAL_DATA` に引っかかって2回とも不合格になり、生成失敗になっていた。

あちらの判定自体は正しい。出品コピーに住所が出るのは、商品メモに紛れ込んだ
**顧客の住所**が漏れた場合しかない。一方、問い合わせ返信で店舗の所在地を
書かないなら、答えていないのと同じ。

区別すべきなのは「住所かどうか」ではなく「その住所がどこから来たか」。
社内文書に書かれている住所なら出してよく、根拠のどこにも無い住所は従来どおり
弾く。判定は「根拠テキストに個人情報が含まれるか」ではなく
**生成文に実際に書かれた記述そのものが根拠の中にあるか**で行う。

## データモデル（すべて新規。既存モデルは無変更）

| モデル | 用途 |
|---|---|
| `KnowledgeDocument` | 社内文書。原本はS3 `knowledge/`、検索用テキストはDynamoDB |
| `ReplyDraft` | 生成した返信案1件。顧客本文・外部ページ本文・Secretは複製しない |
| `AIReplySettings` | 生成ON / リサーチON / ナレッジON / **自動送信OFF**（1行） |
| `ExternalResearchCache` | 外部調査結果。TTLは項目の種類から決める（価格6時間 / 仕様90日） |

S3は `knowledge/*` を新設し、**ADMIN（と Admins）のみ**に許可した。
`inventory/*` 配下だとEDITORにも書き込み権限が付いてしまうため。

## 自動送信について（§41）

有効化する経路をコードに作っていない。

- `updateAIReplySettings` の引数に `autoSendEnabled` を含めていない（型で塞ぐ）
- `app/actions/inquiryReply.ts` に送信処理が存在しない
- 送信は従来どおり `sendReplyAction`（送信前の確認モーダルを伴う）だけ

### 利用条件

AgentCore Web Search の利用条件は、検索結果を使った出力に**出典とリンクを
保持・表示すること**を求めている。参照情報パネルにタイトルとURLの両方を
文字として出しているのはこのため（バルク抽出・競合インデックス構築は
行わない）。

## AWS側の構成

`scripts/aws-setup/13-create-web-search-gateway.mjs`（冪等・`--destroy` 付き）。

| リソース | 名前 | 費用 |
|---|---|---|
| AgentCore Gateway | `bello-web-search`（ap-northeast-1 / MCP / AWS_IAM） | 呼び出し $0.005/1,000 |
| Gateway Target | `web-search-tool`（connector `web-search` 1.2.0） | ツール索引 $0.02/100ツール/月 |
| IAMロール | `BelloAgentCoreWebSearchGatewayRole` | — |
| Web Search | — | $7/1,000クエリ |

固定費なし。権限は、サービスロールが実Gateway ARNとWeb Searchのサービス
所有ARNのみ、呼び出し側のSSR実行ロール（`BelloAmplifyStagingComputeRole`）も
実Gateway ARNのみに限定。再実行時に一瞬でも権限が広がらないようにしてある。
