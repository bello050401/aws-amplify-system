# BELLO 技術的負債・将来課題（2026-09-04 時点）

今回の健全化で「見つけたが直していない」ものと、その理由です。
**理由の無い整理は行わない**方針なので、直さない判断も残しています。

---

## P2 — 時間が取れたら

### 1. 在庫の同時編集による上書き（lost update）

`updateInventory` は読み取ったバージョンを確認せず全フィールドを書きます。
2人が同じ在庫を同時に編集すると、後から保存したほうが勝ち、先の変更は**黙って消えます**。

直すには「競合したときに画面でどう見せるか」という仕様判断が要ります
（保存を止めて警告するのか、差分を見せるのか、そのまま上書きしてよいのか）。
運用人数が少なければ現状で十分という判断もありえます。**利用者判断待ち**。

### 2. 会話の同時作成

`findConversation` は `(channel, externalCustomerId)` で照合しますが、そのGSIが無いため
Scanベースです。同一顧客から同時に2通届くと、会話が2件できる可能性があります。

メッセージ自体は失われず（それぞれの会話に入る）、表示上の問題にとどまります。
根治するにはGSIの追加＋条件付き作成が必要で、スキーマ変更を伴います。

### 3. `cleanup-mercari-misingested.ts` の1ページ取りこぼし

関連する Message / ReplyDraft / NotificationDelivery を `.list({limit: 900})` の
1ページ分しか拾っていません。実データの「会話へ辿れない通知6件」の原因です。

一度きりの復旧スクリプトで再実行の予定が無いため直していません。
**再実行する場合は先にページング化してください。**

### 4. 在庫削除時に関連レコードを残す

`deleteInventory` は `ListingDraft` / `ChannelListing` / 画像処理系を消しません。
実データでは出品下書き1件が孤児になっています。

「在庫は消したが下書きは残したい」運用もありうるため、消すかどうかは業務判断です。
在庫履歴だけは**意図的に残す**設計（古物台帳）なので、これは対象外です。

### 5. 直結側とAppSync側の振る舞いの差

`lib/amplify/directData.ts` はAppSyncのリゾルバを模したものですが、完全な等価ではありません。
今回 `create` の `attribute_not_exists(id)` が抜けていたのを直しましたが、
他にも差がある可能性があります（条件付き更新、`@auth` の適用、自動フィールドの扱い等）。

**直結の処理を足すときは、AppSync側と同じ意味になっているかを都度確認してください。**
`verify:direct-data` に差を固定するテストを足していくのが望ましい形です。

## P3 — 記録のみ

### 6. Mercari API の暫定値（[UNVERIFIED]）

`lib/listing/mercari/` の以下がSandbox接続を確立できておらず暫定値です。
いずれもコード内に `[UNVERIFIED]` と理由付きで明記されています。

- `adapter.ts` — 配送方法・配送元地域のフォールバック
- `mapper/condition.ts` — 商品状態のenum
- `mapper/shippingDuration.ts` — 発送日数のenum
- `mapper/shippingPayer.ts` — 送料負担のenum
- `types.ts` — 各種上限値

Sandbox接続が取れたら実際の値へ更新してください。

### 7. `ChannelListing` が0件

出品チャネルとの連携レコードが1件もありません。EC出品機能は動きますが、
`ChannelListing` を読む処理（商品特定の補助など）は常に空を返します。
**運用が始まっていないだけ**の可能性が高く、構造としては正しいのでそのままにしています。

### 8. AI費用の単価が暫定値

`lib/ai/gateway/modelRegistry.ts` が公開単価を暫定値として使っています。
AWSの実請求と一致する保証はありません（コード内に明記済み）。

### 9. `Inventory.unit` が自由文字列のまま

`UnitMaster` は「候補として提示する名称の一覧」で、`Inventory.unit` への外部キーでは
ありません。そのため単位のリネームは既存在庫の文字列を書き換えず、
使用件数の判定も表記ゆれを吸収しません。

本当の外部キーへ移行する場合は、既存レコードの移行方針を別途決める必要があります。

### 10. `StatusMaster` の `code` を利用者に見せていない

`code` はschema上必須ですが、現時点で読む側がどこにもありません
（ZAICOの `state` は実データが空で写像を見送ったまま）。
表示名から機械的に生成し、名称変更では変えない扱いにしています。
外部連携で `code` を使う必要が出たら、入力欄を設ける判断が要ります。

### 11. Amplify 由来の TODO

`amplify/data/resource.ts` と `lib/inventory/zaicoSyncPorts.ts` にある
`"TODO: delete when we make resource auth ..."` は**上流（Amplify）のコード側のTODO**で、
こちらで消せるものではありません。上流が対応したら見直す、という位置づけです。

## 今回「直さない」と判断したもの（理由付き）

| 項目 | 理由 |
|---|---|
| 空テーブル（`StatusMaster` / `ChannelListing` / `PricingRule`）への問い合わせを省く | 「空だから読まない」特別扱いは、登録された瞬間に出なくなる不具合を作り込む。60秒キャッシュ済みで1分に1回に収まる |
| 独自のエラー階層を大規模に作る | それ自体が目的化する。今回は「失敗を0件へ丸めない」ことだけに絞った |
| 外部呼び出しへの共通リトライ | 何を再試行してよいかは冪等かどうかで決まる。共通化すると危ない方向へ倒れる。タイムアウトだけを共通化した |
| 大規模な依存関係アップグレード | 明確なセキュリティ問題が見つからなかった。メジャーアップグレードは影響範囲が広く、別途評価すべき |
| リージョンの東京移行 | DynamoDB・Cognito・S3の移設を伴う。往復160msの改善効果はあるが、今回の範囲を大きく超える |
