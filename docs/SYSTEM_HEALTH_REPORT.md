### もっとも危険だった問題

**ZAICO重複統合が、参照の付け替えに失敗しても気づかずに在庫を物理削除しうる構造だった。**

統合は「関連6モデル（在庫履歴・出品下書き・チャネル出品・画像処理ジョブ・画像処理履歴・会話）の
参照をcanonicalへ付け替える → 重複した在庫を削除する」順に進みます。その付け替え6関数が、
いずれも取得・更新のエラーを見ていませんでした。Amplify の `.list()` は
GraphQLエラーのとき**throwせず空配列を返す**ため、

```
listが失敗 → data=[] → 「付け替える行は無い」と判断 → 直後に在庫を物理削除
```

となり、在庫履歴も会話の商品リンクも**復旧不能な孤児**になります。
実データを調べたところ、幸い**この事故はまだ起きていません**でした。

## 3. 修正した問題

### P1-1. 取得エラーを0件と取り違えて破壊的操作へ進む

| | |
|---|---|
| 深刻度 | P1（復旧不能なデータ損失。ただし発生には同時の一時障害が必要） |
| 根拠 | `lib/amplify/listAll.ts` 自身が「重複を防ぐ判定」「削除の可否判定」で危険と明記。その2種類のうち後者を、6箇所で守っていなかった |
| 再現条件 | 統合の実行中にAppSyncが一時エラー（スロットリング等）を返すこと |
| 実データ確認 | **まだ起きていない**（孤児の内訳を追跡した結果、既存の孤児は2026-08-30のZAICO重複作成事故の残骸と判明） |
| 修正 | `zaicoDuplicateAudit.ts` の付け替え6関数＋監査スキャン、`listingPartitionBackfill.ts`、`thumbnailBackfill.ts`、`zaicoBackgroundSync.ts` を `unwrapList` / `unwrapWrite` で必ず投げる形に |
| 残るリスク | 統合の途中で投げると、一部だけ付け替わった状態で止まる。付け替えは冪等なので再実行で回復する |

バックフィル系は別の壊れ方をします。listが失敗すると `nextToken` も消えるため、
**「完了」と表示されたまま未処理の行が残る**。`listingPartition` が無い在庫はGSIに載らず、
一覧に出てこないので、これは「在庫が消えたように見える」形で表面化します。

### P1-2. LINE通知の重複防止が同時実行では効かない

| | |
|---|---|
| 深刻度 | P1（顧客対応の二重通知） |
| 根拠 | 「dedupeKeyで既存を探す → 無ければ作る」の check-then-act。`deliveryStore.ts` に「同じキーで2件できてしまった場合でも古いほうを正とする」という読み側の緩和策が既にあり、重複が起こりうると認識されていた |
| 再現条件 | LINEのWebhook再送と初回処理の重なり。この経路はAI生成を挟んで数秒かかるため十分に起こりうる |
| 実データ確認 | **まだ起きていない**（dedupeKeyの重複0件） |
| 修正 | `id` を dedupeKey にして条件付き作成。負けた側は送らない |

**途中で見つかった、より根の深い問題**: その条件付き書き込みは**この経路では効いていませんでした**。
LINE Webhook / メール取込は `runWithDirectData()` でAppSyncを迂回しますが、
直結側の create が**無条件のPut**だったため、
(1) 明示idのcreateが常に成功して重複防止が機能しない、
(2) 同じidで作り直すと**送信済みの通知がPENDINGへ巻き戻り再送される**、
という状態でした。AppSyncのcreateは `attribute_not_exists(id)` 付きなので、直結側だけが仕様から外れていました。

これは実DynamoDBに対する検証（`verify:notification-claim-live`）で7項目確認し、
条件を外すと4項目が落ちることも確かめています。

### P1-3. 受信メッセージの二重登録

P1-2と同じ構造がメッセージ取り込みにもありました。`externalMessageId` から決まるidにして
条件付き書き込みへ。負けた側は例外にせず「重複」として扱うので、既存の
「再送を解析・通知のやり直しの機会として使う」性質も保たれます。
実データ確認では **externalMessageId の重複0件**（まだ起きていない）。

### P1-4. 外部呼び出しに待ち時間の上限が無い

Node の `fetch` に既定のタイムアウトはありません。外部へ fetch している17ファイルのうち、
上限を持っていたのは3つだけでした。SSRで応答が返らない相手に当たると1リクエストが
実行上限まで居座り、LINEの再送と重なって積み上がります。

共通の `lib/http/fetchWithTimeout.ts`（既定15秒）を13ファイル16箇所へ適用。
**再試行はしていません** —— 何を再試行してよいかは冪等かどうかで決まるもので、
共通化すると危ない方向へ倒れるためです。

### P2-1. 件数キャッシュの無効化が抜けていた書き込み経路

CSV取込・ZAICO同期の新規作成、重複統合の削除が、総件数キャッシュ（60秒）を捨てていませんでした。
原因は置き場所で、キャッシュが重いモジュールの中にあり「捨てるためだけにimport」しづらかったこと。
依存の無いファイルへ切り出し、書き込みのすぐ隣で呼ぶ形にしました。

### P2-2. 認可の確認が下位レイヤ頼みだったServer Action

30ファイル中2ファイル（`base.ts` 3件 / `features.ts` 8件）が入口で権限を確かめていませんでした。
追跡した結果、**現時点では突破できません**（どちらもBASEトークン／Feature本体を
`adminAuthMode` で読み書きするためAppSyncが弾く。Bedrock呼び出しより前にトークン読み取りが
入るので、AI費用を未認証で消費させることもできない）。
ただし守りが下位レイヤ1本にぶら下がっているため、他の28ファイルと同じ形へ揃えました。

### P2-3. 1ページ分で静かに切り捨てられる取得

マスタ一覧（Category/Location/Unit/Status）、特集一覧、特集の掲載商品。
とくに掲載商品は、編集画面に出なかったぶんが**保存時に本当に消える**形でした。
いずれも `listAllPages`（最後まで辿り、上限に達したら例外）へ。

## 6. 利用者の判断が必要な項目

1. **在庫の同時編集をどう扱うか**
   いまは後から保存したほうが勝ち（先の変更は黙って消える）。
   「保存時に他の人が編集していたら警告して止める」形にするか、現状のままでよいか。
   運用人数が少なければ現状で十分という判断もありえます。

2. **コールドスタートのウォームアップを入れるか**
   **実ブラウザで測り直したところ、影響は以前の見立てより大きいことが分かりました。**
   その日の最初のアクセスは操作できるまで **約5.4秒**（Warm は約1.1秒）。
   SSRのコールドスタートぶんは約3,750msです（以前の +1,982ms はリダイレクトのみの
   経路を測ったものでした）。
   提案は「5分間隔・営業時間のみ（平日9〜19時、月約2,640回）」で、Coldを踏むのが
   朝一の1回に限定されます。**導入はしていません** —— Amplify Hosting のSSRリクエスト
   課金は契約内容によるため、請求ダッシュボードで確認してから判断してください。
   詳細は `BROWSER_PERFORMANCE.md` §4。

3. ~~**状態マスタをどうするか（現状維持 / 移行 / 廃止）**~~ → **2026-09-04 に「現状維持」で確定しました。**
   `Category` を正式な現行の状態管理として維持し、`StatusMaster` へは移行しません。
   空の「状態」タブはUIから削除済み。詳細は `STATUS_MASTER_CANDIDATES.md` §0。
   以下は判断に至った経緯として残します。
   調査の結果、**「状態」はすでに `Category`（カテゴリ）で運用されていました**。
   カテゴリ20件の中身は商品分類ではなく「発送完了4,576 / 販売中271 / 破棄179 /
   補修待ち48 …」というライフサイクル状態で、`masterSeed.ts` の並びも業務フロー
   そのものです。`StatusMaster` は同じ概念のために作られて一度も使われなかった側でした。
   現状維持／移行／廃止の3択と、それぞれの作業量・利点・欠点、移行する場合の候補一覧は
   `STATUS_MASTER_CANDIDATES.md` にまとめました。**本番マスタへの登録はしていません。**

4. **Next.js のメジャーアップグレードを行うか**
   `npm audit` で4件（high 2 / moderate 2）。`next` はすでに14系の最新（14.2.35）で、
   残る指摘を消すには **Next 16 への移行（破壊的変更）** が必要です。
   この構成で成立しない指摘（middleware / i18n / カスタムサーバー / edge runtime）を
   除いた実際の露出と、移行の影響範囲は `TECH_DEBT.md` にまとめました。
   今回の範囲（既存を壊さない）を超えるため**実施していません**。
