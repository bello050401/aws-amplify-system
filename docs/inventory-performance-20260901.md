# 管理画面の高速化（2026-09-01）

指示書: `BELLO 在庫管理システム 管理画面・画面遷移・データ取得 高速化`（2026-09-01）。
ここには**実測した数値と、そこから分かったこと**だけを書く。

## 結論

在庫一覧のサーバー処理が **約8秒 → 約0.6秒**（TTFB中央値）。
主要遷移はすべて 0.7〜1.4秒に収まった。

## 何が遅かったか（実測による分解）

修正前（Staging実機・3回の中央値）:

| 遷移 | 合計 | TTFB |
|---|---:|---:|
| 設定→在庫一覧 | 8,242ms | 8,135ms |
| メッセージ→一覧 | 14,888ms | 7,308ms |
| 直接: 在庫一覧 | 7,976ms | 7,790ms |
| 直接: 設定 | 1,387ms | 150ms |
| 直接: メッセージ | 629ms | 455ms |

**合計時間のほぼ全部がTTFB＝サーバー側**だった。画像でもReactでも
ルーティングでもない。

内訳の切り分けは、同じ4マスタ（カテゴリ/保管場所/状態/追加項目）を
取っている**設定画面のTTFBが150ms**だったことから逆算できる。
一覧はその4マスタ＋在庫取得なので、

- 認証 + 4マスタ + 描画: 約150ms（約2%）
- **在庫の全件取得: 約7.6〜8.0秒（約98%）**

原因は `lib/inventory/queries.ts` の `fetchAllInventoryRecords`。
1ページ200件のlistをnextTokenが尽きるまで回して**5,313件すべて**を読み、
そこから50件をsliceしていた。27往復ぶんの待ち時間を、50件表示するために
毎回払っていた。

`loading.tsx` がこのルートグループに1つも無かったため、その8秒間ずっと
前の画面が表示されたまま＝「押したのに何も起きない」状態だった。

## 修正内容

| 対象 | 変更 |
|---|---|
| `lib/inventory/inventoryPage.ts`（新規） | `listingPartition` 固定パーティションのGSIへの本物のQueryで、**表示するページに到達するまでだけ**進める。1ページ目なら1往復 |
| `app/actions/inventoryCount.ts`（新規） | 総件数は描画から切り離し、画面表示後にクライアントから取得 |
| `app/inventory/(protected)/InventoryTotalCount.tsx`（新規） | 集計中は「集計中…」、失敗時は「—」。件数の失敗で一覧が消えない |
| `loading.tsx` × 4（新規） | 一覧・設定・詳細・メッセージ。遷移が始まったことが即座に分かる |
| `InventoryNavRail.tsx` | 主要5ルートをhover/focusで先読み。railは未保存変更ガードのためLinkではなくbuttonで、自動prefetchが効いていなかった |
| `InventoryPagination.tsx` | 「次へ」の可否をnextTokenの有無で判断。総件数を待たない |
| `app/actions/inventory.ts` | 追加・削除時に件数キャッシュを捨てる |

検索（クイック検索・詳細検索）は**従来経路のまま**。部分一致とAND/OR混在は
DynamoDBのKeyCondition/FilterExpressionだけでは表現できない。検索は利用者が
明示的に行う操作で、一覧を開くたびに走るものではない。

### 改善がAWS側の気まぐれでないことの確認

同じデプロイ・同じ日・同じ計測で、**旧方式のコード経路を通る画面**
（クイック検索は今も全件走査を使う）を対照として測った:

| | TTFB |
|---|---:|
| 新方式（`/inventory`） | **734ms** |
| 旧方式（`/inventory?q=a`） | **7,265ms** |

修正前のベースライン（7,790ms）とほぼ一致する。改善は実装によるもの。

## API呼び出しと取得件数

| | Before | After |
|---|---:|---:|
| 一覧1回あたりのAppSync往復（行の取得） | 27回（全5,313件） | **1回（50件）** |
| 一覧の初期表示で読む在庫 | 5,313件 | **50件** |
| 総件数の集計 | 描画に含む（同上の27往復） | 描画の外。表示後に1回、60秒キャッシュ |

将来1,000〜1,500件になっても、行の取得は1ページぶんのまま変わらない。

## キャッシュ

入れたのは**総件数だけ**。

- TTL 60秒、プロセス内、条件（カテゴリ/保管場所/状態）ごと
- 追加・削除の書き込み経路で明示的に破棄
- 取得に失敗したら 0 や推測値ではなく「—」を出す（§13.2）

**行データはキャッシュしていない。** 在庫の現在値・販売状態が古いまま
表示される経路を作らないため（§12.2）。

## 途中で作り込んで、実測で撤回した設計

総件数を最初は Server Component + Suspense でストリームする形にした。
Staging実機で**6回に1回、一覧画面が丸ごとエラーになった**
（`/inventory/error.tsx` が発火）。全件走査がサーバー描画の一部である
限り、そこで起きた失敗は画面ごと巻き込む。

件数は「あると便利な表示」であって、一覧が使えるかどうかとは関係がない。
描画後にクライアントから取りに行く形へ変えたところ、8回連続で成功・
全て高速経路・約1秒になった。

あわせて、GSI経路が失敗したら従来経路へ退避するようにした。遅くはなるが
一覧は出る。どちらの経路を通ったかは、画面に出さずDOMの
`data-inventory-source` にだけ残してある（実機で確認するため。秘密値は含まない）。

## 回帰

- offline全18 suite green（1,390件）
- typecheck / lint / build green
- E2E-PERF-01〜10: **20 passed / 0 failed**、console error 0

E2Eで確認したこと: 主要5遷移が動く／初期表示が50行／高速経路を通っている／
戻ってもoffsetと先頭行が保持される／検索の精度が変わっていない（商品名・
在庫IDとも）／一覧を開き直すとサーバーから取り直す／設定の主要タブが動く／
ADMIN限定タブが出る。

## 残課題

- **検索は今も約7.7秒**（全件走査）。部分一致のため構造的に全件が要る。
  必要な項目だけを取得する2段構え（id+名前で絞り込み → 該当分だけ本体取得）で
  短縮できる見込みだが、今回は手を付けていない
- **一覧の画像が約6MB**。TTFBが支配的だった間は問題として見えていなかったが、
  サーバーが速くなったぶん相対的に大きい。サムネイルの有無・遅延読み込みの
  実測は未実施
- `/inventory/listings`（EC出品一覧）と `/inventory/sales` は今も全件取得。
  前者は同じ手法が使える。後者は集計のため全件が要る
- 詳細画面のサーバー処理は未着手（現状で約1秒）
