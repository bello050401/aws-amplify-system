# 在庫金額の集計と月末記録

PCの売上画面とスタッフアプリに「売上／在庫金額」を追加。購入単価×数量を円単位で合算し、工程カテゴリは一商品一回だけ計上する。未入力単価は0円確定とせず、数量と不備を分ける。配送費は仕入時に単価へ含めたものを二重加算しない。

## 集計対象

- 補修待ち、撮影待ち、出品待ち、販売中の4工程と、その他の在庫。
- 移動予定等の補助カテゴリは重複計上しない。複数工程の併存はその他に一回計上し確認対象にする。
- 入金待ちは保有在庫に含める。販売終了日あり・売り切れ・発送完了・出荷指示済・事務所備品・破棄・無償提供は除外する。
- 現行の在庫分け後の数量を使う。分割前のロット仕入数量を各商品へ掛け直さない。

## 保存と負荷

SalesAggregateSnapshotの任意項目inventoryValueJsonに集計結果を保持する。currentは既存の12時間ごとの売上集計と同じInventory走査を再利用する。Categoryをまとめて一回取得し、全件走査を画面表示時に追加しない。

月末はinventory:YYYY-MMへ一回だけ保存する。JSTの翌月1日00:00を境界に、ZAICO同期で既存保存されたremote-windowの全件記録と差分を適用する。日付・数量の現在値から過去の残数を推定しない。境界を含む記録の連続性を検査し、欠落・月末をまたぐ変更で旧値不明なら書き込まない。同一月への再実行は条件付き作成で上書きを防ぐ。

定期処理は直前の締め月の記録を確認し、存在すればS3を読み直さない。過去月は経過日数で削除しない。元の同期アーカイブは既存の90日保持のままであり、アーカイブ欠落や停止後90日経過の月は復元不能となり得る。閉月の作成失敗は[inventory-month]ログに理由を残し、次の定期実行で再試行する。画面で未集計と0円を区別する。

APIは既存の認証・sales機能権限と所有者照合を維持。1表示は集計レコード1件の取得だけで、private/no-store。元の商品は更新しない。旧売上画面への切戻しでも集計レコードは保持でき、商品データの移行・復元は不要。

## 売上表との照合

提供された試算表の各月M22を比較資料とする。空欄のキャッシュ値0は残高0円とは解釈しない。同じ年月の比較額がある場合だけ差額を表示し、現在在庫と過去月末を比較しない。2026年10月は当時の在庫から算出する。9月以前の在庫アーカイブがないため、その月との一致を断定しない。未入力価格は画面の集計内容から対象商品を確認できる。

## 検証

- scripts/verify-inventory-value.ts: 14項目。単価・数量、カテゴリ重複、除外、入金待ち、分割、欠損と0円、オーバーフロー、容量上限。5,700件×1,000回の純粋計算も測定する（画面/APIの実測とは別）。
- scripts/verify-inventory-value-history.ts: 11項目。JST境界、時系列差分、重複、分割、削除、記録欠落、不明な月末更新、再実行、将来更新の混入防止。
- scripts/verify-inventory-value-boundary.cjs: 認証拒否、取得エラー、共有走査、集計の原子的公開、カテゴリ取得失敗時保持、月末の一回保存・再実行・失敗時無更新。
- 既存売上集計と予測計算の回帰検証、PC/スタッフアプリの型検査・配布ビルド、390px表示とPCでのタブ・月切替を確認。

## 運用確認

本番反映後に定期集計Lambdaを一回実行し、currentと直前月のレコード、元の売上集計、画面表示を確認する。失敗した月を現在値や0円で埋めない。修正が必要な月末記録は元資料と差分を確認したうえで明示的な訂正として扱い、通常の再集計で既存締め月を変更しない。
