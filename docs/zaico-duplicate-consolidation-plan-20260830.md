## 2. 重複が発生していた根本原因(修正済み・再発防止確認済み)

旧 `findExistingBySourceId` は `Inventory.list({filter})` を
**nextToken ループなしの単発呼び出し**で行っていた。
`sourceSystem` / `sourceInventoryId` はInventoryのGSIに含まれないため
この呼び出しは実質 Scan + FilterExpression であり、単発では1ページ分
しか走査しない。**テーブルが育つほど目的の行がページ外へ落ち、「既存
なし」と誤判定して新規作成する**——重複作成が 39件 → 109件 → … と
加速していた実測パターンと一致する。

修正後(deploy済み)は二重防御:

1. `ZaicoSourceLink` の主キー直接get(O(1)、スキャン不要)。
2. リンクが無い場合は **nextToken を必ずループする完全スキャン**。
3. 新規作成と判定した場合のみ、`ZaicoSourceLink` の決定的idに対する
   **原子的claim**(条件付きcreate)を挟む。claimに失敗した側はcreateを
   やめてupdate経路へ退避するため、createは決して二重実行されない。

### 実環境での再発防止確認(2026-08-30 21:45〜21:49 JST)

修正後のコードで、ZAICO全件同期が1件実走した(`zaico-sync-worker`
Lambdaが実行、`totalProcessed: 1000` / `created: 837` /
`unchanged: 162` / `updated: 0`)。その前後で:

| 指標 | 同期前 | 同期後 |
|---|---|---|
| Inventory 総数 | 456 | 1,317 |
| distinct ZAICO ID | 139 | 1,000 |
| 重複グループ数 | 97 | **97(変化なし)** |
| 超過レコード数 | 317 | **317(変化なし)** |

新規作成された861件は**すべて未同期だったZAICO IDに対応する正当な
新規登録**であり、そのうち既存と重複したものは **0件**。旧コードで
あれば既存139件も再作成していたはずの経路を通っても、新規重複は
発生しなかった。

## 5. 正本(canonical)の選定基準

**`createdAt` が最も古いレコードを正本とする**(同点はidで安定ソート)。

理由:

- 最古のレコードは旧SKU連番の若い番号(`B000001`〜`B000158`)を持って
  おり、これがUI上の「在庫ID」としてユーザーに見えている値である。
  新しい重複側(`B000300`番台以降)を残すと、ユーザーから見て在庫IDが
  理由なく変わったように見える。
- ZAICO側の同一商品に対して最初に発行されたSKUを維持することは、
  「一度発行したSKUは原則再利用しない」という既存方針とも整合する。

### この基準の既知の限界(要判断)

97グループ中 **89グループ**で、正本候補より `updatedAt` が新しい重複
レコードが存在する。ただし §3 で確認したとおり、それらの更新のほぼ
全ては**同期処理自身による書き込み**であり、人手による編集ではない
(人手由来の内容を持つのは §4 の11件のみ)。

したがって `updatedAt` の新しさは正本選定の基準として採用しない。
**§4 の11件についてのみ、内容を正本へマージしてから超過側を処理する。**

## 6. 実行手順(承認後・未実行)

> 以下はいずれも**まだ実行していない**。ステップ2以降は不可逆な操作を
> 含むため、実行前に個別の承認を求める。

1. **バックアップ**(不可逆操作の前に必須)
   DynamoDBのPITR有効化状況を確認し、`Inventory` /
   `InventoryHistory` / `ListingDraft` / `ZaicoSourceLink` の
   on-demandバックアップを取得する。統合はこのバックアップが取れて
   から開始する。

2. **§4 の11件の内容を正本へマージ**
   画像・カテゴリ・EC出品下書きを正本レコードへ移す。EC出品下書き
   2件は `ListingDraft.inventoryId` を正本のidへ付け替える。
   この11件は件数が少ないため、機械処理ではなく1件ずつ確認して行う。

3. **`ZaicoSourceLink` のバックフィル**
   現在、1,000件のZAICO IDのうち **139件にリンクが存在しない**
   (旧コード時代に同期された分——重複97グループはすべてこの139件の
   中にある)。各グループの正本idを指すリンクを作成する。
   これを行わないと、以後の同期はこの139件について毎回フォール
   バックの全件スキャンを走らせ続け、原子的claimの保護も掛からない。

4. **超過317件の処理**
   `deletedAt` を設定する論理削除を第一候補とする(物理削除ではなく)。
   理由: 一覧・検索は既に `deletedAt` で除外しており、論理削除だけで
   ユーザーから見える重複は解消する。万一の誤判定時に復旧できる。
   物理削除するかどうかは、論理削除後に一定期間運用してから別途判断
   する。

5. **`InventoryHistory` の扱い**
   超過側を指す314件は、いずれも「その重複が作られた」記録である。
   正本へ付け替えると正本の履歴が重複作成の記録で汚れるため、
   **付け替えず、超過レコードと共に残す**ことを推奨する(論理削除
   なら参照は壊れない)。

6. **統合後の検証**
   重複グループ数が 0 になること、distinct ZAICO ID が 1,000 のまま
   であること、`ListingDraft` 2件が正本を指していること、
   `ZaicoSourceLink` が1,000件になることを実測で確認する。
   その後もう一度ZAICO同期を実走させ、件数が増えないことを確認する。
