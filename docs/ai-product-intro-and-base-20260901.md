夜間統合指示書(2026-09-01) §4・§5・§6 の対応記録。
**推測と実測を分けて書く。** 数値はすべてこの日に実際に測ったもの。

## 1. 結論(先に)

報告されていた「AIが変な商品説明を書く」問題は、**モデルの捏造ではなく、
渡してはいけない社内データを顧客向けプロンプトへ渡していたこと** が
主因だった。本番Inventory 5,313件を実測して特定した。

実際のNovaモデルで実在商品20件を生成して比較した結果:

| | 違反なし(合格) | 社内スコア露出 | 未裏付けの金額 |
| --- | --- | --- | --- |
| **BEFORE**(従来の渡し方) | **7/20 (35%)** | 12件 | 2件 |
| **AFTER**(今回の修正後) | **20/20 (100%)** | 0件 | 0件 |

加えて、**顧客の氏名・住所が公開商品説明へ流れ得る経路**を2つ塞いだ(§3)。

## 2. 根本原因 —— 実測で特定したこと

### 2.1 `conditionRating` は顧客向けの文章ではなく社内の5段階スコア

本番Inventory 300件を抽出して値の分布を数えた:

```
conditionRating: 設定済み 118/300、平均2文字
  "3.5" × 59   "4" × 38   "3" × 10   "5" × 8
  "2.5" × 1    "4.5" × 1  "4.0" × 1
```

`app/actions/ai.ts` はこれを `conditionNote` としてそのまま渡し、
`buildListingUserPrompt` が **「コンディション: 4」** と描画していた。
モデルはその事実に忠実に **「コンディションは4です」** と書いていた ——
報告されていた不具合そのもの。**モデルは正しく振る舞っており、
入力が間違っていた。**

一方、顧客に本当に伝えるべき状態説明は `damageNotes` にあった:

```
damageNotes: 設定済み 137/300、平均14文字
  例: 「ウレタンヘタりあり。2脚中1脚は背もたれ上部と背面に若干の布破れがあり」
      「細かい傷有り」「若干シェードに傷あり」
```

**この `damageNotes` はAIへ一切渡されていなかった。**
渡すものと渡さないものが逆になっていた。

### 2.2 `note` に顧客の配送先住所が入っている

同じ300件で、`note` に郵便番号+都道府県+丁目を含む行が **2件**、
商品名自体が「【指定なし：住所注意備考欄】」となっているものが **4件** あった。

`note` はそのままプロンプトへ渡され、生成結果は**公開される商品説明**になる。
つまり **他人の住所が商品ページに載り得る** 経路だった。

### 2.3 商品名の `【…】` に社内情報 —— 顧客の氏名を含む

300件中 **190件(63%)** の商品名に `【…】` が含まれていた。中身の実例:

```
「兄」「指定なし」「日時指定なし」「モデルルーム案件」「ヤフオク1/2」
「在庫1」「在庫2」「2脚セット」「配達希望日確認中」「2/9納品確定：セット販売」
「井口へ売却」「林田様確定」「伊藤様」   ← 取引先・顧客の氏名
「指定なし：住所注意備考欄」
```

商品名はAIへ渡す一次情報なので、これらもそのまま顧客向けの説明へ流れ込む。
**顧客の姓が公開商品ページに載り得た**うえ、在庫数(「在庫1」)も同じ経路で漏れる。

### 2.4 `note` に社内の価格情報

`note` 162件中 **82件に「数字+円」**、34件に「定価/販売価格」があった。
実例: `"定価42000円販売価格18000円送料込み"`。

初回の評価実行で、実際に生成文へ
**「定価42000円のところ、販売価格18000円（送料込み）でお求めいただけます。」**
が出た。これもモデルは与えられた事実に忠実だっただけ。説明文中の価格は
出品情報側の価格と食い違う原因になるため、渡さないことにした。

## 3. 直した内容

### 3.1 入力側 —— `lib/ai/productIntro/facts.ts`

`buildCustomerSafeFacts()` を通してからでないとAIへ渡せないようにした。

| 項目 | 処理 |
| --- | --- |
| `conditionRating` が数値スコア | **落とす**。顧客向けの状態説明は `damageNotes` から取る |
| `conditionRating` が説明文 | `damageNotes` が無ければ状態説明として使う |
| `note` に住所・電話番号 | **丸ごと落とす** |
| `note` に金額 | **金額の行だけ落とす**(商品情報の行は残す) |
| 商品名の `【…】` | **除去**(顧客の氏名・在庫数・納品予定等) |
| 寸法 | `幅◯ × 奥行◯ × 高さ◯（cm）` へ整形。無ければ null(捏造しない) |

落とした項目は `redactions` として返り、**サーバーログにだけ**記録する。

### 3.2 出力側 —— `lib/ai/productIntro/factSafety.ts`

プロンプトの指示だけに頼らず、生成結果を決定的な規則で検査する。
検査に落ちたら最大3回まで作り直し、**それでも通らなければ結果を返さない**
(社内情報が載った文章を出すより、生成できなかったと伝えるほうが害が小さい)。

検出する違反:

`INTERNAL_CONDITION_SCORE` / `STOCK_DISCLOSURE` / `SKU_OR_MANAGEMENT_ID` /
`UNSUPPORTED_BRAND` / `PERSONAL_DATA` / `PERSON_NAME` / `PRICE_CLAIM` /
`SECTION_HEADING_CONTAMINATION` / `PROMPT_LEAKAGE` / `EMPTY_OUTPUT` /
`TOO_LONG` / `EXCESSIVE_REPETITION`

`UNSUPPORTED_BRAND` は、**今回の商品の事実に含まれないブランド名**が
出た場合に落とす —— 報告されていた
「関連ブランドにはムートやHAYがあります」への直接の対策。
商品名にHAYが含まれる商品でHAYに言及するのは正当なので通す。

誤検出を避ける確認もテストで固定した(寸法の数値・「3人掛け」・「円形」を
それぞれ在庫数・スコア・金額と取り違えない)。

### 3.3 プロンプト

システムプロンプトへ、観測された不具合に対応する禁止事項を明記した
(数値でのコンディション表現、在庫数、社内識別子、個人情報、
商品名に無いブランド、定型セクション見出し、指示文自体の出力)。

ユーザープロンプトは §4.8 に従い
**「文体例」→「今回の商品について確認できている事実」** の順に分離した。

### 3.4 返信案(LINE等)も同じ経路へ

`generateReplyDraft` にも `conditionRating` が直接渡っていた。
顧客が読む文章である点は同じなので、同様に
`buildCustomerSafeFacts` を通すようにした。

## 4. BELLO文体の学習(§4.4〜§4.6)

### 4.1 抽出

指示書は `◎商品のご紹介` 見出しを想定していたが、実データを見たところ
BELLOが実際に使っているのは **罫線で囲まれた導入部** だった:

```
＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿
ヤマギワのテーブルライト「Libra」
モダンテイストでシンプルながらも存在感のあるデザイン。
…                                    ← ここが「商品のご紹介」に相当
＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿＿
【商品名】…  【サイズ】…  【注意事項】…
```

`extractProductIntro()` は両方に対応する(見出し形式・罫線形式・
先頭テキスト形式)。HTML・`<br>`・全角/半角・装飾記号の揺れも吸収する。

**取り出せなかったものを「とりあえず全文」で代用しない。**
定型文だけ・社内情報混じり・短すぎる、はそれぞれ理由付きで失敗を返し、
corpus から除外する。

### 4.2 実測(本番5,313件に対する全件実行)

```
スキャン        : 5,313件 / note付き 2,920件
紹介文の抽出成功: 132件
  失敗の内訳: NO_INTRO_SECTION 2,768 / TOO_SHORT 11 / INTERNAL_CONTAMINATION 9
個人情報で除外  : 1件
金額を含み除外  : 32件
重複で除外      : 14件
corpus採用      : 40件（平均160文字、平均3段落）
```

`INTERNAL_CONTAMINATION` で9件弾けているのが重要 —— これらを混ぜていたら、
AIは「説明文にコンディションスコアや販売価格を書く」ことを手本として
学習していた。

### 4.3 文体資料はビルド成果物

`npm run build:style-corpus` が
`lib/ai/productIntro/styleCorpus.generated.json` を作る。
実行時はこれを静的に読むだけで、生成のたびにInventoryをスキャンしない
(§6.2の性能要件)。

安全性は二重の網: 抽出時に社内情報混じりを弾き、書き出し時にさらに
個人情報・金額・重複を弾く。**入るのはBELLO自身が書いた顧客向けの
紹介文だけ**で、社内メモ・価格・個人情報は入らない。

### 4.4 few-shot 選択

商品名の語の重なり(bigram込みのJaccard)で近い例を選ぶ。
ベクトル検索のような有料インフラは導入していない —— まず単純な指標で
足りるかを見る、という §4.6 の方針に従った。

- 毎回3件まで、合計1,500文字までに制限
- 同一文面の重複を避ける
- 自分自身を手本にしない
- ブロックの**前後の両方**で「事実の出典ではない」と明示する
  (長いブロックの手前だけの注意書きは無視されやすいため)

そのうえで、過去商品のブランド名等が新商品へ移っていないかを
生成後に `UNSUPPORTED_BRAND` が機械的に検査する ——
プロンプトの但し書きだけに頼らない。

## 5. 品質評価(§5.1) —— 実モデルでの実測

`AWS_PROFILE=Bello npm run evaluate:listing-copy 20`

実在の在庫20件について、同じ商品を2通りの渡し方で生成し、
**品質ゲートを通す前の生の結果**を採点した(ゲート後だけを見ても
ゲートの効果は分からないため)。

```
── BEFORE（従来の渡し方: 社内スコア・noteをそのまま渡す） ──
  生成成功       : 20/20
  違反なし(合格) : 7/20 (35%)
  平均レイテンシ : 2,540ms
  違反の内訳: INTERNAL_CONDITION_SCORE 12件 / PRICE_CLAIM 2件

── AFTER（buildCustomerSafeFacts + 文体例） ──
  生成成功       : 20/20
  違反なし(合格) : 20/20 (100%)
  平均レイテンシ : 2,371ms
```

生成例(AFTER):

> **title**: 未使用品 SLAMP CACTUS テーブルランプ
> **description**: 未使用品のSLAMP CACTUS カクタス テーブルランプです。モダンでラグジュアリーなデザインが特徴で、ホテルライクな雰囲気を演出します。幅25cm × 奥行25cm × 高さ21cmのコンパクトなサイズながら、存在感のある卓上照明です。お部屋のアクセントとして、また上質な空間づくりに最適なアイテムです。
> **condition**: 未使用品のため、目立った傷や汚れはありません。

商品名の復唱だけで終わらず、BELLOの既存文章にある
「お部屋のアクセントとして最適です」に近い語り口へ寄っている。
社内スコア・在庫数・価格・無関係ブランドはいずれも出ていない。

> 注: BEFOREの数値は検査器の種類が増える前後で変わる(初回計測時は
> `PRICE_CLAIM` がまだ無く 60%、`PRICE_CLAIM` 追加後は 35%)。
> どちらの計測でも AFTER は 100% で、差の向きは変わらない。

## 6. BASE連携の状態(§4.2 / §6.1)

### 6.1 実測: StagingのBASEは接続されていない

```
Amplifyアプリ bello-inventory-staging の環境変数:
  アプリ側   : CONVERSATION_TABLE_NAME, MESSAGE_TABLE_NAME のみ
  ブランチ側 : 0件
  → BASE_CLIENT_ID / BASE_CLIENT_SECRET は未設定

DynamoDB:
  BaseOAuthToken-j6up24p7lnczdmklzjdt3vrp4y-NONE : 0行
  BaseItemCache-…                                : 0行
  Feature-…                                      : 0行
```

### 6.2 P0だったこと: 本番で黙ってモックデータを返していた

`getBaseClient()` は、認証情報が無いと **どの環境でも**
`console.warn` だけ出してモッククライアントへフォールバックしていた。
モックが返すのは `lib/base/fixtures.ts` の作り物の商品
(vitra Softshell、Cassina、HAY、USM、Artek 等、いかにもBELLOにありそうな商品)。

つまり **Staging(本番相当)で、管理画面のBASE商品検索は
作り物の商品を実在の商品として返していた**。そのまま特集ページを作れば、
存在しない商品が載ったページを公開し得た。画面上には
「BASEに繋がっていない」という表示がどこにも無かった。

**直した内容**: モックを使うのは明示的なopt-in(`BASE_USE_MOCK=true`)か、
本番ビルドでないローカル開発に限る。本番で認証情報が無ければ
作り物を返さず `BaseNotConfiguredError` で失敗する。

### 6.3 設定画面にBASE接続状態を追加

設定 → 「BASE連携」タブ。**新しいBASE認証情報は作らず**、既存の
特集ページ連携設定をそのまま参照して状態を表示するだけ。

表示するのは、接続状態(接続済み / 未連携 / 未設定 / モック使用中)、
アプリ認証情報の有無、OAuth連携の有無、商品データの取得元(実データか
モックか)。**Client Secret / Access Token の実値は一切表示しない。**

## 8. 【ユーザー操作が必要】BASE連携

BASEの実商品を使うには、以下は本人操作が必要(コード側では代替できない)。

1. BASEデベロッパー登録で取得した Client ID / Client Secret を、
   Amplify Console の環境変数
   `BASE_CLIENT_ID` / `BASE_CLIENT_SECRET` / `BASE_REDIRECT_URI` へ設定する。
2. BASEの認可画面でBELLOからのアクセスを許可する(BASEアカウント所有者本人)。

これが済めば、`npm run build:style-corpus` の取得元をBASEのdescriptionへ
差し替えるだけで、BASE商品からの文体資料構築が動く
(`extractProductIntro` は入力がどちらでも同じように動作する)。

## 9. 残っている課題(未修正・要判断)

### Amplify Data の `errors` を見ていない読み取りが22箇所

`const { data } = await serverDataClient.models.X.list(...)` の形で
`errors` を無視している箇所が22件ある(`errors` を確認しているのは18件)。
権限エラーやネットワークエラーが「データが無い」と区別できず、
画面上は空表示になる —— §6.1 が問題にしている silent failure と同じ形。

**今回は直していない。** 22箇所それぞれについて「失敗をどう表示すべきか」
の判断が必要で(空表示のままでよい箇所もある)、UIの実機確認なしに
一括で変えるとかえって壊す危険があるため。明日以降の最優先候補。

### 商品名・noteの社内情報は、データ側の整理も検討に値する

今回はAIへ渡す直前で除去する対策を入れたが、
`【林田様確定】` のような顧客氏名が商品名に入り続ける運用そのものは、
検索・一覧表示・CSV出力など**AI以外の経路**でも露出し得る。
運用ルール側の整理を検討したほうがよい(これは実装ではなく運用の判断)。
