### 2.5 既知の残骸（原因と、消してよいかの判断）

#### (a) 存在しない在庫を指す在庫履歴 — 315在庫分 / 328行

内訳を出したところ、

```
ZAICO同期:314 / ZAICO画像:9 / カテゴリ:2 / 削除:1 / 登録:1 / 画像:1
```

で、314行はすべて `ZAICO同期 / ZAICO ID xxx から新規作成 (SKU Bxxxxxx)`、
**日付はすべて 2026-08-30**、実行者も同一でした。

これはZAICO同期が同じ商品を重複作成していた不具合の日で
（`lib/inventory/zaicoDuplicateAudit.ts` 冒頭に経緯が残っています）、
その後の重複整理で消された在庫の履歴です。

**判断: 消すべきではありません。** 在庫を物理削除しても履歴は残す設計で
（`deleteInventory` は削除のあとに「削除」の履歴を書きます）、古物台帳としての記録だからです。

なお「削除」の記録が無いまま在庫だけ消えているケースは、本来なら
**重複統合が参照の付け替えに失敗した跡**でもありえます。今回それが起きていないことは
日付と内容から確認できました（付け替え失敗なら日付が散らばり、内容も混在するはずです）。

#### (b) 存在しない会話を指す通知 — 6件

`scripts/cleanup-mercari-misingested.ts`（誤取込の会話を消す一度きりの復旧スクリプト）が、
関連する Message / ReplyDraft / NotificationDelivery を `.list({limit: 900})` の
**1ページ分だけ**で拾っていた取りこぼしです。

**判断: 実害は軽微。** 表示上「会話へ辿れない通知」になるだけで、送信済みの記録としては正しい。
消す場合は業務判断（通知履歴を残したいか）が要るため、こちらでは消していません。

#### (c) 存在しない在庫を指す出品下書き — 1件

`deleteInventory` が `ListingDraft` を消さないためです。

**判断: 削除するかは業務判断。** 「在庫は消したが下書きは残したい」運用もありえます。

| 経路 | 何が起きうたか | 実データでの発生 |

## 4. 継続的な検知

`npm run verify:data-integrity` を定期的に（週1回程度でも）実行すると、
孤児・重複・二重通知が**増えた瞬間**に分かります。基準値からの増加だけを見る形なので、
既知の残骸で毎回落ちることはありません。

読み取り専用（Scanのみ）で、実行時間は在庫5,329件規模で数十秒です。
