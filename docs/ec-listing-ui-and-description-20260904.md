## 2. UI(§1/§2/§3)

### 説明文の初期高さ

`rows={4}` → `rows={16}`(4倍)。リサイズは維持し、`resize-y` を**明示**した
——preflight任せにすると、将来誰かが `resize-none` を足しても気づかれない。
横方向のリサイズは止めた(2カラムをユーザー操作で壊せないようにする)。
文字数カウンタを下に添えた。

`<label>` と `<textarea>` を `id`/`htmlFor` で結び付けた。以前は結び付いて
おらず、支援技術からもE2Eからも「説明文」という名前で辿れなかった。

### 2カラム

`page.tsx` を `flex-col xl:flex-row` にし、右に
`InventoryFactsPanel`(`hidden xl:block w-80`)を置いた。フォーム側の上限は
`max-w-2xl xl:max-w-4xl`。

**xl(1280px)で切った理由**: フォーム 672px + 右パネル 320px + 間隔と
ページ余白で約1,064px 必要。ナビレール(64px)がその外側にあるので、
lg(1024px)では右パネルが潰れる。iPhone・iPadは1カラムのまま、そこから
先で2カラムになる(§3「タブレット等は適切なブレークポイント」への答え)。

モバイルでは**描画ごと落とす**(下へ回さない、§3)。

### 右パネルの中身(§2-1)

`getInventoryDetail` が既に返している値だけを読む(別DBへ複製しない)。
商品名/在庫ID/ブランド/カテゴリ/在庫ステータス/数量、幅・奥行・高さ・全長・
座面寸法・材質、3辺合計・家財おまかせ便ランク・佐川サイズ、コンディション
評価・傷汚れメモ・メンテナンス(判定根拠つき)、仕入/販売/販売予定価格、
ZAICO連携元・ZAICO在庫ID・市場・販売先商品ID。

**値が無い項目は行ごと出さない。**「—」で埋めると、未登録なのか取得失敗
なのかが読めない。足りない項目は下部の警告ブロックが名指しで出す。

配送判定は商品説明の生成と**同じ関数**(`buildListingFacts`)を通している。
画面と本文で別々に計算すると必ずずれる(§8)。

## 3. 商品説明の生成(§4–§21)

### AIとルールの境界(§19/§28)

```
AI     ◎商品のご紹介 だけ
ルール ◎商品詳細 / ◎発送について / ◎コンディション /
       ◎返品・返金対応について / ◎お取り置きについて
```

境界は `lib/ai/productPage/service.ts` の `buildDescription()`。
`ruleSections` が渡されたときは、AIの出力から採るのは `introduction`
だけになる。**生成後に差し替えるのではなく、最初からルール側で作る**
——差し替え方式だと、AIが書いた誤った寸法がどこかの経路で残る余地が出る。

プロンプトにも「これらのセクションは確定済みで、あなたの出力は使わない」
と明示した。書かせても捨てるので、トークンの無駄であるうえ紹介文へ
滲み出す原因になる。

### 指示書§19からの意図的なずれ(要確認)

§19はAI領域に「◎コンディションの商品別文章」を挙げているが、
**ルールベースで実装した**。§28が「傷・汚れ」「メンテナンス実施内容」を
名指しでAI創作禁止としており、そちらを優先した。商品ごとの分岐
(メンテナンスの組み合わせ × 状態の有無)はデータから決まるので、
固定文の連結ではなく**商品ごとに違う文章**になる(§11の要求は満たす)。

### ◎商品詳細(§6/§6-1)

ZAICOの値をそのまま並べる。AIに整形させない——「幅46cm」を「およそ46
センチ」と書き換えられると元の値と表示が一致しなくなる。

座面寸法は `lib/inventory/seatDimensions.ts`。CustomField を第一の出所と
し、無ければ**幅/奥行/高さの自由入力に紛れている座面表記**を拾う
(`lib/shipping/rank.ts` が送料判定から除外した候補をそのまま使う——
同じ判定表を2つ持たないための再利用)。範囲表記("43-53")は数値へ丸めず、
書かれたまま持ち回る。取れなかった軸は書かない。

### ◎発送について(§7/§8/§10)

`calculateShippingRankFromDimensionsDetailed`(既存)をそのまま使い、
「家財おまかせ便Cランク」を差し込む。**新しい判定ロジックは作っていない。**

判定できないときは推測せず `【配送方法未確定：要確認】` を残す(§10)。
規格外候補(451cm〜)もランク名を書かない——それは「Gランクの上」ではなく
個別見積りで、書くと誤案内になる。

### 佐川急便のサイズ(§9)

`lib/shipping/sagawaSize.ts`。**3辺合計 + 20cm** を判定値とし、次の区分へ
切り上げる。60/80/100/140/160(通常)、170/180/200/220/240/260(飛脚ラージ)。
261cm以上は判定不可。重量が分かる場合は寸法の区分と重量の区分の大きい
ほうを採る。外形3辺の読み取りは `rank.ts` の `resolveOuterDimensionCm` を
共有する(座面寸法・SH・AHを辺として拾わない保証を二重に書かない)。

**顧客向けの説明文へは自動で入れていない。** どの商品を佐川で送るかを
決めるデータがBELLOに無く、それを推測するのは§10違反になる。右パネルと
生成の内訳に事実として出し、担当者が判断できるようにした(→ §7 未解決事項)。

### ◎コンディション(§11–§16)

`lib/inventory/maintenance.ts` が リンサー/研磨/コーティング/クリーニング を
判定する。否定形(`研磨、塗装無し`——実データにある)と予定形(`研磨予定`)は
実施記録として扱わない。「プロ仕上げ」は何をしたか決まらないので採らない。

文章の組み立て(`descriptionSections.ts`):

| 記録 | 文章 |
| --- | --- |
| 研磨 + コーティング | 「当店にて表面を丁寧に研磨したうえで、仕上げにコーティングを施しております。」 |
| 研磨のみ | 「…仕上げを施しております。」(コーティングに触れない) |
| コーティングのみ | 「当店にて表面にコーティングを施しております。」(研磨したと書かない) |
| リンサー | §12の薬剤師監修の文章。材質が明らかにファブリック非該当なら使わず警告 |
| クリーニング | リンサーが無い場合のみ |

状態の文は「登録されている傷・汚れがあればそれを出す」「無く、かつ社内
評価が4.0以上なら良好の文」「どちらも無ければ書かずに警告」。
**傷の記録があるとき「良好」とは書かない**(§14)。

そのあとに §15 の共通文、§16 の共通注意事項を必ず付ける。

### 実データで見つけた不具合(修正済み)

実在庫で生成して初めて分かったもの:

```
◎コンディション
ファブリック部分は、…クリーニングを行っております。

リンサー          ← ここ
```

`damageNotes = "リンサー"`(実測71件)は**メンテナンスの記録**であって
顧客向けの状態説明ではないのに、そのまま出ていた。さらに「傷の記録が
ある」と誤判定され、傷の無い商品で良好の文章を出せなくなっていた。

`stripMaintenanceOnlyLines()` を足し、**判定は元の文字列に対して行い、
顧客向けの状態説明からはメンテナンスだけの行を落とす**ようにした。
傷の記述が1文字でも混ざる行は残す(開示を減らさない)。

あわせて `looksNonFabric` の除外材質を絞った。木・スチール・アルミの
椅子に布張りの座面が付くのはこの在庫では普通で、それらを理由に
ファブリック洗浄の文章を落とすと、実際にリンサーを掛けた商品でその
事実が消える。天板や什器そのものがその材質になるもの(ガラス・大理石・
セラミック等)だけを残した。

### データ不足時(§21)

`buildListingFacts` が警告を積む。生成は止めない。

```
⚠ 幅・奥行・高さのいずれかが登録されていません。
⚠ 座面寸法が登録されていません（座面のある商品の場合はZAICOをご確認ください）。
⚠ 配送ランクを確定できません：…
⚠ 佐川急便のサイズを判定できません：…
⚠ 材質が登録されていません。
⚠ メンテナンスの記録が見つかりませんでした。
```

生成画面(生成後)と右パネル(生成前)の両方に出る。

### 人の編集を消さない(§22)

以前は生成ボタンで無条件に上書きしていた。**最後に画面へ入れた文面と
違うときだけ**確認ダイアログを出す。生成直後にもう一度押す場合や
未編集の下書きを作り直す場合は確認を挟まない(毎回聞くと惰性で「はい」を
押すようになる)。

## 4. EC別の制約(§25)

`lib/listing/descriptionFormat.ts` を置き、BASE・Mercari双方の送信直前に
通した。共通の商品説明は1つのまま、変換だけがチャネルごと。

```
内部共通の商品説明 → formatDescriptionForChannel → 各ECへ送信
```

現在やっているのは改行の正規化(CRLF→LF、3行以上の空行を畳む)と制御文字の
除去、HTMLタグらしき記述の**通知**(除去はしない——本文中の「<」を勝手に
消すと文章が壊れる)。

**文字数上限は入れていない。** BASE `detail` / Mercari `description` とも
上限の記載を確認できなかったため、`maxLength: null`(=切り詰めない)として
`[UNVERIFIED]` を明記した。推測した上限で本文を黙って削るほうが、長すぎて
APIに弾かれるより気づきにくい。上限が判明したら表に数値を入れるだけでよく、
呼び出し側は変えなくてよい。

## 5. BASE既存商品分析との接続(§23)

既存の仕組み(BelloStyleProfile 267件の文体分析 + 類似BASE商品の参照)は
**そのまま**「◎商品のご紹介」の生成に使われている。今回の変更で、
セクション構造・固定テンプレート・配送判定・サイズ・メンテナンスは
すべてルール側が確定させるので、BASE過去文章より優先される
(§23の要求と一致)。BASE分析の役割は紹介文の品質だけに絞られた。

## 7. 未解決事項・人の確認が必要なこと

1. **佐川急便をいつ使うか**。サイズ判定は実装・テスト済みだが、
   「この商品は佐川で送る」と決めるデータがBELLOに無い。商品説明へ
   自動挿入すると§10の「配送方法を無理に判定しない」に反するため、
   現在は画面と生成の内訳に出すだけにしている。判断基準(サイズ上限・
   カテゴリ・重量など)を決めていただければ、説明文への挿入まで繋げられる。
2. **重量**。Inventoryに重量の項目が無いため、佐川の重量判定は常に
   寸法だけで決まる。重い小型商品(石材・ガラス天板)で実際の区分と
   ずれる可能性がある。
3. **カラー**。§2-1にあるが、対応する項目がZAICOにもBELLOにも無い。
   材質(`⚪︎材質`)だけを出している。
4. **EC別の文字数上限**。未確認のため切り詰めていない(§25)。
   実際の上限が分かり次第、`descriptionFormat.ts` の表に入れれば効く。
5. **状態説明の文体**。`damageNotes = "小傷あり"` のような短い記述は、
   そのまま顧客向けの本文に出る。事実を書き換えないことを優先した結果で、
   文章として整えるには「事実を変えずに言い換える」判断が要る。
   現状は担当者が編集する前提。
6. **材質の登録率**。5,329件中228件(4%)。紹介文の素材の記述はここに
   依存するので、登録が増えるほど品質が上がる。
