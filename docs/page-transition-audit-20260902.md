# 画面遷移が遅い件 — コード側調査

2026-09-02 / 対象ブランチ `claude/inventory-management-system-5vbvc7`（Staging）

ブラウザ実測ができない状態での調査。**計測しなくても確実に無駄だと分かるもの**だけを
直し、幅が分からないものは推測で触らずここへ「実測待ち」として残している。

件数はすべて Staging の実データを数えた値（us-west-2 / apiId `j6up24p7lnczdmklzjdt3vrp4y`）。

## 全ルートに共通していたもの

### 認証確認が1画面につき2回

`getInventorySessionStatus` は保護レイアウト（`app/inventory/(protected)/layout.tsx`）と
**その下の各ページ**の両方から呼ばれる。ページはさらに `getInventoryRole` 経由でも呼ぶ。
同じCookieに対して `fetchAuthSession` が最低2回走り、JWTの復号と検証をやり直し、
トークンが期限に近ければCognitoへのリフレッシュ往復まで2回していた。

`React.cache()` でリクエスト内だけ重複排除。呼び出し側は1行も変えていないので、
`getInventoryRole` の71箇所すべてがそのまま恩恵を受ける。

`getCurrentInventoryUserEmail`（23箇所）も同じ理由で包んだ。

### なぜキャッシュしても認可が緩まないか

`cache()` のスコープはリクエスト単位。別の利用者のリクエストへ漏れず、ログアウト後まで
生き残らない。Cookieはそのリクエストの間は変わらないので「同じ入力に同じ答え」という
意味は変わっていない。削ったのは往復の回数だけ。

## 直したもの

### 1. 重複していた認証確認（全ルート）

上記のとおり。全ルートで1往復ずつ減る。

### 2. マスタが100件を超えると黙って消える（未発現）

`listCategories` / `listLocations` / `listStatuses` / `listCustomFieldDefinitions` は
どれも `limit` 未指定で `filter: { isActive: { eq: true } }` を付けていた。DynamoDBの
filterは**読んだ後に間引く**ので、これは「100件読んで、そのうち有効なもの」を意味する。
無効化した行が増えて総数が100を超えた瞬間、有効なマスタが選択肢から黙って消える。
`nextToken` も辿っていないので2ページ目以降は最初から見ていない。

`lookupShippingRate` が東京都/Cで0件を返していたのと同じ種類の不具合
（`lib/amplify/listAll.ts` 冒頭に実測がある）。あちらは7箇所直したが、マスタ4種は
取りこぼしていた。

**いまは壊れていない。** Staging実データ:

```
Category               19件（うち有効 19）
Location               13件（うち有効 13）
StatusMaster            0件
CustomFieldDefinition   6件（うち有効  6）
UnitMaster              6件
```

どれも100に届いていない。「増えたら壊れる」側なので、件数が小さいうちに
`listAllPages` へ寄せた。設定画面の管理タブが使う `listAllCustomFieldDefinitions`
（無効も含む全件）も1ページ目だけを返していたので同様に直した。

これは速度の改善ではなく**正しさ**の修正。往復は増えていない（全件が1ページに収まる限り
呼び出し回数は同じ）。

> `StatusMaster` が0件なのは不具合ではない。`Inventory` 5,313件のうち `statusId` を
> 持つ行は**0件**で、ステータスは追加項目側で運用されている。念のため数えて確認した。

### 3. 詳細 / 編集ページの直列待ち

```
以前: 認可 → item → （マスタ4〜5件を並列）
いま: 認可 → （item ∥ ステータス ∥ 追加項目定義 ∥ 単位）
           → （カテゴリー ∥ 保管場所）
```

ステータス・追加項目の定義・単位は `item` に依存しないのに、`item` を取り切るまで
投げていなかった。依存があるのはカテゴリーと保管場所だけ（無効化済みでも名前が出るよう
`item.categoryId` / `item.locationId` を渡す必要がある）なので、そこだけ次の段に残した。

### 4. 設定ページのBASE接続確認が直列だった

`getBaseConnectionState(host)` は上の7件に何も依存していない（`headers()` は同期）のに、
`Promise.all` の**後ろ**で単独にawaitしていた。この画面は外部サービスの接続状態を4つ読む
（ZAICO / Mercari / LINE / BASE）ので、そのうち1つが直列にぶら下がっているのは効く。
`Promise.all` へ入れた。

## 直さなかったもの（実測待ち）

推測で変更すると、効かなかった場合に「変えた」という事実だけが残って切り分けが
難しくなる。以下は**ブラウザ実測を見てから**判断する。

| 候補 | なぜ保留か | 実測で見るもの |
|---|---|---|
| ルートごとの `revalidate` / `unstable_cache` | 在庫は編集の直後に反映されなければならない。キャッシュを入れるなら「どのくらい古くてよいか」を決める必要があり、それは実測ではなく運用の判断 | そもそもサーバ処理時間が支配的なのか |
| 一覧の画像サムネイル | 検索projectionで転送量は60.1%削減済み。残りが体感を支配しているかは不明 | 画像リクエストの本数と合計時間 |
| Amplify Hosting SSRのコールドスタート | コード側で減らせない。往復回数を減らしても定数項は残る | 連続遷移と初回遷移の差 |
| クライアントバンドル（設定33.4kB / 一覧13.5kB） | 遷移の遅さがサーバ側かクライアント側かがまだ切り分けられていない | TTFB と FCP/LCP の内訳 |
| `loading.tsx` が無いルート（`listings` / `sales` / `new` 等） | 体感の話なので、実際に待ちが見えているかを確認してから入れる | 遷移中に画面が固まって見えるか |

### すでに手が入っていて、今回は触っていないもの

- サイドバーの主要5ルートは hover / focus 時点で `router.prefetch` 済み
  （`InventoryNavRail.tsx`）。未保存変更ガードのため `<Link>` ではなく `button` で
  組まれており、その副作用でApp Routerの自動prefetchが効いていなかったのを補ってある。
- `/inventory` の総件数は Suspense で後追い（行の表示を待たせない）。
- 売上は月次集計（read model）から読む。5,313件/1,546KB → 13件/1.6KB。
- 設定ページのブートストラップは描画パスから外してプロセス単位に畳んである
  （料金マスターが450件になった時点で設定ページが8回中7回500になっていた）。
