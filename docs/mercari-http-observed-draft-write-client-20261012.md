# メルカリShops下書きHTTP書込部の準備境界（2026-10-12）

Downloadsの既存HARから値を出さずにGraphQL文書の宣言とフィールド引数を再確認した。作成は `CreateProductDraft($input: CreateProductDraftInput!, $idempotencyKeySeed: Float!)` → `createProductDraft(createProductDraftInput: $input, idempotencyKeySeed: $idempotencyKeySeed)`、更新は `UpdateProductDraft($input: UpdateProductDraftInput!)` → `updateProductDraft(updateProductDraftInput: $input)`。画像asset登録はHTTP 200応答を観測済みだが、multipart要求本文はHARにない。これらは管理画面の観測であり、公開API契約ではない。

`webHttpObservedDraftWrite.ts` に、サーバー専用・送信先固定の**一回のGraphQL mutation**を準備した。BELLOの通常画面、Server Action、API route、ジョブ実行器からは呼ばない。`fetch` と認証Cookieは信頼できるサーバー呼出元からのみ渡す設計で、このリポジトリには本番呼出元と画像asset証明の作成器がない。画像ファイル送信処理もない。

1. 凍結済みBELLOジョブと既存のDynamoDB予約の要求ID・試行ID・店舗枠・4秒の送信期限を照合する。さらに送信直前のBELLO在庫レコードをUUIDで読み直し、現在の `id`・`sku` が凍結ジョブの在庫ID・元在庫コードと一致することを要求する。店舗枠の次回可能時刻は、この送信期限から30秒以上後でなければならない。
2. BELLO原画像の同一バイトから登録済みasset IDを得た証明、1画像制限、凍結ジョブに対応する入力マッピング証明を要求する。更新には対象下書きIDと同じジョブの読取証明も要求する。いずれの証明も現状では生成できない。
3. BELLOの既存紐付けがなく、同じ認証状態で `OwnShops` が対象店舗を含み、下書き全ページの重複調査が作成なら不在、更新なら対象1件のみと確認できた場合だけ次へ進む。これらの読取アダプターは未接続。

これは「作成応答で下書きIDを受けた」「更新応答で同じ下書きIDを受けた」までの限定処理で、商品完成や出品成功ではない。一つの予約からはmutationを1件しか送らない。**作成後の更新には別の予約と対象下書きの永続的な紐付けが必要**だが、現行の予約は同じジョブの2回目を拒否するため、連続した下書き完成フローは未実装。既知のB005396は既存下書き2件があるので常に書込禁止。

## 保存済み準備登録からの更新専用接続（2026-10-12）

`webHttpStoredDraftUpdate.ts` は、保存済み `MercariBridgeHttpDraftJob` を要求ID・依頼者で読み直し、同じ依頼に紐付いた**既存下書き**・画像assetとBELLO原画像の同一バイト・人手選択・更新入力契約・直近の本人認証をそれぞれ確認できた場合だけ、上記マッパーと一回限りの書込部に渡すサーバー専用の接続点である。`CREATE` と公開操作の経路は持たず、PCも起動しない。売却・在庫・業務カテゴリ・販売市場はBELLOから読み、リモートの対象1件だけという全ページ重複確認を要求する。店舗共通の30秒間隔をDynamoDB予約で守り、結果不明時は同じ認証状態で読取照合して再送しない。書込部はリモート調査の前後でBELLO在庫を再読取する。

画像asset同一性・永続的な対象下書き紐付け・人手選択・更新契約・認証済みHTTPセッション・完全な重複読取を提供する**本番アダプターは存在しない**。この接続点を画面、Server Action、API route、ジョブ実行器から呼ばない。現在の準備登録だけでは更新対象も画像assetも確定せず、書込はできない。合成テストでUPDATE一回、証拠不足の停止、販売済み・重複の停止、30秒枠、結果不明時の再送禁止を確認したが、実Shopsへの更新成功を意味しない。作成後更新用の別予約・永続紐付けが未設計という前述の境界も残る。画像multipartの新証拠が得られても、それだけでこの未確認条件は満たされない。

独立レビュー後、重複の全件検索が長引く場合に認証確認を使い回せないよう修正した。検索後の予約前に同じセッションで再確認した時刻とCookie期限を照合し、書込部でも最新の重複読取後と更新要求の直前に再確認する。31秒かかった検索で古い確認時刻のままなら予約せず停止し、予約後や試行確定後に認証が不明になれば更新要求を送らない。いずれも合成テストで確認済み。新しい読取確認アダプターも本番にはまだない。

`webHttpReadOnlyClient.ts` に、既存HARで観測した `productDrafts(shopId,cursor,first)` の一覧queryと `GetProductDraft(id)` の詳細queryを用いる読取照合アダプターを追加した。一覧応答にはSKU・数量がないため、固定店舗を `OwnShops` で照合した同じセッションで全ページのIDを収集し、各IDの詳細からバリエーション別のSKU・数量を取得する。ページ情報の欠落、カーソルの循環、IDの重複、詳細の欠落、HTTP/GraphQLエラー、認証切れ、Cookie期限切れ、ページ・件数上限到達は未確定とし、途中までの候補を返さない。同じSKUが複数の下書きまたはバリエーションにあれば既存照合器が重複として扱う。照合結果は再送・更新・公開を許可しない。HARに一覧の一貫したスナップショット保証はなく、走査中の他操作による変化は検知できないため、欠落がないことの絶対的な証明とはしない。この読取アダプターも本番呼出元には接続していない。
