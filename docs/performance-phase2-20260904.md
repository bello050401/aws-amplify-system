## A. 既存の検索仕様（実装から起こした完全な仕様）

方式を選ぶ前に、コードから現行仕様を洗い出した。以下は「こうあるべき」ではなく
**現在そう動いているもの**。今回の改修でここは一つも変えていない。

### A-1. 検索の3経路

| 経路 | 入口 | 実装 |
|---|---|---|
| 通常の一覧 | 検索語なし・詳細検索なし | `listInventoryOffsetPage`（GSIへのQuery、表示ページだけ取得） |
| クイック検索 | 検索ボックス `?q=` | `listInventorySimpleSearch` |
| 詳細検索 | `?advanced=1&adv=…` | `listInventoryAdvanced` |

サイドバーの絞り込み（カテゴリ/保管場所/状態）は3経路すべてに乗る。

### A-2. 検索対象フィールド

**クイック検索**（検索ボックス）が見るのは次の3つだけ。

- 在庫ID（`displayId`。保存列ではなく `sourceSystem`/`sourceInventoryId`/`sku` からの導出値）
- SKU（`sku`）
- 商品名（`name`）

3つの **OR**、**部分一致**、**大文字小文字を区別しない**。

**サイドバーの絞り込み**

- カテゴリ（`categoryId`）— 複数選択は内部で **OR**
- 保管場所（`locationId`）— 完全一致
- 状態（`statusId`）— 完全一致
- 互いに **AND**。クイック検索の文字列とも **AND**。

**詳細検索**は静的43項目 + `CustomFieldDefinition` 由来の動的項目（`cf:` 接頭辞）。

| グループ | 項目 |
|---|---|
| 基本情報 | 在庫ID / SKU / 商品名 / カテゴリ / 保管場所 / 状態 / 数量 / 単位 / バーコード / 備考 |
| 価格 | 購入価格 / 販売予定価格 / 販売価格 / 販売手数料 / 送料 / その日の仕入れ合計金額 / 市場 / 商品ID / 出品情報 |
| サイズ | 幅 / 奥行 / 高さ / 全長 / 全長調節可否 / 取付タイプ |
| コンディション | コンディション評価 / 傷汚れ箇所等メモ |
| 日付 | 販売開始日 / 販売終了日 / 取引の年月日 / 作成日 / 更新日 |
| 古物台帳 | 品目 / 数量（仕入台帳）/ 取引区分 / 真偽確認の措置 / 相手氏名 / 職業 / 住所 |
| 管理情報 | 管理メモ |

**「ブランド」という専用フィールドは存在しない。**「材質」も同様で、どちらも運用上は
追加項目（CustomField）側にある場合のみ検索対象になる。この一覧は
`buildSearchFieldDefs` が実行時に組み立てるので、追加項目を増やしても自動で対象に入る。

### A-3. 演算子（部分一致 / 完全一致の別）

| 値の型 | 演算子 | 一致の仕方 |
|---|---|---|
| 文字列 | contains / notContains / equals / startsWith / isEmpty / isNotEmpty | **すべて大文字小文字を区別しない**。contains=部分一致、equals=完全一致、startsWith=前方一致 |
| 数値 | eq / ge / le / gt / lt / between / isEmpty / isNotEmpty | 数値比較 |
| 日付 | on / after / before / dateBetween / isEmpty / isNotEmpty | `YYYY-MM-DD` 部分だけで比較（`Date` へ通さない＝タイムゾーンで1日ずれない） |
| カテゴリ/保管場所/状態/選択肢 | equals / isEmpty / isNotEmpty | 完全一致のみ |

DynamoDB の `contains` は大文字小文字を区別するため、**文字列の判定はDB側では行えない**。
これが「候補を取得してからアプリ側で判定する」設計の理由で、今回もその設計は変えていない。

### A-4. AND / OR

- 詳細検索は条件リスト**全体に1つ**の結合子（AND または OR）。条件ごとの入れ子は無い。
- 入力途中で未完成の条件は無視される。条件が0件なら全件一致。
- サイドバーのカテゴリ複数選択だけが内部 OR。それ以外はすべて AND。

### A-5. 並び順

**更新日（`updatedAt`）の降順の1通りのみ。** 同値のときは `id` 降順で安定化する。
利用者が並び順を選ぶUIは無い。3経路すべてが同じ比較関数を共有する。

### A-6. ページング

`?offset=50&limit=50` のURLクエリ。絞り込み後の配列を `slice(offset, offset+limit)`。
**総件数は絞り込み後の正確な件数**を必ず表示する（推定値・打ち切り値は出さない）。

### A-7. 検索結果から最終的に必要になるフィールド

一覧の表示列（`INVENTORY_LIST_COLUMNS`）+ 拡張フィールド（`ALL_EXTENDED_FIELDS`）+
構造フィールド（id / 並び順 / 論理削除 / マスタ参照 / 在庫ID導出 / customFields）の**和集合**。
実体はサムネイル画像キー・価格・備考・追加項目などを含む `InventoryListRow`。

重要なのは、**この全部が要るのは「表示する50件」だけ**だということ。
5,329件すべてについて要るのは「判定に使う列」と「並び替えに使う列」だけだった。

## B. 何が遅かったのか（実測）

3経路のうち検索2経路は `fetchAllInventoryRecords` を通り、非削除の在庫を
**全件・全列**読んでからアプリ側で絞り込んでいた。

```
旧: 全列を全件走査        17,789ms / 14往復 / 5,329件 / 11.83MB
```

**どの検索条件でもこの負荷が固定でかかっていた。** 50件表示するたびに、毎回。

原因を分解すると:

| 要素 | 事実 |
|---|---|
| 往復回数 | 14回。DynamoDBの1ページ1MB上限で決まる |
| 転送量 | 11.83MB。判定に使わない列（画像配列・各種メモ・古物台帳項目など）が大半 |
| 射影が効かない理由 | AppSync の `selectionSet` は**AppSyncが返す項目**を絞るだけ。DynamoDB→AppSync 間は常に全列が流れる |

つまり `selectionSet` による削減（11.83MB→7.7MB）は AppSync から先だけの話で、
**一番重い区間には効いていなかった**。

## C. 方式の比較と選定

指示書の3案を、この規模（5,329件、将来10,000件超）で評価した。

### 案A: 全件走査の結果を短時間キャッシュする

| | |
|---|---|
| 効果 | 2回目以降は速い。初回は17.8秒のまま |
| 問題 | **在庫を1件編集するたびに全件キャッシュを捨てる**必要がある。捨てた直後の検索は再び17.8秒 |
| 問題 | SSRはLambdaで複数インスタンスに分かれる。インスタンスごとにキャッシュが要り、当たる保証が無い |
| 問題 | 11.83MBをプロセス内に持つ。10,000件なら22MB以上 |
| 判定 | **不採用。** 遅さの原因（毎回12MB運ぶ構造）を消さずに隠すだけで、「古いデータを表示して速く見せる」に近づく |

### 案B: 検索専用の軽量データ構造

| | |
|---|---|
| 効果 | 転送量を根本から減らせる |
| 検討 | 別テーブルを新設して同期する形にすると、**Inventoryと二重管理**になり、同期漏れが「検索にだけ出てこない在庫」として現れる。もっとも見つけにくい壊れ方 |
| 採用形 | **別テーブルを作らずに実現できる。** DynamoDB へ直結すれば `ProjectionExpression` で「その検索が実際に参照する列だけ」を読める。軽量な検索用レコードを**その場で組み立てる**ので、同期する対象が存在しない |
| 判定 | **採用** |

### 案C: OpenSearch などの検索サービス

| | |
|---|---|
| 規模 | 5,329件。10,000件でも小さい。全文検索エンジンが要る規模ではない |
| 費用 | OpenSearch Serverless は最小構成でも常時 OCU 課金が発生し、月あたり数万円規模。現在のDynamoDB読み取り費用（後述）とは桁が違う |
| 同期 | DynamoDB Streams → Lambda → OpenSearch の経路を新設。**障害点が3つ増える**（Stream遅延・Lambda失敗・インデックス不整合）。同期が遅れると検索結果だけが古くなる |
| 仕様 | 現在の仕様は「大文字小文字を区別しない部分一致」で、形態素解析もスコアリングも使っていない。OpenSearch の強みが要らない |
| 判定 | **不採用。** 指示書の「将来のためという理由だけで過剰な構成を追加しない」に該当する |

### 選んだ方式（案B）の具体形

検索を2段に分ける。

```
第1段（候補の絞り込み）
  DynamoDB へ直結 → その検索が実際に参照する列だけを ProjectionExpression で読む
                  → Scan を8セグメントに並列分割
  判定は従来と同一の matchesQuickSearch / evaluateQuery をそのまま通す

第2段（表示行の実体化）
  絞り込み後の50件だけを GetItem（同時発行）で全列取得
```

射影に何を入れるかは**人が並べない**。実行中の検索条件が参照している検索フィールドキーから
機械的に導出する（`lib/inventory/searchScanProjection.ts`）。

- `displayId` → `sku` / `sourceSystem` / `sourceInventoryId`
- `cf:*` → `customFields`
- それ以外 → 同名の列

並列セグメント数を8にした理由（実測）:

| 分割 | 時間 | 直列に待つ段数 |
|---|---|---|
| 1（直列） | 5,017ms | 14段 |
| 4 | 1,852ms | 4段 |
| **8** | **1,540ms** | **2段** |
| 12 | 1,361ms | 2段（往復総数だけ増える） |

## D. 実測（改善前後・同一条件・同一データ）

このノートPCから実行しているため、**往復1回あたり約160ms** が新旧どちらにも同じだけ
乗っている。本番（同一リージョンのLambda）ではこの待ちがずっと小さいので、
**絶対値は上振れした値**として読む。比率のほうが実態に近い。

### D-1. 検索

| | 時間 | 直列段数 | 読取件数 | 転送量 |
|---|---|---|---|---|
| **旧**（全条件共通の固定負荷） | 13,799〜19,364ms | 14段 | 5,329件 | 11.83MB |
| **新** クイック検索（該当なし） | 540〜877ms | 2段 | 5,329件 | 1.95MB |
| **新** 一覧の絞り込みのみ | 604〜1,042ms | 2段 | 5,329件 | 1.95MB |
| **新** クイック検索（324件ヒット） | 1,239〜2,992ms | 2段 | 5,329件 | 1.95MB |
| **新** 詳細検索（商品名 contains） | 1,196〜1,363ms | 2段 | 5,329件 | 1.95MB |
| **新** 詳細検索（2条件 AND） | 1,191〜1,195ms | 2段 | 5,329件 | 1.95MB |

## F. 指示書の個別項目

### F-1. `bello/mercari-api-token`（§4）— **Secret の新規作成は不要だった**

全参照を追跡した結果:

| 参照箇所 | 実体 |
|---|---|
| アプリ本体 | **1箇所も無い** |
| `scripts/measure-performance.ts` | 第1フェーズで**私が書いた計測ハーネス**が、存在しない名前を指定していた |
| `docs/performance-audit-20260904.md` | 上の結果をそのまま「Secretを作れば直る」と書いていた（誤り） |

（Secrets Manager 上で確認、2026-08-29 作成）。第1フェーズの `ResourceNotFound` は
Secret の不足ではなく、こちらのハーネスの誤記だった。

対応: 名前を2箇所に書かないよう `lib/listing/mercari/secretStore.ts` から
`MERCARI_SECRET_NAME` を export し、ハーネスがそれを参照するようにした。
再計測で正常に読めることを確認（187ms / 1件）。**AWS管理者の操作は発生しない。**

### F-2. StatusMaster 0件（§5）— **原因は「登録画面が一度も作られていなかった」こと**

調査結果:

| 事実 | 数値 |
|---|---|
| StatusMaster の行数 | 0件 |
| `statusId` を持つ在庫 | 0件 / 5,329件 |
| StatusMaster を作成する画面 | **存在しない**（設定画面はカテゴリ/単位/保管場所/追加項目のみ） |
| ZAICO からの写像 | 無し（`state` が実データで空だったため写像を見送った経緯がコードに残っている） |

つまり「使われていない」のではなく、**登録する手段が無かった**。一方で一覧の「状態」列・
サイドバーの状態絞り込み・登録/編集フォームの状態選択・CSV入出力はすべて生きており、
構造ごと削ると機能を落とすことになる（指示書§8の禁止事項に該当）。

対応: **正しいマスタを作れるようにする** ——設定画面に「状態」タブを追加した。
`code`（schema上必須）は表示名から機械的に生成し、名称変更では変えない（識別子だから）。

**データは1件も入れていない。** 何を状態として持つかは運用が決めることで、こちらが
それらしい値を入れてよいものではない。既存のシード処理（カテゴリ/保管場所/単位）にも
状態は追加していない。

### F-3. コールドスタート（§3）— 調査のみ。**定期ウォームアップは導入していない**

Staging の SSR 実行経路（CloudFront を素通りさせるためクエリを毎回変えて計測）:

| 状況 | 1発目 | 直後の2発目 | 差（＝コールド増分） |
|---|---|---|---|
| 連続アクセス（ウォーム） | 382〜533ms | — | — |
| **5分アイドル後** | 578ms | 334ms | +244ms（＝通常のばらつき。**まだウォーム**） |
| **10分アイドル後** | **2,465ms** | 483ms | **+1,982ms（コールド）** |

**アイドルからコールドに落ちる境目は 5分超〜10分以内。** 増分は約2秒で、
第1フェーズで観測した +1.7秒とほぼ一致する。

※ 15分以降の測定は、途中で今回のデプロイ（job 224）が入って Lambda が入れ替わったため、
「アイドルによるコールド」と「デプロイ直後のコールド」が混ざる。切り分けられない値は
載せない。上の 5分/10分 は**デプロイ前に取った値**なので、この結論は影響を受けない。

分かっていること:

- Amplify SSR（Lambda）のウォーム保持時間は AWS が公表しておらず、**外から確定できるのは実測だけ**。
  今回の実測で「5分は保つ、10分は保たない」ところまでは確定した。
- 必要なウォームアップ間隔: 5分は保ち10分は保たないので、確実に効かせるなら **5分間隔**。
  月あたり約 8,640回の追加SSRリクエスト。
- 費用: Lambda の呼び出し課金自体は極小だが、**Amplify Hosting は SSR リクエスト単位でも
  課金される**ため、その上乗せがアイドル時間帯にも常時発生する。
  料金体系は変わりうるので、金額そのものは請求ダッシュボードで確認していただきたい
  （こちらから請求情報は参照していない）。
- 実運用の頻度: 利用者が数名の社内システムで、昼間は数分おきに操作が入る一方、
  夜間・休日は数時間アイドルになる。**コールドを踏むのは「その日の最初の1回」と
  昼休み明けなど、1日数回**にとどまる見込み。

現時点の見解（決定ではなく提案）: 1日数回・1回あたり約2秒のために、24時間×5分間隔の
ウォームアップを常時回すのは割に合わない。**指示どおり本番へは入れていない。**
入れるとしても「営業時間帯だけ」に絞るのが妥当で、その判断はご本人にお願いしたい。

### F-5. 全画面の再点検（§7）

計測ハーネスで再測した結果（DynamoDB / Secrets Manager のみ。AppSync・SSR・描画は含まない）:

| 画面 | 合計 | 往復 | 転送量 |
|---|---|---|---|
| 在庫一覧 | 3,379ms → **約1.0秒**（件数集計の並列化後） | 19回 | 404KB |
| 在庫一覧（検索） | 14,338ms → **約0.5〜1.4秒** | 14回 → 直列2段 | 12,113KB → 1,950KB |
| 商品詳細 | 966ms | 6回 | 15KB |
| メッセージ | 1,056ms | 6回 | 100KB |
| EC出品 | 1,474ms | 9回 | 15KB |
| 設定 | 1,500ms | 8回 | 228KB |

指示書§7の観点で確認した結果、**実測の裏付けがある問題は検索と件数集計の2つだけ**だった。
以下は測ったうえで「直す必要が無い」と判断したもの（推測で触っていない）:

- **直列awaitの残り**: 商品詳細6往復・EC出品9往復は第1フェーズで `Promise.all` 化済み。
  再測でも1項目あたり160ms前後＝往復1回ぶんで、直列に積み上がっていない。
- **空テーブルへの問い合わせ**: `StatusMaster`（0件）・`ChannelListing`（0件）・
  `PricingRule`（0件）。いずれも1往復160ms、マスタは60秒キャッシュ済みなので
  1分に1回に収まる。**「空だから読まない」特別扱いはしない** ——登録された瞬間に
  出なくなる不具合を作り込むことになる。
- **Secrets Manager**: メッセージ画面2件・EC出品1件。いずれも183〜210msの1往復で、
  重複読み取りは第1フェーズで解消済み（`getZaicoTokenSource` の二重呼び出し等）。
- **画像URLの署名**: 一覧はサムネイルキーだけを持ち、署名はクライアント側。SSRの時間に乗らない。
- **過剰なプリフェッチ・SC/CC境界の重複取得**: 再測で該当なし。

### F-6. 禁止事項（§8）への適合

| 禁止事項 | 状況 |
|---|---|
| 検索条件を減らす | 減らしていない。対象43項目＋追加項目、演算子もすべてそのまま |
