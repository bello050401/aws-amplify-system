# メルカリShops直接連携の次の観測境界（2026-10-04）

## 採用する経路と実証済みの範囲

本人の方針は、正規のメルカリShops管理画面にログインした専用PCブラウザと、その画面で実際に観測したHTTP通信を使う直接連携である。公式Shops APIを利用する機能はこの経路へ組み込まない。別途作成した `tools/bello-mercari-bridge/src/officialSkuLookup.mjs` は未採用の独立候補であり、PCアプリ・BELLO本体・今回の実証手順から呼ばない。

B005795の既存商品では、通常の管理画面読取から得た正確なqueryを同じPCのログイン状態で一度だけHTTP送信し、同一商品・店舗の `MATCHED / HTTP 200` を確認した。証拠と一回限りの試行記録は [認証付きHTTP読取検証](mercari-direct-read-proof-20261004.md) に記した。これは**既存商品の読取**だけの成功であり、書込、新規出品、BELLO Webサーバー上の認証付き送信は未実証である。Web画面だけで完結する連携も未実証。

## 書込の既存証拠と欠けている情報

| 対象 | 観測できた事実 | 直接HTTP書込のために欠けている情報 |
| --- | --- | --- |
| 既存商品の画像 | 旧操作で `createImageAsset` のmultipart応答がHTTP 200・GraphQLエラーなし。別セッションの編集画面に画像2枚が表示された。 | multipartの要求形式、画像アセットと商品との関連付け、送信と読戻しの同一試行の照合。画像のバイト同一性も未確認。 |
| 既存商品の非公開保存 | 旧通信概要で `input.status` 等の**項目名と型**を観測。後の画面には対象商品の非公開・価格・在庫が表示された。 | 操作名・query・変数の正確な値と型の全体、クリック直後の要求と応答の対応、商品・店舗IDと非公開状態の応答照合。後の表示が旧保存の結果かも未確認。 |
| 新規出品 | 該当する通常操作の通信は観測していない。 | 新規作成の要求と応答の契約全体、画像取込、非公開作成後の読戻し、重複時の扱い。既存商品の更新要求から作成要求を推測しない。 |

保存済みの安全な通信概要には本文、変数値、Cookie、画像バイトがなく、後から送信契約を復元できない。HTTP 200だけで保存・出品成功と判定しない。[画像観測](mercari-existing-image-live-observation-20261004.md)と[非公開保存の分析](mercari-private-save-live-analysis-20261004.md)は旧試行の記録であり、再送の許可ではない。

## 新しいSKUを求める前にできること

1. **読取だけで現在状態を固定する。** 既存B005795の正確な商品ID・店舗IDに結び付く通常の読取で、現在の非公開状態、価格、在庫、画像表示を個別に確認できる範囲を調べる。確認できない項目は未確認と記す。この操作から書込契約は得られない。
2. **旧試行との重複を排除する。** B005795には画像選択と非公開保存の消えない試行マーカーがある。画像の再選択、保存の再クリック、マーカー削除、既存商品IDの再作成をしない。「公開設定に進む」だけでも送信がなかった証拠はないため、観測目的で押さない。
3. **既存コードの観測能力を整理する。** `manualMutationObservation.mjs` は通常の管理画面操作に付随する通信の操作名、queryハッシュ、入力の項目名と型、対象ID・非公開状態との一致、応答エラーとID・状態を安全な固定値へ縮約できる。ただし旧保存では段階・要求・応答の同一性が不足した。現在の安全記録を再読取しても欠けた本文は戻らない。

**内容不変の非公開保存も外部書込である。** B005795では旧試行と重複するため実行しない。別の既存非公開商品で行うとしても、新しい一回限りの書込試行となり、画面上の値が同じでも更新日時等が変わる可能性がある。本人が対象と画面内容を確認する前に行わない。既存商品の更新を観測できても、新規出品の契約を得たことにはならない。

## 将来、書込観測を1件だけ行う場合の最小条件

これは**計画**であり、今回の外部書込はない。既存商品で更新通信を観測する場合は、旧試行と別の非公開商品に限定し、開始前に商品ID・店舗ID・BELLO在庫ID、全表示項目、画像の枚数と順序、非公開状態を読取で固定する。売却・終了・在庫不一致や既存マーカーがあれば停止する。通常の「非公開で保存する」操作を観測する前に、対象商品と操作種別で永続的な一回マーカーを作る。観測器は操作前に設置し、最終クリック直前に段階を記録して観測上限を保存通信へ割り当てる。操作後は要求の操作名・queryハッシュ・入力の項目名と型・正確な対象ID/非公開状態との一致、応答のGraphQLエラー有無・商品/店舗ID・非公開状態・HTTP状態を**同じ要求**で照合する。機密値や本文は保存せず、未知の応答は `UNKNOWN` とする。応答が不明でも再クリックせず、別セッションの正確な商品読戻しで結果を確認する。前後の画像・価格・在庫・公開状態が一致しなければ成功扱いにしない。

安全な概要とqueryハッシュだけでは、直接HTTP送信に必要な正確なGraphQL文書と入力の対応を再構築できない。将来の一回の通常保存と同時に、要求本文を**そのPCのメモリ内だけ**で解析し、単一の書込操作、固定の文書、入力項目、本人確認済みの商品IDと非公開状態を検証する観測器を別途設計・レビューする。保存するのは検証済みの非秘密な仕様と固定判定だけとし、Cookie、トークン、商品値、画像バイト、任意の生本文は残さない。通常保存の要求を直接HTTPでもう一度送ることはしない。この実装と実機観測はまだない。

この1件が成立しても、証明できるのはその既存商品の更新通信だけである。新規出品と画像送信は、それぞれ通常画面で別の一回限りの操作・要求/応答照合が必要になる。新しいSKUと商品下書きの確認は、その段階で具体的な出品対象が必要になってから本人と行う。公開操作はさらに別の判断とし、非公開保存と混ぜない。BASEとNext Engineの動作は今回変更しない。
