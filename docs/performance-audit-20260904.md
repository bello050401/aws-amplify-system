# BELLO 性能総点検 報告書(2026-09-04)

対象: 性能・レスポンス総点検指示書 §1–§14。

---

## 0. 先に結論

実測した結果、体感の遅さは**1箇所の巨大なボトルネック**ではなく、
次の4つが重なったものでした。

| # | 原因 | 実測 | 状態 |
| --- | --- | --- | --- |
| 1 | 一覧の総件数を数えるために在庫11.83MBを読んでいた | **16.3秒 / 11.83MB / 往復14** | 修正済(3.7秒 / 0MB) |
| 2 | Amplify SSR のコールドスタート | **+1.7秒**(実Staging) | 未修正(→ §8 P1) |
| 3 | マスタ4種を全画面が毎回読み直していた | 毎画面4往復 | 修正済(2画面目以降0往復) |
| 4 | 在庫一覧がマスタを待ってから在庫を取りに行っていた | 2ウェーブ直列 | 修正済(1ウェーブ) |

加えて、温まった状態でも **SSR の TTFB に約280ms** かかります。これは
日本 → CloudFront(NRT) → us-west-2 のオリジン往復で、コードでは縮みません。

## 1. 測定方法と、測れなかったこと(§1)

### 測れたもの

| 手段 | 何を測ったか | コマンド |
| --- | --- | --- |
| 実Stagingへの HTTP | SSRのTTFB、コールドスタート、応答サイズ | `npm run measure:staging-http` |
| 実StagingのDynamoDB | 各画面が行う読み取りの時間・往復回数・転送量 | `npm run measure:performance` |
| 画面の読み込み関数 | 各画面のデータ読み込みを同じ構造でそのまま実行 | `npm run measure:page-loads` |
| ビルド出力 | クライアントJSの大きさ | `npm run build` |

### 測れなかったこと(推測で埋めていません)

**ログイン済み画面のブラウザ実測ができていません。** 理由:

1. Staging へブラウザでログインするには資格情報が要りますが、この環境の
   Windows 資格情報マネージャーに登録されていません(登録は利用者本人にしか
   できません)。
2. ローカルで代替しようとしましたが2つの壁がありました。
   - `next start`(本番ビルド)では `NODE_ENV` がビルド時に埋め込まれるため、
     開発機の認証バイパス(条件が `NODE_ENV!=="production"`)が構造的に通らず、
     307でログインへ戻されました。
   - `next dev` はコンパイル時に Google Fonts を取りに行きますが、この環境は
     そこへ到達できずタイムアウトします。

そのため、**「在庫一覧 4.2秒 → 1.1秒」のような画面全体の秒数は出せません**。
代わりに、画面が実際に呼ぶ読み込み関数を同じ構造で実行して比較しています。
往復回数と読み取り量は本番と同じで、そこが今回の改善対象そのものです。

### 数字を読むときの前提

- `measure:page-loads` / `measure:performance` は **この端末から us-west-2** へ
  接続しています。1往復あたり約160msのネットワーク遅延が含まれます
  (Amplify上なら同一リージョンで数ms)。**絶対値は本番より大きく出ます。**
- 同じ理由で、比べてよいのは「同じ条件での変更前後」と「往復回数・転送量」です。

| --- | --- | --- | --- |
| ログイン画面(SSR、DBなし) | 2,030ms | 298ms | **+1,732ms** |

**読み取れること**

- **コールドスタートが +1.7秒**。しばらく操作していないと必ずこれを踏みます。

## 5. ボトルネックランキング(§8)

### P0 — 非常に大きい

**P0-1. 一覧の総件数を数えるために在庫11.83MBを読んでいた**

- 場所: `lib/inventory/inventoryPage.ts` `countActiveInventory`
- 実測: **16.3秒 / 11.83MB / 往復14**(データ層のみ)
- 原因: `selectionSet: ["id"]` を付けていたが、それは **AppSyncが返す項目を
  絞るだけ**で、DynamoDBは行の中身を全部読んでいた(射影は読んだ後に効く)。
  件数しか要らないのに12MBを運んでいた。
- 改善: DynamoDB の `Select: COUNT` で数える。行を返さず数値だけ受け取る。
- 実測改善: **17,785ms → 3,675ms(-79%)、転送 11.83MB → 0MB**
- リスク: Amplifyのフィルタと同じ条件をDynamoDBの式で書き直すため、
  ずれると**件数だけが静かに違う**。→ 実データで6通りの条件を突き合わせる
  検証を追加(`npm run verify:inventory-count`、全件/カテゴリ1件/OR/保管場所/
  AND/存在しないID)。すべて一致を確認済み。

**P0-2. Amplify SSR のコールドスタート +1.7秒**

- 場所: Amplify Hosting の SSR(Lambda)
- 実測: 1回目 2,030ms / 温まった状態 298ms = **+1,732ms**
- 原因: しばらく叩かれていないとコンテナ起動から始まる。
- 状態: **未修正**。§9 の「機能を削らない」を守る範囲でできる対策は
  「初期化時の読み込みを減らす」ですが、今回の計測ではクライアントJSも
  サーバー初期化も特に大きくありません(First Load JS 147〜170KB)。
  効果が見込めるのは定期的なウォームアップですが、これは**動作を変える
  変更**なので判断を仰ぎます(→ §8)。

### P1 — 大きい

**P1-1. マスタ4種を全画面が毎回読み直していた**

- 場所: `lib/inventory/queries.ts` の `listCategories` / `listLocations` /
  `listStatuses` / `listCustomFieldDefinitions`
- 実測: 1画面あたり4往復。中身は 20 / 13 / 0 / 12件しかない。
- 原因: `requestCache`(Reactのcache)は**1リクエストの中でしか効かない**。
  画面を移動するたびに読み直していた。
- 改善: リクエストを跨ぐキャッシュ(`lib/inventory/masterCache.ts`)。
  書き込み側11箇所が必ず捨て、加えて60秒TTLで別インスタンスの変更にも追いつく。
- 実測改善: **商品詳細の2画面目 497ms → 333ms、問い合わせ 6本 → 2本**

**P1-2. 在庫一覧がマスタを待ってから在庫を取りに行っていた**

- 場所: `app/inventory/(protected)/page.tsx`
- 原因: マスタ4本は並列だったが、その**全体**が在庫取得の前に挟まっていた。
  2つに依存関係は無い(在庫の絞り込み条件はURLのクエリだけで決まる)。
- 改善: 在庫の取得を先に始め、マスタと同時に待つ。
- 実測改善: **1,392ms → 1,098ms**(同一条件・同一ハーネス)

**P1-3. 検索・詳細検索が在庫を全件走査する**

- 場所: `lib/inventory/queries.ts` `fetchAllInventoryRecords`
- 実測: **16.4秒 / 往復14 / 11.83MB**(射影ありで 7.7MB)
- 原因: 部分一致とAND/ORの混在で、DynamoDBの条件式では表現できない。
- 状態: **未修正**(→ §8 で対処案)

### P2 — 中程度

**P2-1. 直結経路のGSI Queryが上限を渡していなかった**

- 場所: `lib/amplify/directData.ts` `modelIndexQuery`
- 原因: DynamoDBへ `Limit` を渡さず1往復で1MB(実測769件)を読み、
  アプリ側のループが必要件数で打ち切っていた。**返す件数は変わらないのに
  読む量だけが10倍以上**。
- 影響範囲: 直結経路のみ(メルカリメール取込・問い合わせ処理・定期実行)。
  画面側は AppSync が limit を正しく渡しているので元から影響なし。
- 改善: `Limit` を渡す。
- 実測: 計測ハーネス上で在庫一覧の読み込みが 1,219ms → 548ms
  (ハーネスは直結経路を通るため。**画面の改善幅ではありません**)

**P2-2. Mercari TOKEN の Secret が存在せず、毎回509msの例外**

- 場所: EC出品画面 `isMercariConnected()`
- 実測: 509ms(`ResourceNotFoundException` まで)
- 原因: Secret 自体が未作成。未接続表示は正しいが、毎回例外まで待っている。
- 状態: 未修正(Secretの作成はAWS管理者の作業。→ §8)

### P3 — 軽微

- StatusMaster が **0件**(テーブルが空)。毎画面1往復して常に空を得ている。
  在庫ステータス名も解決できていない。**データ側の欠落**で、性能というより
  機能の問題として報告します。
- クライアントJS: First Load JS 147〜170KB。特に大きくありません。

## 6. 修正前 → 修正後(§10)

同じハーネス・同じ条件(実Staging直結)での比較です。

| 操作 | 修正前 | 修正後 | 改善 |
| --- | --- | --- | --- |
| **在庫の総件数(一覧の裏で走る)** | 17,785ms | **3,675ms** | **-79%** |
| 在庫一覧のデータ読み込み(初回) | 1,219ms | 1,098ms | -10% |
| 商品詳細(2画面目) | 497ms | **333ms** | -33% |
| EC出品(2画面目) | 514ms | 499ms | -3% |
| 在庫一覧の直列→並列(同条件比較) | 1,392ms | 1,098ms | -21% |

問い合わせ本数(往復回数)の変化 —— こちらは本番でもそのまま効きます。

| 画面 | 修正前 | 修正後 |
| --- | --- | --- |
| 在庫一覧(2画面目以降) | 5本(2ウェーブ) | **1本(1ウェーブ)** |
| 商品詳細(2画面目以降) | 6本 | **2本** |
| EC出品(2画面目以降) | 6本 | **4本** |
| 総件数 | 5本・11.83MB | **0本(COUNT)・0MB** |

転送量: 総件数の集計で **11.83MB → 0MB**。

AppSyncは1呼び出しごとに固定費がかかるので、2画面目以降の商品詳細で
6→2本になるのは、そのまま4往復ぶんの短縮です。絶対値は §1 の理由で
出せていません。

## 7. 計測基盤(§12)

今回だけ速くして終わりにしないための仕組みを残しました。

| コマンド | 用途 |
| --- | --- |
| `npm run measure:staging-http` | 実StagingのTTFB。冷/温を分けて出す |
| `npm run measure:performance` | データ層の往復回数・転送量・所要時間 |
| `npm run measure:page-loads` | 各画面の読み込みを同じ構造で実行して比較 |
| `npm run verify:inventory-count` | 件数の高速集計が従来の数え方と一致するか |
| `BELLO_QUERY_TIMING=1` | データアクセス1本ずつをサーバーログへ出す |

`BELLO_QUERY_TIMING` は `lib/perf/queryTiming.ts` + データクライアントの
Proxy で実現しています。**画面ごとに計測コードを書いていない**ので、
今後増える画面にも自動で乗ります。出力例:

```
[perf] 商品詳細 — 合計 333ms / データアクセス 2本 計327ms
     167ms  Inventory.get (1件)
     160ms  InventoryHistory.listInventoryHistoryByInventoryIdAndChangedAt (8件)
```

**既定は無効で、本番では何も出しません**(§12)。`Server-Timing` ヘッダを
組み立てる関数も用意してあり、必要になれば開発時にブラウザの開発者ツールから
見られます。

## 8. まだ残っているボトルネックと、次に効く場所

### 次に高速化すると最も効果が大きい順

**1. 検索・詳細検索の全件走査(P1-3)** — 実測 16.4秒 / 7.7MB(射影あり)

現状は「部分一致・AND/OR混在」をアプリ側で評価するため全件が要ります。
選択肢は3つで、いずれも**判断が要る**ので手を付けていません。

- (a) 走査した結果をプロセス内に短時間キャッシュする。検索の絞り込みを
  繰り返す操作は速くなりますが、1回目は変わらず、7.7MBをインスタンスごとに
  抱えます。
- (b) 検索対象の列だけを持つ軽量な行を別テーブル/GSIに持つ。読む量が
  1/10以下になりますが、同期の仕組みが要ります。
- (c) 検索専用のサービス(OpenSearch等)を入れる。最も速くなりますが、
  構成とコストが増えます。

**2. コールドスタート +1.7秒(P0-2)**

定期的にウォームアップする(数分おきに1回叩く)のが最も効きますが、
「動いていないときも動かす」変更なのでご判断ください。

**3. SSRの固定費 約280ms**

日本 → us-west-2 の往復です。縮めるにはリージョンを東京へ寄せる必要があり、
DynamoDB・Cognito・S3の移設を伴う大きな変更になります。

**4. Mercari TOKEN の Secret 未作成(P2-2)** — 毎回509msの例外待ち

> **【2026-09-04 第2フェーズで訂正】この項目は誤りでした。**
> `bello/mercari-api-token` という名前を読んでいるのはアプリではなく、
> **この計測ハーネス自身**でした(存在しない名前を私が書いていた)。
> アプリが実際に読むのは `bello/mercari-access-token` で、すでに存在します。
> **Secretの新規作成は不要**です。詳細は docs/performance-phase2-20260904.md §F-1。

**5. StatusMaster が空(P3)**

在庫ステータスのマスタが0件です。

> **【2026-09-04 第2フェーズで原因判明】「データの投入が要ります」は誤りでした。**
> 原因は**登録画面が一度も作られていなかった**ことで、入れる手段が無かった
> だけです。設定画面に「状態」タブを追加しました。何を状態として持つかは
> 運用が決めることなので、データは1件も入れていません。
> 詳細は docs/performance-phase2-20260904.md §F-2。

### 今回やらなかったこと(意図的に)

- 機能を削る高速化はしていません(件数表示・検索・フィルタはすべて残っています)。
- 古いデータを見せて速く見せる形にはしていません。キャッシュはすべて
  **書き込み時の破棄**を配線したうえで、TTLを併用しています。
- 整合性を犠牲にした近似は入れていません。件数は実データで一致を検証済みです。
