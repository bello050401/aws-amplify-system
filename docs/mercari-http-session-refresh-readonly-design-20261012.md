# メルカリShops HTTPセッションの長期維持・更新: 読取限定の設計記録（2026-10-12）

この記録は保存済みHAR、同HARに含まれる画面ビルドの静的JavaScript、既存の非秘密ログインHAR要約を読み直した結果である。認証情報の値、Cookie、要求・応答本文は転記しない。新たなログイン、更新要求、商品書込、公開、未観測URLへの通信は行っていない。管理画面の内部通信は公開API契約ではなく、ビルド更新で変わり得る。

静的JSには少なくとも**二つの異なる認証状態の扱い**が見える。一方は `/auth/token/refresh` を呼んだ後に `Self` を読む分岐。もう一方は認証ライブラリの `refreshAccessToken()` と `Self` により、有効期限表示を更新する分岐である。後者のコードには `Authorization: Bearer` と `DPoP` を組み立てる補助関数もある。同じ利用者に両方を順番に適用する根拠はない。10分は画面コード内の事前更新判定値であり、Cookieの寿命でもBELLO側の更新間隔でもない。

## BELLO側の読取限定状態

既存の [`webHttpSessionLifecycle.ts`](../lib/listing/mercariBridge/webHttpSessionLifecycle.ts) は、店舗・BELLO本人・保存時刻と、判明した場合の期限に認証状態を結び付ける器だけを持つ。保存時と利用時に読取プローブを行い、`VALID` は読取準備、`EXPIRED` は再ログイン待ち、追加認証が確定した場合は本人対応待ち、通信障害や判定不能は `UNKNOWN` として停止する。いずれも書込許可を出さない。期限不明に架空の寿命を置かず、画面の10分判定や公式案内の180日を保存期限に流用しない。

既存の [`webHttpReadOnlyClient.ts`](../lib/listing/mercariBridge/webHttpReadOnlyClient.ts) は、一時的なIDP引渡し後に既知の読取を行う。毎回利用できる更新器ではなく、HAR中のトークンを長期保管する設計でもない。専用Secret保管口にも、本人の通常ログインを取得する本番アダプター、自然な更新を確認したプローブ、更新器は接続されていない。

将来、保存状態を使った読取を設計する際の判定境界は次の通り。

1. 読取の直前に、BELLO本人・対象店舗・既知の期限を照合する。期限切れ・401/403・追加認証の確定は停止し、本人による再ログインを求める。
2. `Self` 等の既知の読取が成功しても、対象店舗を同じ認証状態で再確認する。結果が不完全、リダイレクト、空HTML、GraphQLエラー、通信障害なら `UNKNOWN` として停止する。ログイン切れと推定して無断で更新しない。
3. 更新が必要になっても、実測済みの更新契約と提供元の利用条件が揃うまで、静的JSの候補URLや認証ライブラリをBELLOの送信処理に移植しない。HARのトークン、Cookie、チャレンジ値を再利用しない。
4. 仮に将来更新が確証された場合も、更新前後の本人・店舗一致を読取で検証し、期限・世代の競合を原子的に管理する。結果不明時に更新を繰り返さず、認証状態を秘密値なしの状態コードとして扱う。商品書込の条件は別途検証する。

## 追加で必要な観測

本人が通常画面を使う中で**自然に**更新が発生した場合に限り、更新前後のホスト・パス・方法・状態、リダイレクトの有無、Cookie/Set-Cookie・Authorization・DPoP・CSRFの存在と期限属性、`Self` と対象店舗の読取成否を非秘密のメタデータで記録する。要求本文、トークン、Cookie、個人識別子、認証コードは記録しない。発生しなければ「未観測」とする。期限を人為的に短縮したり、チャレンジやbot対策を再送して発生させない。HTTP専用の認証状態の保存・更新が提供元に許されるかも確認が必要である。

現時点の結論は、**一回のローカル読取は成立したが、長期維持・refreshの実通信と成功条件は未確認**。画像multipartの要求本文も未観測なので、認証更新器、画像送信器、商品書込器の実行経路はつながない。
