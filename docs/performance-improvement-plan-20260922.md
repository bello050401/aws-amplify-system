# BELLO 自社システム速度改善仕様書（2026-09-22）

## 目的と判定方法

対象は在庫一覧、商品詳細・編集、画像登録、EC出品、売上、メッセージ、設定の通常操作。最優先は「一覧の文字が出るまで」と「画面内の商品写真が見えるまで」。既存実運用データを変更せず、同一端末・同一ネットワーク・同一条件で改善前後を比較する。

測定値は初回/再訪、50件/100件、写真あり/なし、PC/モバイルを分け、各5回の中央値と最悪値を記録する。目標は、温まった認証済み一覧で文字の表示 p50 2秒以内、画面内画像の表示 p50 3秒以内、詳細の主画像表示 p50 2秒以内。これは**目標値**であり、現状の実測値ではない。画像転送量は一覧の可視10枚で合計1MB以下、原画像の先読み0件を目標にする。品質基準は画像順・トップ画像・傷写真・アクセス権・既存の編集機能を維持すること。

## 今回確認した現状

- 2026-09-22 の公開staging HTTP（未ログイン）: ログイン画面の温時TTFB 224ms、保護画面の認証リダイレクト 255〜265ms。これは在庫DBや画像転送を**含まない**下限値。
- ログイン済みの開いている在庫画面では5,389件、表示元は `index`、画像要素41件が読込済み、破損0件だった。この観察はロード完了後の状態であり所要時間ではない。
- `app/inventory/(protected)/page.tsx` は50/100件の在庫取得後、全行の Photo Registration トップ画像問い合わせを `await` してから一覧を描画する。`lib/photoRegistration/webAdapter.ts` は在庫ごとにバッチを検索し、該当バッチの画像一覧を読む。最大100件の並列問い合わせが初期描画の待ち時間に乗る。
- 従来画像には320pxのサムネイルと960pxの中画像があり、署名URLの認証ウォームアップ、同時実行制限、キャッシュ、画面外の遅延読込も実装済み。これらを置き換える前に効き具合を測る。
- 撮影画像の詳細は1枚あたりサムネイルと加工済み画像を署名する。今回この2件を並列化した。DBの読み取り回数は変わらないため、効果は署名処理の所要時間に限られる。
- 計測スクリプトは既定のAWSプロファイルでセッション失効となったが、既存の `Bello` プロファイルを明示して読取計測できた。DynamoDB直結の初回一覧は532ms（5問い合わせ）、商品詳細345ms（5問い合わせ）、EC詳細365ms（5問い合わせ）。2画面目の一覧は1,281ms（3問い合わせ）だが、同一計測内の比較用旧直列経路は346msであり、ばらつきが大きい。いずれもPhoto Registrationの代表画像問い合わせ、AppSync、ブラウザ画像取得は含まない。単発値を画面全体の速度として扱わない。

## 実装の順序と安全条件

1. **計測を先行**: ブラウザのPerformance記録では、HTML応答、React描画、画像URL署名、実画像転送を分ける。セッションや個人情報をログに保存しない。
2. **一覧の構造改善**: 初期描画に必要なのは在庫の文字情報と代表画像キーだけ。行ごとの Photo Registration 探索を同期経路から除く。理想は代表画像キーを在庫レコードに投影し、更新時に書き替える方式。既存データはバックフィルを一気に走らせず、読み取り時の段階的フォールバックか検証環境での小分け移行にする。DynamoDB構造変更が必要なら分離環境で試験する。
3. **画像の適正化**: 一覧は320px前後、詳細の主表示は960px前後、原本は拡大時のみ。撮影画像にも同等の派生画像を持たせる。無い旧画像は従来URLにフォールバックし、表示欠落を避ける。見える画像から優先し、隠れたPC/モバイル側で重複取得しないことを確認する。
4. **認証・キャッシュ**: 署名URLは認証資格情報の期限を超えて再利用しない。画像そのものは不変キーなら長期キャッシュ可能。共有や公開設定の変更で速さを作らない。
5. **回帰確認**: トップ画像変更、撮影画像と商品画像の一致、傷写真選択、在庫一覧への戻り、検索・ページ切替、権限切替、期限切れURL後の再取得を対象にする。
