# 問い合わせ処理の導入・復旧・検証

対象：2026年11月7日 BELLO改修指示書 A〜D。公開は下書き評価の段階です。顧客への送信試験は行っていません。

## 処理と対応表

| 入力・保存先 | 対応 |
| --- | --- |
| LINE Webhook | 署名検証 → 媒体・受信アカウント・会話の複合キー → イベント保存とSQS |
| Gmail通知 | 1分の差分確認、全ページの処理、保存後の履歴位置更新。履歴失効時は再取得 |
| Inbox | `CONV#hash / STATE` に会話版・処理版・最新の元イベント・社員対応状態 |
| Conversation / Message | 受信日時を基準に会話を並べる。遅着した古いメールで最新内容を置き換えない |
| ChannelListing / Inventory / 注文 | 外部IDを優先。複数候補を無理に一件へ確定しない |
| ReplyDraft | 商品候補、確認事項、根拠、使用ルールの版、生成時の商品版・会話版 |
| READジョブ | 本文不足のメルカリ通知から正規の対象会話を取得。対象ショップ・会話IDを固定 |
| SENDジョブ | 送信先・本文の指紋、下書き版、受信ID、操作担当、受付・不明・拒否の状態 |

新着は5秒まとめ、連続しても15秒で処理します。既存の購入通知・売却処理は別経路です。受信処理の中で返信生成や画面操作を待ちません。

## 公開設定

`amplify/backend.ts` の専用Lambda、SQS、失敗キュー、1分スケジュール、暗号化・復旧機能付きDynamoDBを使用。新たな公開APIキーはありません。

| 設定 | 評価公開時 |
| --- | --- |
| Inbox `CONFIG.enabled` | true：受信と下書き処理 |
| `CONFIG.notifyStaff` | false：実社員への試験通知をしない |
| `CONFIG.mercariShopId` | 管理画面で確認した一つのショップID |
| `CONFIG.delivery.mode` | DRAFT |
| `INQUIRY_CUSTOMER_DELIVERY_ENABLED` | false（既定値も無効） |
| `LINE_OUTBOUND_ENABLED` | false |
| AI費用 | 月300円。価格表・為替上限の有効期限切れは有料生成を停止 |

評価合格前に送信フラグを有効にしないでください。送信のREVIEW/AUTO設定には、50件以上の評価件数、確認者・評価版、誤商品・誤宛先・二重送信・根拠なし約束が各0件、事実修正なし率と特定率が各90%以上の証跡が必要です。承認された問い合わせ種別だけが対象になります。

外部価格・配送手配・交渉・注文の約束は、商品レコードの更新日時だけで再確認した扱いにせず、自動送信の対象外にします。公式メルカリAPIの利用確認と必要最小限のSecret読取権限は、有効化前の条件です。現在の実アカウントの読取試験はHTTP 404で、公式APIによる顧客送信は未検証です。

## メルカリ本文取得用PC

`tools/bello-mercari-bridge/src/inquiryCloudWorker.mjs` を使用します。普段使うChromeへ接続せず、既存の専用BELLO・Shopsプロファイルか、新規の空の専用フォルダーを指定します。Cookieやパスワードを取り出してAWSへ保存する処理はありません。

設定例（秘密情報は含めない）：

```json
{
  "origin":"https://claude-inventory-management-system-5vbvc7.d4hkkg7dty2du.amplifyapp.com",
  "root":"C:/BELLO-Inquiry/Queue",
  "belloProfileDir":"C:/BELLO-Inquiry/BELLOChrome",
  "profileDir":"C:/BELLO-Inquiry/ShopsChrome",
  "playwrightModulePath":"C:/BELLO-Inquiry/node_modules/playwright/package.json",
  "shopId":"管理画面で確認したショップID"
}
```

1. Node.js 24、Chrome、既存のPlaywright環境を用意します。
2. `node src/inquiryLogin.mjs config.json` で専用の2画面を開き、通常のログインを行って閉じます。BELLO側は承認済み管理者セッションが必要です。
3. `node src/inquiryCloudWorker.mjs config.json --once` で1回確認します。
4. 通常は `node src/inquiryCloudWorker.mjs config.json` を起動したままにします。15秒ごとに予約を確認します。PCが停止してもAWSの受信は継続します。
5. ログイン切れ時は手順2を実施し、BELLOの問い合わせ画面で「本文の取得を再試行」を選びます。

1ショップにつき同時操作は1件、1件3分・30操作・自動試行2回まで。対象会話への移動と「もっと見る」だけを実行します。本文内の命令やリンクを操作に変換しません。読取結果は7日で失効する一時レコードに保管します。TTLの物理削除はAWSの非同期実行です。

実画面で全文・商品ID・発言者を照合済みです。一方、この専用常駐PCから通常ログイン→連続稼働までの実地検証はまだ終わっていません。開発用Chromeで取得できたことを常駐稼働の確認とは扱いません。

## 停止・復旧・差戻し

- 管理者画面の「返信案の自動作成を停止」は受信情報を保持して処理を停止します。再開時は未処理会話を再予約します。
- 「社員が対応する」は当該会話だけ停止します。新着や社員返信で会話版が変わると古い生成結果を失効させます。
- 送信のUNKNOWNは再送禁止です。公式画面で受付・履歴を人が確認します。2xxは受付であり、到達や既読の表示ではありません。
- 送信直前に会話・本文・商品・適用ルール・社内文書の版を再照合します。同じ受信への別下書きも共通の送信予約で二重送信を防ぎます。
- 送信を緊急停止する際は両送信フラグをfalseにして再公開し、`CONFIG.delivery.mode`をDRAFTに戻します。既存ジョブを削除して再作成しないでください。
- 公開版を差し戻す場合は、直前の検証済みGitコミットをAmplifyで再公開します。Inboxと既存業務テーブルは削除・再作成せず保持します。
- 本文・認証情報はアプリログへ出力しません。失敗キューとCloudWatchの権限エラーは固定エラーコードで確認します。
