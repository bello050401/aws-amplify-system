# ZAICO 3-way マージ 追加監査

2026-09-02 / 全件同期を流す**前**に、実際に流したとき何が起きるかを潰す。

前提: 全件同期は未承認・未実行。ここは静的監査と純粋関数の検証だけで、
ZAICO APIも叩いていない。件数はStagingのDynamoDBを直接数えた値。

---

## 直したもの

### 1. 履歴が「守った項目」まで変更したことにしていた（High）

`zaicoSyncEngine` は履歴用の差分を**マージの前**に、ZAICOとBELLOの生の
差分から作り、マージが「人の編集を守るので書き込まない」と決めた**後**に、
その生の差分をそのまま履歴へ書いていた。

人が「発送完了 → 補修待ち」へ戻した判断を正しく守れている場合でも、
履歴には次のように残る。

```
ステータス: 補修待ち → 発送完了（ZAICO同期）
```

これは実際に起きた差し戻し事故と**同じ見え方**になる。そしてこの履歴は、
その事故を突き止めるのに使った証跡そのもの。

```
2026-08-30T12:48 [人]   inv=3026f919 "発送完了" → "補修待ち"
2026-08-30T13:30 [同期] inv=3026f919           → "発送完了（ZAICO同期）"
```

嘘が混じると、次に何かあったときに追えなくなる。それ以上に「対策したのに
直っていない」と誤らせる。マージ後に `merge.updates` / `extendedFields` /
`customFields` から組み立て直した。

### 2. 据え置きの分類が理由の日本語文への文字列一致だった（Medium）

```ts
if (decision.reason.includes("人が変更") || decision.reason.includes("BELLO側に値がある") || ...)
```

文面を少し直しただけで分類が静かに外れ、人の編集を守ってはいるが**報告に
載らない**という、一番気づきにくい壊れ方をする。`KeepKind` を値として持たせた。

| KeepKind | 意味 | 報告する |
|---|---|---|
| `ZAICO_EMPTY` | ZAICO側が空。空で既存値を消さない | しない |
| `SAME_VALUE` | 値が同じ。書き込む必要が無い | しない |
| `HUMAN_EDIT` | 人が編集した値を守った | **する** |
| `ALREADY_FILLED` | BELLO側に値があるので補完しなかった | **する** |
| `NO_SNAPSHOT` | 前回値が無く、人の編集か判断できない | **する** |

「ZAICOが空」「同値」を報告しないのは既存の意図のまま。毎回出ると本当に
見るべき1件が埋もれる。

### 3. 数値と数字文字列を別物として比べていた（Low・現時点では未発現）

`valuesEqual` は `String()` で正規化していたので `2` と `"2.0"` が「違う」。
ZAICOは数量をこの形の文字列で返す。

片方が実際の数値で、もう片方が数値に読める文字列のときだけ数として比べる
ようにした。**両方が文字列なら数として比べない** —— `"007"` と `"7"` は
別物でありうる（バーコード・型番）。

現時点では発現していない。数量は `parseZaicoQuantity` が数値へ直してから
マージへ渡す。寸法はBELLO側も `a.string()` でZAICOも文字列なので文字列同士の
比較になる（実データ: `width "38"` / `height "83 アーム高さ66"`）。

## 未解決 — 承認前に決めておきたいこと

### スナップショットがまだ1件も無い

```
Inventory 全 5,313件
  zaicoSnapshotJson を持つ    0件   ← 3-way判定の基準がどこにも無い
  categoryId を持つ       5,312件   （HUMAN_WINS）
  customFields を持つ     1,324件   （HUMAN_WINS）
  adminMemo を持つ          606件   （HUMAN_WINS）
```

3-wayマージは「前回ZAICOが渡した値」を基準に、人が触ったかどうかを判定する。
その基準がまだどこにも無い。

初回同期でZAICOとBELLOが食い違う人優先項目は、すべて `NO_SNAPSHOT` として
据え置かれ、報告に載る。ここまでは設計どおり（人の値を消さない側へ倒す）。

問題はその次。初回同期はスナップショットにZAICOの値を記録するので、

```
2回目以降:  BELLOの値 ≠ スナップショット（=ZAICOの値）
         →  「人が変更している」と判定
         →  据え置き ＋ 毎回警告
```

となり、**その食い違いが人の編集だったのか、単に初回時点でズレていただけ
なのかに関わらず、永久に据え置かれて毎回警告が出る**。

#### なぜ勝手に直さなかったか

直す方法は「据え置いた項目のスナップショットには、ZAICOの値ではなく
BELLOの現在値を記録する」。そうすれば2回目に「人は触っていない」と判定され、
ZAICOの値が入る。

しかしそれは、**本当に人が編集していた値をZAICOで上書きする**という意味に
なる。ご指示の最優先事項（人が入力・修正した値を意図せず同期で上書きしない）
と正面からぶつかる。どちらを取るかは実装judgementではなく運用の判断なので、
勝手に決めない。

#### 選べる案

| 案 | 初回同期の挙動 | 2回目以降 | risk |
|---|---|---|---|
| A. 現状のまま | 食い違いは全部据え置き | 永久に据え置き＋毎回警告 | 人の値は絶対に安全。ZAICOの更新が永久に入らない項目が残る |
| B. 据え置き項目はBELLO値をスナップショットへ | 同上 | 2回目にZAICOの値が入る | 人の編集が2回目に消える |
| C. 初回だけ「基準作り」として実行 | 何も書かず、スナップショットだけ作る | 以降は正しく3-wayが効く | 初回時点の食い違いは人が確認する必要がある |

**Cを勧める。** 初回は書き込みゼロでスナップショットだけを作り、そのときの
食い違い一覧を人が見て決める。以降は3-wayが本来の意味で働く。初回の食い違いを
人が1度だけ確認する手間と引き換えに、AでもBでも避けられない誤りを両方避けられる。

いずれにせよ**実装前に承認が要る**ので、ここには書くだけにしてある。
