# Yahoo!オークションの売却通知

既存のGmail読み取り専用接続と5分間隔の購入通知取得を使用する。受信による在庫変更、売却確定、EC操作、メール送信は行わない。

## 取得・統合

- 実メールで確認した `auction-master@mail.yahoo.co.jp` の出品者向け通知のみ処理。
- 「即決価格での落札」「終了（落札者あり）」は落札、「お届け先住所確定」は住所確定、「支払いが完了しました。商品を発送してください」は発送待ち。
- オークションIDごとに候補を1件に統合。本文・件名・商品URLのIDが矛盾する通知は取り込まない。
- 新しい通知で状態が進む。逆順で届いた通知でも後退せず、不足していた落札価格を補完する。「残り数量」は売却数量に使用しない。明示された落札数量がない場合は売却画面で数量の入力を求める。
- 通知の重複はメールIDと候補IDの両方で防止。売却済みの結果を保持して状況のみ更新し、削除済みの候補は復活させない。
- 保存は状態・更新版を条件に実行し、売却確定や削除との競合は再読み込みして処理。保存に失敗したメールは取得済みにせず再試行する。
- 保存対象は商品名、価格、オークションID、数量、段階別の通知日時など。メール本文、件名、落札者・住所は保存しない。

## 商品照合・画面

従来のYahoo出品台帳、eコンビニ出品結果、人が承認したeコンビニ紐付けをローカルデータから照合する。外部サービスの出品を照合時に操作しない。IDが一意でも、人が写真・在庫IDを確認して選択する。一意でない、または対象在庫が無効な場合は商品名検索を使う。PCとiPhoneは同じ売却管理部品を使用する。

取引状況（落札・住所確定・発送待ち）とBELLOでの売却状態（未処理・処理済み）を別々に表示。従来の売却確認と、売れたチャネルを除外するEC変更確認を維持。

## 検証

以下のスクリプトはテスト用データを使い、外部ECや本番在庫を変更しない。

```
node --import tsx scripts/verify-yahoo-sale-mail.ts
node --import tsx scripts/verify-sale-candidates.ts
node --import tsx scripts/verify-sale-workflow.ts
node scripts/qa/run-verify-with-server-only-noop.cjs scripts/verify-sold-out.ts
node scripts/qa/run-verify-with-server-only-noop.cjs scripts/verify-stock-split.ts
```

2026-10-27: 上記63テスト合格。Yahooの4通を全24通りの到着順で検証。重複、価格欠落、金額不一致、売却・削除との競合、保存失敗からの再取得を含む。実メール4通でも1候補・発送待ち・落札価格の保持を読み取り検証済み。PCの実ブラウザーで検索、確認、テスト保存を操作し、5点→売却2点・残り3点、保存1回を確認。390px幅でも表示確認。

## 公開・復旧

新規テーブル・バケット・スケジュール・認証情報は追加しない。既存購入通知Lambdaとフロントエンドを更新し、Web実行ロールの読み取り対象にYahooAuctionListingのScanだけを追加する。

公開前に売却候補テーブルのオンデマンドバックアップ `before-yahoo-mail-20261027` を作成し AVAILABLE を確認。通常のロールバックは本変更のコミットをrevertして再デプロイする。旧版でも既存候補を保持できる。バックアップ復元は新テーブルへ行い、差分確認後に必要なレコードのみ復旧する。全件の無条件上書きは行わない。

任意のメール形式、落札キャンセルや発送完了の自動判別は今回の対象外。後続通知だけ届いた取引は価格・数量を確認して入力する。実際のiPhone本体操作と実商品の売却確定はテスト実施済みとは扱わない。
