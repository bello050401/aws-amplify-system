# BELLO 性能報告書（2026-09-04 時点）

すべて Staging（us-west-2 / 在庫5,329件）の実測です。**推測値は含みません。**

## 測定条件と、その読み方

実行はこのノートPC（日本）から。**往復1回あたり約160ms** が改善前後どちらにも同じだけ
乗っています。本番（同一リージョンのLambda）ではこの待ちがずっと小さいので、
**絶対値は上振れした値**として読んでください。比率のほうが実態に近い値です。

測っているもの: DynamoDB の Query / Scan / GetItem、Secrets Manager、往復回数、転送量。
**測っていないもの**: AppSync の解決処理、Amplify SSR の起動、Reactの描画。
Stagingへブラウザでログインする資格情報がこの環境に無いため、画面のTTFB（それらを含む値）は
取得できていません。推測での穴埋めはしていません。

## 1. 改善前後（同一条件・同一データ）

### 1.1 在庫検索 — 12〜25倍

| | 時間 | 直列段数 | 読取 | 転送量 |
|---|---|---|---|---|
| 改善前（全列を全件走査） | 13,799〜19,364ms | 14段 | 5,329件 | 11.83MB |
| **改善後** クイック検索（該当なし） | **540〜877ms** | 2段 | 5,329件 | **1.95MB** |
| **改善後** 一覧の絞り込みのみ | **604〜1,042ms** | 2段 | 5,329件 | 1.95MB |
| **改善後** クイック検索（324件ヒット） | **1,239〜2,992ms** | 2段 | 5,329件 | 1.95MB |
| **改善後** 詳細検索（商品名 contains） | **1,196〜1,363ms** | 2段 | 5,329件 | 1.95MB |
| **改善後** 詳細検索（2条件 AND） | **1,191〜1,195ms** | 2段 | 5,329件 | 1.95MB |

やったこと: 検索を2段に分けた。
第1段は「その検索が実際に参照する列だけ」を `ProjectionExpression` で読み、Scanを8セグメントに並列分割。
第2段は絞り込み後の**表示50件だけ**を `GetItem` で全列取得。
判定・並び順・件数は従来とまったく同じ関数を通しているので、**検索仕様は1文字も変えていません**。

新旧の結果が一致することは `npm run verify:inventory-search-fast` が実データ46通りで
（総件数・ページのID・順序・行の中身が1属性も違わないこと）照合しています。

### 1.2 総件数の集計 — 20〜47倍

| | 時間 | 転送量 | 結果 |
|---|---|---|---|
| 当初（行を読んで数える） | 16,300ms | 11.83MB | 5,329 |
| 第1フェーズ（`Select:COUNT`・GSI・直列） | 3,727ms | 0MB | 5,329 |
| **現在**（`Select:COUNT`・Scan・並列8） | **345〜715ms** | **0MB** | 5,329 |

COUNTは1MB走査ごとに返るので往復回数は減らせません。減らせるのは「直列に何段待つか」で、
そこはセグメント分割で下がります。GSIへのQueryは分割できないためScanに変えました。
数える対象は同じで、`verify:inventory-count` が実データで新旧の一致を確かめています。

## 2. コールドスタート（実測）

CloudFrontを素通りさせるためクエリを毎回変えて計測しました。

| 状況 | 1発目 | 直後の2発目 | 差（＝コールド増分） |
|---|---|---|---|
| 連続アクセス（ウォーム） | 382〜533ms | — | — |
| **5分アイドル後** | 578ms | 334ms | +244ms（通常のばらつき。**まだウォーム**） |
| **10分アイドル後** | **2,465ms** | 483ms | **+1,982ms（コールド）** |

**ウォームからコールドに落ちる境目は5分超〜10分以内。** 増分は約2秒です。

判断: **定期ウォームアップは導入していません。** 確実に効かせるなら5分間隔＝月約8,640回の
追加SSRリクエストが常時必要で、1日数回・約2秒のために24時間回すのは割に合わないと考えます。
入れるとしても営業時間帯だけに絞るのが妥当で、その判断はご本人にお願いします。

## 3. 今回の健全化で性能に影響した変更

| 変更 | 性能への影響 |
|---|---|
| 外部fetchに15秒のタイムアウト | 正常時は影響なし。異常時に**待ち続けなくなる**（従来は実行上限まで居座った） |
| マスタ・特集の取得をページング化 | 現在の件数では往復1回のまま。100件を超えると往復が増えるが、それは切り捨てが起きないことの対価 |
| 件数キャッシュの無効化を全経路へ | 取込・同期の直後に1回だけ再集計が走る（345〜715ms） |
| メッセージ・通知の条件付き書き込み | 往復数は不変。条件が付くだけ |

## 6. 実ブラウザからの計測（2026-09-04 追記）

これまでの数値はすべて DynamoDB / AppSync 区間でした。実ブラウザ（Chromium）で
「クリックしてから操作できるまで」を測り直し、**全画面に効く問題を1つ見つけて直しました**。

| 画面 | 項目 | Before | After |
|---|---|---:|---:|
| ログイン画面 | リクエスト数 | 375本 | **17本** |
| | 転送量 | 4,780KB | **657KB** |
| | 初回描画 (FCP) | 536ms | **272ms** |
| 管理ログイン | リクエスト数 | 374本 | **16本** |
| | 転送量 | 4,125KB | **2KB** |

原因は日本語書体の全サブセット先読み（font の preload リンクが353本）。
ルートレイアウトにあるため全画面で毎回起きていました。`preload: false` の1行で解消。

Cold の実測も更新しました。**その日の最初のアクセスは操作できるまで約5.4秒**
（Warm は約1.1秒）。SSRのコールドスタートぶんは約3,750msで、以前 `fetch` で測った
+1,982ms（リダイレクトのみの経路）より重いことが分かりました。

詳細と、ログインが要る画面を測れていない理由は `BROWSER_PERFORMANCE.md` を参照。
