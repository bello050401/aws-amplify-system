# メルカリShops通常ログイン状態のWeb側管理（2026-10-09）

本人の確定方針は、ログインから商品・画像処理までHTTP通信だけで行い、その認証状態を安全に保管すること。認証が実際に切れた場合だけ再ログインを求める。PC・クラウドブラウザー方式、Public APIトークン方式には切り替えない。

## この差分で実装したもの

`webHttpSessionLifecycle.ts` はサーバー専用の状態管理である。将来の**本人操作を伴う信頼済みログイン取得器**から、店舗・Cognito本人sub・固定セッションID・認証時刻・不透明な認証状態・判明している期限を受け取る。保存前に同じ認証状態で読取プローブが `VALID` を返した場合だけ保存する。認証状態そのもの、プローブの応答本文、例外文は戻り値にもログにも出さない。取得器や読取プローブの実Shops実装はまだ存在しない。

後続の利用時は毎回保存内容を読み、本人・店舗・形式・判明している期限を確認し、読取プローブを再実行する。期限が不明なら任意の固定寿命を置かず、読取で有効性を判断する。`EXPIRED` または判明している期限切れは `AUTH_REQUIRED` として再ログイン待ちにする。通信障害等の `UNKNOWN` は `AUTH_UNVERIFIED` として停止し、認証切れとは決め付けない。どの結果も `allowHttpWrite=false` で、送信許可を返さない。

`webHttpSessionSecretStore.ts` は**事前に用意された専用Secret ARN**に対する `GetSecretValue` / `PutSecretValue` のみを実装する。旧Public API用の `bello/mercari-access-token` は利用しない。`CreateSecret`、実AWS呼出し、Secret作成、IAM変更は今回行っていない。Secrets Managerは保存値を暗号化し、更新時に新しいバージョンを作る。[AWSの暗号化仕様](https://docs.aws.amazon.com/secretsmanager/latest/userguide/security-encryption.html)、[バージョン仕様](https://docs.aws.amazon.com/secretsmanager/latest/userguide/manage_update-secret-value.html)を参照。

## 実送信までの未実証条件

1. 本人が必要なSMS認証を行えるHTTP専用のShops通常ログイン取得器。ログイン・SMS・更新の実要求と応答契約、保存サイズ、本人・店舗との結び付け、Shops側の利用許可は未実証。推測の送信先やパラメータは実装しない。パスワード・認証コード・Cookieを通常ログ、チャット、Gitへ出さない。
2. 保存した不透明状態を使って、既知の `GetProductDraft` を同じ実行環境から読み、`VALID` / `EXPIRED` / `ADDITIONAL_AUTH` / `UNKNOWN` を秘密非出力で判定する実プローブ。HTTP認証に必要なCookie以外の状態やCSRF条件はまだ不明。今回のモック結果を実認証の成功と扱わない。
3. 専用Secretの保管方法とIAM最小権限、旧バージョン保持・失効時の破棄、同時再ログインの扱い。Secretの既存有無・実IAMは今回確認していない。Secret作成やKMS設定には費用と運用判断が伴うため実施していない。
4. 実送信器は、保存済みという理由だけで動かさず、送信直前の最新認証確認、既存商品・下書き重複照合、店舗30秒枠の原子的予約、結果不明時の再送停止が必要。下書き作成の二重成功は[HAR証拠](mercari-b005396-http-draft-har-evidence-20261009.md)で確認済み。画像アップロード要求本文も未観測。

今回の検証はモックの認証状態・Secretクライアントのみ。Shopsログイン、秘密の抽出・表示、HTTP実読取・書込、AWS資源作成、公開は行っていない。既存EC出品、BASE、Next Engineには変更を加えていない。

## 読取結果と出品判定の接続

`webHttpReadiness.ts` は保存済みセッションで既知のB005396下書き2件を読み、同じ認証コンテキストから対象商品の新鮮な重複照合・既存紐付け・書込契約・店舗全体の送信履歴を取得するための方式中立の接続点である。B005396自身は下書きが既に2件あるため常に新規作成不可とする。HTTP 401、信頼済み取得器が検出した追加認証、応答不明、対象証拠の欠落・期限切れは停止する。認証切れまたは追加認証が確認された場合だけ再ログインを求める。

`READY_FOR_RESERVATION` はモックで確認した純粋な判定結果で、`allowHttpWrite` は常に `false`。実際のHTTP専用ログイン取得器、認証済みHTTP転送、対象商品の網羅的な重複照合、画像処理、原子的な送信予約と送信器は未実装。実Shops読取・書込やAWS変更は行っていない。

認証ポートは既に `VALID`、`EXPIRED`、`ADDITIONAL_AUTH`、`UNKNOWN` を区別し、追加認証が確認された場合は保存・送信せず本人の再認証を待つ。今回、この状態の回帰テストを追加した。Shopsの実レスポンスをどの状態へ分類するかは観測できていないため、実HTTP認証器、セッション更新処理、推測のURL・ヘッダー・パラメータは追加しない。

次に必要な最小証拠は、本人が選ぶショップアカウント種別での**正常なログインとSMS認証1回**について、通信の順序、送信先のホスト・パス、HTTP方法・状態、リダイレクト先のホスト・パス、要求・応答の項目名と型、Cookie/Set-Cookie等の有無と期限属性だけを残した局所的な記録である。更新通信については実際に発生した場合の同じメタデータを別に記録し、発生しなければ「未観測」とする。取得前にShops提供元からHTTP専用ログインの利用可否と仕様を確認する。本人が公式の通常ログイン操作から一度だけ受動的に通信を記録する場合も、原本は端末外へ出さず、ローカルでパスワード・SMSコード・Cookie/Set-Cookieの値、Authorization、CSRF値、本文値、メール・電話番号を除去し、非秘密の構造情報だけを共有する。原本や秘密値をチャット、通常ログ、Git、BELLO画面に貼らない。これらの証拠が得られるまで認証済みHTTP読取と出品は起動しない。

そのローカル要約の準備として `node scripts/summarize-mercari-login-har.mjs <local-har-path>` を用意した。元HARは読み取るだけで、別ファイルやネットワークへ送らない。標準出力はMercari系HTTPS通信の順序、固定語彙に限定したホストとパス、方法、状態、Content-Typeの種類、許可したヘッダー名、確認済みGraphQL操作名だけ。URLのクエリ値、可変パス、未知の操作名、ヘッダー値、要求・応答本文は出さない。未知の操作名は `REDACTED` となるため、この要約だけでHTTPログイン契約は確定しない。100 MiB超の入力は拒否し、出力は先頭1,000件までと件数・切り詰めフラグに制限する。実HARの再読込やログイン・通信の自動操作はまだ行っていない。
