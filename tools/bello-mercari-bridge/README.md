# BELLO Mercari Shops local read bridge (preparation)

This independent PC module queues **read-only checks for an existing product ID** on one shop account. Its optional pinned local proof action can also press the observed **private save** control once for one existing product without editing fields. It has no new-product, public, stop, or image upload method. The ADMIN-authenticated BELLO HTTPS GET/POST bridge has accepted signed-in PC read reports on staging. Plain `run-read` records `CONNECTOR_NOT_CONFIGURED`. The opt-in `--browser-read yes` reader reads the exact edit screen and can correlate one observed private list row back to the same product ID. Image identity remains unobserved; quantity is read only under the exact single-variant DOM contract below.

Node.js 24 or newer is required because the worker imports the shared TypeScript comparison function directly. No package installation is needed for queue tests; the optional visible browser launcher needs an existing Playwright installation and Chrome.

The known B005795 proof product must be reused. Do not enqueue a new-product operation. The queue root stores one non-secret account binding, immutable read requests, and sanitized result codes/comparisons. The first account binds the root; another account is rejected. A failed read becomes `UNKNOWN`, an expired session becomes `AUTH_REQUIRED`, and both preserve the same remote ID. Runs are explicit and read-only; there is no automatic retry. The worker accepts only an exact-product observation with both account and remote ID matching before it promotes field or private-state observations.

## One-time separate login

The current Codex in-app browser session is not attached to this module. For a future reviewed reader, the merchant can open a **separate dedicated Chrome profile** using:

```powershell
node src/cli.mjs open-login --profile "C:\Users\win\AppData\Local\BELLO\MercariBridge\ChromeProfile" --playwright "C:\path\to\node_modules\playwright\package.json"
```

The merchant logs in in the visible official Shops window and closes it when finished. The module does not extract cookies, copy the in-app browser session, handle the password, or send login data to BELLO. Chrome itself may retain the new browser session in this local profile; protect that Windows profile accordingly. This command prepares an independent session only. It does not make a Shops reader available or prove that automation is permitted.
The launcher creates a marker in an empty profile directory and refuses a non-empty unmarked directory, so an existing Chrome or in-app browser profile cannot be attached accidentally.

After that login, `open-existing` can reopen the **same** dedicated profile and navigate only to the observed exact-ID edit path. It binds `--root` to `--shop` and rejects a different shop later. It reports `AUTH_REQUIRED` for a sign-in redirect or `NAVIGATED_UNVERIFIED` for an exact URL; neither is a field or privacy confirmation. Close the browser after inspection. Its arguments are `--root`, `--profile`, `--playwright`, `--shop`, and `--remote`. No selector or form action is implemented.

```powershell
node src/cli.mjs open-existing --root "C:\Users\win\AppData\Local\BELLO\MercariBridge\Queue" --profile "C:\Users\win\AppData\Local\BELLO\MercariBridge\ChromeProfile" --playwright "C:\path\to\node_modules\playwright\package.json" --shop "<observed-shop-id>" --remote "<existing-product-id>"
```

## Queue contract

`enqueueExistingRead(root, { accountReference, inventoryCode, remoteId, expectedFields })` stores a `READ_EXISTING` job. `runExistingRead(root, accountReference, jobId, reader)` calls the injected reader at most once for the exact ID and stores only comparison outcomes. A reader may return `{kind: "AUTH_REQUIRED"}` or `{kind: "OBSERVED", observation}`; the latter must identify the exact account and product. An absent/failed reader is never treated as success. A crashed lock remains for manual inspection, with no automatic replay.

The observed UI edit path is `/seller/shops/{shopId}/products/{productId}/edit`. The edit screen alone has no non-public label. To check privacy, the reader uses the title observed on that exact edit screen to find one row in the observed filtered product list. The `商品名` header covers an image cell; the immediately following blank header covers the title-text cell. The reader requires the image alt and the single title paragraph to match the edit title, verifies `非公開` in the column headed `公開設定`, clicks the title-text cell, and requires navigation back to the exact shop and product ID. It requires the observed native table shape with ten unspanned header and body cells; absent or ambiguous evidence stays unobserved. The list image alt is only a row-correlation check, not primary-image identity. The dedicated profile can observe response metadata from its normal product visits; it does not issue hidden API requests or capture response bodies. Image identity remains unobserved.

The partial browser reader checks the observed 商品管理 heading and 公開設定に進む button, then reads fields whose parent label uniquely names 商品名, 商品の説明, 商品管理コード, or 販売価格. Duplicate or missing labels leave the field unobserved. It checks both the field extraction document URL and the final browser URL; a redirect discards the fields. It never clicks a save control. Quantity is read only when exactly one `variants.*.quantity` input is present, its exact name is `variants.0.quantity`, its type is `number`, and its direct parent contains exactly one input and one label `数量`. The separate `maxQuantityPerOrder` field is never used as quantity. Multiple, absent, or malformed quantity fields remain unobserved. The private list-row correlation above has synthetic tests but still needs a signed-in PC acceptance read. Image identity remains unobserved.

Run isolated contract tests with `npm test` from this directory. No external network or browser is used by tests.

## Prepared BELLO connection (maintainer workflow, not merchant handoff)

The PC's BELLO login uses a **second dedicated Chrome profile**, separate from the Shops profile. The administrator signs in normally at BELLO's `/inventory/login`. Playwright's `browserContext.request` uses that same BELLO browser context's cookies for HTTPS requests to the pinned BELLO origin. No fixed device key, saved password, copied cookie, or Shops session is sent to BELLO. Redirects are not followed. The server requires the `ADMIN` group and the exact `requestedBy` owner on both the existing binding and read request before returning a small `READ_EXISTING` payload or accepting one sanitized result. The POST also requires exact same origin and a custom header. The isolated Next Engine app rejects this route.

The local commands prepared for a later managed PC launcher are `open-bello-login` (visible normal login, using `--bello-origin`, `--bello-profile`, `--playwright`) and `run-cloud-read` (one explicit existing-ID read, adding `--request`, `--root`, and optionally `--browser-read yes --shops-profile`). `run-cloud-read` first fetches one owned request, reads the exact existing Shops ID once, then reports only status/reason/comparison enums and its attempt ID. Without `--browser-read yes`, it reports `CONNECTOR_NOT_CONFIGURED`. The BELLO receipt always says `listingConfirmed: false`.

These are developer primitives. Do not ask the merchant to run a CLI. The visible PC launcher is `BELLOメルカリ照合.cmd`, installed with `Install-BelloMercariDesktop.ps1` by a maintainer. Installation pins one reviewed request ID and the staging BELLO origin in a non-secret local config, installs Playwright, and creates the desktop shortcut `BELLO メルカリ照合`. The person double-clicks that shortcut, signs in normally in separate visible Chrome profiles for BELLO and Shops, closes the login windows, then clicks one read button. The local control page listens only on `127.0.0.1` and checks same-origin form submissions. It never asks for a password or reads the Codex in-app browser session. A failed read stays failed; no automatic retry or listing action exists.

During that one exact-product read, the Shops browser can show an in-memory network summary on the local control page. It records only request method, a fixed-vocabulary path with variable segments replaced, response status and count for Shops `fetch`/`xhr` responses. It ignores query strings, headers and request/response bodies; the summary is neither written to normal logs nor sent to BELLO. This diagnostic view does not prove an API integration is available or permitted. No real signed-in traffic has yet been inspected.

The optional `manualObservation` local configuration pins one existing shop/product ID, SKU, expected price, and expected quantity. The PC page offers a single private-save proof button. It verifies the exact edit URL, title, SKU, price, quantity, and private list row before claiming a permanent local attempt marker; then it clicks only `公開設定に進む` and the exact `非公開で保存する` button. The marker is written before the first potentially mutating click. The real save request contract is not yet known, so the first live attempt remains `UNKNOWN` even if response metadata shows the existing private product. The app retains the visible Chrome window and observer after the click so it cannot cancel an in-flight save by navigating or closing the browser. The PC page can refresh the sanitized communication summary; closing the dedicated Chrome ends observation. The marker remains and the app never retries. This does not confirm a new listing. The app does not change a form field, publish, or create a product. Mutation observations stay in memory and display only ordered request methods, redacted destinations, allowlisted field names/types, auth-header presence flags, HTTP status, safe GraphQL operation/root field names, error presence and fixed category, existing product/shop ID match flags, and a known product status enum. No raw IDs other than the configured target, values, error messages, credentials, file contents, or raw bodies are displayed, stored, or sent to BELLO. The former manual observer remains available only before a save attempt. Synthetic tests cover this path; the new metadata fields have no live acceptance yet. See [the direct HTTP observation plan](../../docs/mercari-direct-http-observation-20261004.md).

The BELLO ADMIN result view checks the same `requestedBy` owner as the PC route and shows only bounded status and comparison codes. The underlying Amplify models use `ADMIN` group authorization, so this is an application-level owner check, not model-level isolation between ADMIN accounts. A separate schema authorization design is required if ADMIN-to-ADMIN data isolation is needed.

An optional `imageProof` configuration pins one prepared local JPEG path and SHA-256 for the existing private product. The PC page then offers one image-selection attempt. It checks the exact product fields and private list row, the observed original image and the single file-input shape; starts the sanitized network observer and writes a permanent marker before `setInputFiles`. A selection may send image bytes immediately, so an exception is `UNKNOWN` and never retried. The product save and public controls are never called. The dedicated Chrome stays open for inspection. See [image preparation and recovery limits](../../docs/mercari-existing-image-preparation-20261004.md).

The one-time image selection was subsequently tried on the exact existing product. The visible result was `UNKNOWN / FILE_SELECT_RETURNED`, and the sanitized observer saw a Shops GraphQL multipart response with `createImageAsset` and HTTP 200. The merchant later pressed the private-save control once. A separate signed-in browser session reloaded the exact product edit page and found two rendered uploaded images, so the two-image association survived a separate read. Image byte identity, the save-request contract, and the private state after that save remain unverified. The current installed process retains Chrome but has only a traffic-refresh control. This source now includes a separate read-only retained-page image check for a future run; it verifies the exact edit URL and pinned product fields, compares the original image path hash in memory, and returns only fixed visibility codes. It does not navigate, select another file, save, publish, or close Chrome. **Do not restart the live process merely to install it while the retained Chrome remains open.** See [the live image observation](../../docs/mercari-existing-image-live-observation-20261004.md).

A later opt-in `imageWorkflowEnabled: true` replaces the individual image and private-save proof buttons with one explicit image-add/private-save/readback action for a **fresh existing private product**. Durable, separate image-selection and private-save stage markers make a failed or unknown action non-retryable. Old image/save markers block the unified path, including B005795. Only a target-matched private update response plus a same-product two-image/private-list readback can confirm success; otherwise the browser stays open and the result remains unknown. The current installed process is unchanged. See [unified workflow and acceptance limits](../../docs/mercari-private-image-unified-workflow-20261004.md).

If one local read attempt was saved but BELLO did not receive it, a maintainer can set `recovery: { jobId, attemptId }` in the non-secret local `config.json` after checking the exact saved attempt. The launcher then offers 「前回の結果だけをBELLOへ再報告する」. That action fetches the same owned BELLO request, checks its shop, product, inventory code, and expected fields against the saved job, then posts only the existing sanitized result. It does not reopen Shops or create another read attempt. A failed boundary shows only a fixed phase, HTTP status, and allowlisted server code; no raw response, page content, cookie, or token is displayed.
