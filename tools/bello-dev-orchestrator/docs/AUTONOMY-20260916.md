# 自動運用パイプライン（2026-09-16）

## 今回の実装

主リポジトリへの6ad1bea統合後、既存135テストとWindows PowerShell 5.1の構文検査に成功。その後、以下を追加した。

1. **独立テスト**: 設定済みのコマンドをOrchestrator自身が専用worktreeで実行する。終了コード、制限時間、出力上限、ログ、試行番号、ソース内容の指紋、検証設定の指紋を記録する。報告に「成功」と書かれていても実測が失敗なら完了・stagingへ進めない。検証後の変更・別試行・手動審査でも古い結果を流用しない。
2. **Codex実装担当**: 設定画面からClaude/Codexを選択し、次のタスクから適用する。共通の報告契約と検証・審査を使う。Codexには専用worktree、workspace-write、ネットワーク無効、非対話、JSONスキーマを指定する。実行ファイル・モデル・制限時間は管理設定に置く。
3. **staging反映**: 独立検証と審査に合格した確定コミットを、指定のstagingブランチへfast-forwardで反映し、AWS Amplify RELEASEを起動する。AWSアカウント・アプリ・リポジトリ・DEVELOPMENTブランチ・自動ビルド無効を照合する。ジョブIDと対象コミットを保存し、再起動後は状態確認を再開する。起動応答の消失は再起動せず確認待ち、状態取得の一時エラーは再確認する。
4. **外部通知**: HTTPS webhookへJSONを送る。完了・失敗・要対応を永続送信待ちへ保存し、再試行・上限・手動再送・同じIdempotency-Keyを扱う。実装完了とstaging成功をpayloadのstaging項目で区別する。送信先URLとトークンは環境変数から読む。

## 運用開始前の設定

### 独立テスト

`verification.commands` は担当エージェントの報告から生成せず、管理者が信頼できる検証計画として設定する。file/args/cwd/timeoutSecondsで指定し、シェル文字列として実行しない。cwdはworktree内の相対パスのみ。

タスク用worktreeに依存パッケージが必要。既定の型検査には当該worktreeのnode_modulesが必要で、依存がない場合は成功にせず修正・要対応になる。依存の準備は実装担当の通常の作業に含まれるが、既存のlockfile問題をこの変更で解決したとは扱わない。

検証は独立した起動・記録であり、リポジトリ自身のテストが悪意なく十分であることまで証明するものではない。実行時環境変数からクラウド・API・通知の秘密値を除くが、一般のローカルテストはOSレベルの完全な隔離ではない。

### Codex

インストール済みCLIの `codex exec --help` で指定オプションを確認した。モデル呼び出しを伴う実Codexタスクは未実行。CLI認証は既存のログインを使用し、APIキーをリポジトリのテストへ渡さない。ユーザー設定の広い権限が継承されないよう `--ignore-user-config` と制限を明示している。CLI固有の起動は試験用実行処理で契約を検証し、実モデル・AWS・外部送信は代替処理で試験した。

公式仕様: [Codex非対話実行](https://learn.chatgpt.com/docs/non-interactive-mode)。

### staging

管理設定stagingに、accountId/appId/branch/region/profile/repositoryを指定し、専用データの確認後にisolatedDataConfirmedを設定する。ブランチはstaging/stage/preview系に限定する。自動ビルドを本機能が勝手に変更することはない。

**現行BELLOのamplify.ymlはbackendのpipeline-deployを含む。現在の状態では自動反映を停止する。** 別の安全なfrontend専用反映構成、または具体的なバックエンド変更の承認・検証が必要。承認なしにIAM/S3/Cognito等の重大変更を行うための迂回設定は追加していない。

インフラ・migration・amplify.ymlの変更はゲートで止める。リモートstagingブランチとの差分にも同じチェックを行う。通常のGit操作は引き続きpushを拒否し、staging専用関数のみ厳密な対象とfast-forwardを許可する。force push・本番ブランチへのpushは実装していない。

AWSの成功ジョブとコミット一致までを確認する。公開後の実画面E2Eや本番データへの影響がないことを、このローカル試験で検証済みとは扱わない。

公式API: [Amplify start-job](https://docs.aws.amazon.com/cli/latest/reference/amplify/start-job.html)、[get-branch](https://docs.aws.amazon.com/cli/latest/reference/amplify/get-branch.html)。

### 通知

- BELLO_NOTIFICATION_WEBHOOK_URL: 送信先HTTPS URL（設定ファイルには値を置かない）。
- BELLO_NOTIFICATION_TOKEN: 任意のBearer token。
- payload: eventId, taskId, title, state, at, reason, staging。
- redirectは追従せず、URLを含み得る通信例外を保存しない。
- 受信側もIdempotency-Keyで重複を排除すること。応答消失時の完全な一回送信はHTTPだけでは保証できない。
- 初回導入以前の履歴は送信対象外。導入後は無効設定中も将来の再送に備えてイベントを記録する。

## 保存・復旧

既存テーブルの削除・列変更は行わず、staging_deliveriesとnotification_outboxを追加する。verificationは既存checkpointsに保存する。staging待機中はdelivering状態で、完了するまで依存タスクは開始しない。タスク詳細で実測テストとstaging状況、設定画面で通知失敗数を確認できる。
