# ZAICO同期 Baseline / Before-After Performance Report (2026-08-30)

## 計測方法について(正直に)

このサンドボックスには実ZAICO API・実AWS(DynamoDB)アクセスが無い(第三ラウンド報告の根本原因 — `AWS_ACCESS_KEY_ID`/`ANTHROPIC_API_KEY`が機能しない、を参照)。そのため本レポートの数値は、**実際の同期ロジック(`lib/inventory/zaicoSync.ts`の`syncOneZaicoItem` — 本番と全く同じコード、ベンチマーク専用の複製は一切書いていない)を、実DynamoDB/S3の代わりに「操作種別ごとの遅延モデル」を持つin-memory mock port経由で駆動した、シミュレーション値**である。

遅延モデル(`scripts/benchmark-zaico-sync.ts`の`SIM`定数):
- DB操作(GetItem/PutItem/UpdateItem)1回の基礎コスト: 4ms
- DynamoDB Scanが実際に読み取った1行あたりの追加コスト: 0.02ms
- 画像ダウンロード+アップロード+thumbnail生成: 140ms
- チェックポイント(ZaicoSyncJob.update)1回: 6ms

これらは実測DynamoDB/S3の値ではなく、一般に公開されている特性(GetItem/PutItemはO(1)、ScanはRCU消費が読み取り件数に比例して増える)を根拠にした仮定値。**絶対的なミリ秒値の精度を主張するものではなく、「アルゴリズムが件数に対してどうスケールするか」(O(N²)的か O(N)的か)を実証するための計測**である。AWS認証が復旧し次第、同じベンチマーク構造をStaging実測(CloudWatch/DynamoDB)に置き換えて再測定する。

再現: `npm run benchmark:zaico-sync -- --before` / `npm run benchmark:zaico-sync -- --fixed`

## 発見した根本原因(baseline計測前のコード監査で確定)

`lib/inventory/zaicoBackgroundSync.ts`の`advanceZaicoBackgroundSyncJob`(実際にブラウザの設定画面が繰り返し呼んでいる、現行のZAICO一括同期の実処理経路)が、`syncOneZaicoItem`へ`prefetched`引数を渡さず`undefined`のまま呼んでいた。

- `syncOneZaicoItem`は`prefetched`が無いと、商品1件ごとに`port.findExistingBySourceId`を呼ぶ。
- 実装(`zaicoSyncPorts.ts`)のこの関数は`serverDataClient.models.Inventory.list({filter:{...}})` — `Inventory`モデルに`sourceInventoryId`のGSIが無いため、これはAmplify Data上ではDynamoDB **Scan**(FilterExpression付き)になる。
- つまり1000件の同期では、変更が無い商品も含め**1000回、Inventoryテーブル全件をScanし続けていた**。
- 同じ理由で`findOrCreateCategory`/`findOrCreateLocation`(`lib/inventory/masters.ts`の`findOrCreateMasterEntryByName`)も商品1件ごとにCategory/Locationマスタ全件を取得し直しており、二重のN+1になっていた。

対照的に、より古い(タイムアウト問題のため実質使われなくなっていた)`syncAllZaicoItems`は`port.fetchAllZaicoManaged()`を1回prefetchして正しく使っていた — **後発の`advanceZaicoBackgroundSyncJob`実装時にこの最適化が失われていた、確認済みのregression**。マスタのN+1は両経路とも未対策だった。

## 修正内容

1. `advanceZaicoBackgroundSyncJob`: 1ページ(50件)ごとに`port.fetchAllZaicoManaged()`を1回prefetchし、そのMapを`syncOneZaicoItem`へ渡す(`syncAllZaicoItems`と同じパターン)。
2. `syncOneZaicoItem`に新しい任意引数`masterCache`を追加。Category/Location名 → id のin-memory cache。cache missの時だけ`port.findOrCreateCategory`/`findOrCreateLocation`を呼び、結果をcacheへ書き戻す。`advanceZaicoBackgroundSyncJob`はページ毎に空cacheを新規生成、`syncAllZaicoItems`はrun全体で1個を使い回す。
3. 後方互換: 両引数とも省略可能(省略時は従来通りport呼び出し) — `syncSingleZaicoItem`(単発同期)は変更不要。

## unchanged fast path(§10.4/§30.4/§42の必須条件)

修正前・修正後どちらも: unchanged商品はDB write=0、image download=0、thumbnail generation=0、Inventory.updatedAt更新=0 — **この条件は今回の修正以前から満たされていた**(`syncOneZaicoItem`の早期return設計)。今回の修正が対象にしたのは書き込みではなく「unchanged判定に至るまでの読み取りコスト」。

## 残るボトルネック(今回未対応、理由付き)

- `findExistingBySourceId`自体は`prefetched`が渡されない呼び出し経路(`syncSingleZaicoItem`、単発同期)では引き続きScanベース。1件だけの同期なので実害は小さいが、`Inventory.sourceInventoryId`への専用GSI追加 + 生成されるIndex Query APIへの置き換えが本来の恒久修正——このリポジトリ全体で「secondaryIndexesは宣言されているが、どのモデルも実際にはGSI専用のQuery関数を使わずfilter付き`.list()`(=Scan)で読んでいる」という共通パターンを今回確認した(`amplify/data/resource.ts`の`Inventory`/`ChannelListing`等、複数モデルに影響)。この横断的な是正は本ラウンドのP0(ZAICO同期)の範囲を超えるため、技術的負債として明記し今回は見送る。
- ZAICO一覧APIの`updated_at`等による差分取得(§10.5/§30.5)は、ZAICO公式ドキュメントに該当パラメータの記載が無いことを本ラウンドで確認できておらず、推測実装をしない原則によりSPEC_UNCONFIRMEDのまま。
- 完全無人化(ブラウザを閉じても継続、§30.11/§54)は別セクションで扱う(このラウンドで新設したLambda-native pattern — pricing-scheduler/image-processing-worker — を転用可能であることを確認済みだが、今回はまだ配線していない)。
